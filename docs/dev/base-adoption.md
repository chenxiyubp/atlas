## 0. 本文档的定位

本文回答四个问题：**基座是什么、为什么换、它给了阡陌什么又缺什么、代价与风险是什么。**

它**取代**旧文档 `docs/dev/base-analysis.md` 在文档集中的位置，但**定位不同**：旧文档是"一棵不能碰的树的研究笔记"，服务于隔离；本文是"一块地基的采用决策与能力盘点"，服务于施工。旧文档研究的是**另一棵树**（来源不明、无有效许可的第三方反编译树），与本次基座**没有关系**，已随路线变更废止，保留在历史提交 `67f6081` 中。

**证据纪律**：本文所有关于基座能力的陈述都注明出处文件。没有出处的判断标为"推断"。**没有实测的性能数字一律不写**——本文出现的每一个数字要么来自基座自己的文档，要么来自可复现的命令（如 `git log`），且都标了来源。第 7 节列出本报告的局限，请连它一起读。

> **v2.0 读法提醒（重要）**：**§1~§7 是 2026-08-11 的原始分析，其证据等级是"基座文档"，不是源码核实**（原因见 §7 局限 1）。**§8 是 2026-08-16 的代码核实定稿，证据等级是"实跑核实的文件:行号 / 提交 SHA"。凡 §1~§7 与 §8 冲突，一律以 §8 为准。**过时的判断已在原处加"**v2.0 勘误**"注并指向 §8 的对应条目；**没有加注的段落表示 P0.2 复核未推翻它，不表示它已被逐条源码核实**——未核范围见 §8.4。

## 2. 为什么改路线

### 2.1 旧路线（洁净室）在做什么

旧路线的全部工程约束都源自一个事实：**旧基座没有有效的开源许可授权。**没有 LICENSE 即默认"保留全部权利"，且其来源是对他人已发布产品的反向还原。由此派生出一整套隔离机制——`vendor/` 不入库、`scripts/fetch-base.sh` 按 pin 拉取、pre-commit 拦截、CI `vendor-guard`、CI `no-vendor` 作业、`docs/` 零代码片段、M1 前基座必须彻底退场。自研代码则从零写起，落在 `@qianmo/*` 三个包里。

这套机制**本身没有做错**。在那个前提下它是唯一正确的选择。变的是前提。

### 2.2 新前提

| 维度 | 旧基座 | 新基座（occ） |
|---|---|---|
| 许可 | 未识别到有效授权 | **MIT**（可用、可改、可再分发，条件是保留版权与许可声明） |
| 归属 | 第三方，来源不明 | **项目负责人自有** |
| 分发状态 | 单个匿名提交的 GitHub 仓库 | **已在 npm 公开发布**，有版本历史与 tag |
| 可运行性 | 旧调研结论为静态解析下不可运行（多处空实现与整目录缺失） | **完整可运行**（`bun install` / `bun run dev` / `bun run precheck`） |
| 升级路径 | 无（上游闭源，本地只有一个压缩提交） | **有**（git 历史完整，可按 tag 合并） |
| 能否入库/分发/进产物 | 三项全禁 | **三项全可** |

三条硬约束（不可再分发、不可作为交付物、必须隔离）同时消失。**隔离机制失去了隔离对象。**

**这一节是本文最重要的部分。**路线变更不是纯收益，下面每一条都是真实损失，必须让团队在评审时看到。

| # | 损失 | 影响 | 缓解 |

### 2.5 净判断

**收益集中在产品线 ① 与工程质量；产品线 ② 一分未得；法律面是换了一种问题，不是消灭了问题。**

- 产品线 ①（云端常驻编程智能体）：起点从零抬高到"一个功能完整的单机编程智能体"，剩下的是**常驻化**（休眠唤醒、节点形态、沙箱）。
- 产品线 ②（智能体通信协作网络）：**基座给的是零**，理由见 §3.2——跨机传输层在基座上游已被整体删除。路线图 v2.0 因此把传输通道（P2.2）推上关键路径长杆。
- 法律面：从"没有许可，必须隔离"变成"许可清晰，但溯源需要如实陈述并事前咨询"。**后者更好处理，但不是自动消失。**

即便计入 §2.4 的七项代价，路线变更仍然成立——因为 C-1/C-2/C-3 是**举证与陈述成本**，而旧路线的约束是**能力上限**（不能分发、不能进产物、M1 前必须拆掉重写）。用可解释的成本换掉不可逾越的上限，这笔交易划算。**但它不是免费的，评审时请按这个口径理解。**

## 3. 基座给了什么、缺了什么

判定三态：**已有**（可直接使用，我方工作是核验与配置）/ **部分**（有骨架或相邻能力，需改造补齐）/ **无**（基座不提供，从零自研）。

| 阡陌能力 | 判定 | 基座提供了什么（附出处） | 缺口 |
|---|---|---|---|

## 5. 风险

### R-1 ⚠️ 基座是逆向工程产物这一事实，对参赛与开源发布的影响

**这是本报告必须如实写清、且不做任何粉饰的一条。**

**事实（全部有出处）**：

1. 基座自述其定位为"以逆向复原（reverse-engineered restoration）的代码为基座，由社区维护和优化的衍生版本"，并在致谢中记录它 fork 自另一个 Claude Code 还原工程（出处：基座 `README.zh.md`）。

4. 基座 `README.zh.md` 的许可章节**曾**写有"本仓库的还原与原创工作以 MIT License 发布，**仅供学习研究用途**"，同时声明"'Claude'、'Claude Code' 与 'Anthropic' 是 Anthropic 的商标；本项目与 Anthropic 无关联、未获其背书"。**已解决（2026-08-11）**：基座侧同日修正三语 README 许可段——中文版删去"仅供学习研究用途"限定，英文版与日文版补上 MIT 授权表述并统一商标声明；本仓库内的基座 `README.zh.md` / `README.ja.md` 已同款修正。**许可正文与自述自此一致**，商标与"无关联、未获背书"声明**逐字保留不变**。

`retro-m0.md` §3.5 点名了同一件事上的两次判断，**两次都结论对、理由错**。这两处必须有统一的定稿口径，否则答辩现场会被拿同一个数字反复问。
