### 3.4 为什么基线是 `3380c88` 而不是 `848ad8c2`

> **本节的「结论先行」已被 §0′ 附注更新（工作面基线改为 `base-snapshot/v2.46.0`），先读那里。**

**结论先行**：对外举证一律用 **`3380c88`**（本仓库的基座导入提交），**不用 `848ad8c2`**（上游 open-claude-code 的 pin 提交）。依据是章程 **v2.4「举证命令勘误」**（§5.5 末条，另见 §5.8 第 1 条括注、§6.2 L-1 对策②、`base-adoption.md` §2.4 C-1 与 §5 R-2 的同款勘误，以及 roadmap v2.4 与 P8.3 条目）。

理由（章程 §5.5 的判断，本文只转述不复制）：本仓库是**零改动快照导入**，不含上游 git 历史；`848ad8c2` 是**上游仓库**的提交 SHA，在一份正常克隆的本仓库里不是有效 git 对象，`git diff 848ad8c2..HEAD` 会报 `unknown revision`。上游溯源以根 `BASE.md` 的记录 + 与上游仓库比对为准，不经本仓库 git 对象。

1. 只敲 `git diff 3380c88..HEAD` / `git log 3380c88..HEAD` / `git show --stat 3380c88`。
2. 若评委手里的材料写着 `848ad8c2..HEAD`（旧写法；根 `NOTICE` 与 `README.md` 已于 2026-08-15 勘误，见 §3.5 ①），当场说明这是已勘误的旧写法并改用 `3380c88`，**不要现场试跑旧命令**。
3. 不要把 `3380c88` 说成「上游的 commit」。它是**本仓库**的导入提交；上游 pin 是 `848ad8c2` = tag `v2.38.3`，两者是两个仓库里的两个对象，`BASE.md` 记录其对应关系。

git rev-parse 848ad8c2                   → 848ad8c2c8daca9f5aa2410da555553e07700f5d

### Q3「为什么不直接用 Anthropic 官方的 Claude Code 或者官方 SDK？」

**书面答案**

> 三个理由，按重要性排。
>
> **第一，我们要改的东西在扩展点之外。**阡陌的核心是把一个单进程 CLI 改造成沙箱内可休眠、可被跨节点唤醒的常驻节点。这需要动进程内的会话生命周期、流看门狗、信箱读者这些内部机制——比如基座那条 90 秒的流空闲看门狗默认开着，沙箱冻结一次就会把正常的流判成挂死，我们必须让它跨过时间跳跃后重新计时。这类改造在一个闭源产品或一个只给外部接口的 SDK 上做不了。我们的评估结论是：唤醒那半边有现成通道，**休眠那半边没有任何进程内扩展点**。
>
> **第二，许可与归属。**我们需要一个可以入库、可以修改、可以随材料分发、也可以开源的地基。open-claude-code 是 MIT，且归属在团队负责人手里——不会因为第三方仓库删库、改许可或断更而受影响。
>
> **第三，成本与验收线不能互换。**换基座抬高的是起点，不是验收线。我们的八条验收标准在换基座时**一条判据都没有放松**，后来修订的两条（休眠态定义、判环粒度）是把定义改精确，不是把线放松。

### Q6 ⭐「你们安全上最弱的一环是什么？」

**书面答案**（这一问答得越具体越可信）

> 我列四条，按我自己认为的严重程度排。
>
> **第一，跨节点消息构成 prompt injection 攻击面，而且这类攻击只能提高成本、不会被解决。**跨节点消息最终会进入对端智能体的 LLM 上下文，等于把不可信输入喂给模型。它有三重独立性：独立的信任边界、独立的放大机制（恶意 prompt 可在互联 agent 之间自复制）、独立的失效模式（消息事实上替用户做了授权）。我们在立项文档里把它记为技术风险 T-7，并且**把判定基准写死了：不以「模型是否被说服」验收**——验收必须落在结构性约束上（授权链、来源标记、能力边界），「这次没被骗到」不算通过依据。落地上，`user-confirmed` 这一级权限**只认本节点私钥签发的**，远端签得再好也拒，而且这条判断在验签之前就做。
>
> **第二，M0 的默认策略允许未签名的任务请求。**默认 `OPEN_POLICY` 下，可选的只是「是否强制出示令牌」——**出示了就一定全程校验**，但可以不出示。原因是 M0 没有密钥分发机制，`--trust <node>=<publicKey>` 是手工配的、没有 TOFU，在拿不到公钥之前强制签名只会让整张网安静下来。强制版本 `--require-signed-tasks` 已经实现并在集成用例里跑通，M1 上 mTLS 之后切默认。
>
> **第三，审计日志的「不可改」只成立两句，第三句不成立。**写入方改不了（fd 是 `O_APPEND | O_NOFOLLOW`，类里没有 seek / truncate / delete）；外部改动可检测（哈希链断点能定位到具体序号）；但**外部改动无法阻止**——有文件写权限的人可以整篇重写并重算哈希。挡住它需要 append-only 挂载或机外见证，M0 两样都没有。我们没有在代码或文档里声称它不可变，而且专门写了一条用例把这句钉住，免得读套件的人误以为文件是不可变的。
>
> **第四，M0 的加密是 TLS + 预共享密钥，够演示不够上线。**不做 PKI、不做证书签发与轮换、不做端到端加密，这是立项时就写下的非目标，M1 换 mTLS。另外 PSK 是对称的——所以 capability 我们没有用它签，改成每节点 Ed25519 自签，否则任何持钥节点都能伪造任意节点签发的「用户已确认」凭证。

**举证指针**：章程 §6.1 **T-7**（三重独立性 + 判定基准）、§2.2 **N-3**（生产级加密非目标）、§3.3 **C-5**（Ed25519 决议与 N-3 的界线）；roadmap v2.22 **P4.3**（S-1 / S-3 / `OPEN_POLICY` 边界）、v2.28 **P7.2**（「不可改」三句）；`packages/capability/test/authorization-invariants.test.ts`（会变红的扫描）。

**回答纪律**

- **不说**「我们的系统是安全的」「已经做了完整的安全防护」。
- **不说**「prompt injection 我们已经解决了」——判定基准明确写了这类攻击不会被解决。
- 不把 M1 的计划说成 M0 的现状（mTLS、密钥分发都还没有）。
- 举第三条时把「三句只认两句」完整念出来，不要只念前两句。

### Q13「和现有产品比，你们的创新点到底在哪？」

**书面答案**

> 一句话：**把「会话内工具」变成「网络里的常驻节点」，并把这件事的工程边界全部量出来。**

> 具体三条，每条都有可验证的判据：
>
> 1. **常驻与休眠唤醒**：智能体在沙箱冻结态（进程不占用可分配内存、不消耗 CPU 配额）被跨节点唤醒，60 秒内回 ack、5 分钟内回结果。真机实测 10/10，ack P95 是 8.022 秒。

**举证指针**：§2 两栏表右栏；章程 §1.2 核心判断、§1.6 安全设计哲学；`a2a-gap.md` §1 / §2；roadmap v2.20 / v2.22 / v2.23 / v2.25。

> **还没测到的（我不能拿本机数字充数）**：正式的性能与稳定性基线报告——24 小时长跑、n=100 的唤醒延迟阶梯、正式吞吐表——**全部待真机恢复**，目前是未完成状态。我们已经把量具、方法和文档骨架做完了，也把两个会让报告作废的测量坑钉死了：在 Bun 下 `process.memoryUsage().heapUsed` 是个冻结常量（三次采样都是 0.20 MB，而同期 RSS 从 27 涨到 106 MB），所以采样必须走 `bun:jsc heapStats`；而 `heapSize` 是滞后指标，判读必须按多点斜率。

> 另外声明一条范围：M0 的非目标里写明**只测基线、不调优**，除非某项指标卡住验收。
