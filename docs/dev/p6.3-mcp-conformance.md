## 1. 选型与配置

### 1.1 两个第三方 server

两个都从 npm 装进 `node_modules`，**精确 pin**（不是 `^`）写在根 `package.json` 的 `devDependencies`：

| 包 | 版本 | 上游 SDK | 选它的理由 |
|---|---|---|---|
| `@modelcontextprotocol/server-filesystem` | `2026.7.10` | `@modelcontextprotocol/sdk@^1.29.0` | **有副作用、可外部复证**。写进去的东西能用 `node:fs` 直读，不必只信 server 自己的回包；而且它是唯一一个会**消费 roots**、从而暴露互操作差异的官方 server |
| `@modelcontextprotocol/server-memory` | `2026.7.4` | `@modelcontextprotocol/sdk@^1.29.0` | **状态化、且落盘位置可控**。它维护一张知识图并写 JSONL，跟 filesystem 的形态完全不同（结构化输入、跨调用状态），两台合起来才不是"同一种 server 测两遍" |

装依赖走的是 `bun install --registry https://registry.npmmirror.com`，与仓库 `bun.lock` 里既有的 861 条 npmmirror 解析保持同源；锁文件里**没有** `registry.npmjs.org` 条目。

### 1.2 为什么不把 `occ mcp serve` 算成"第三个 server"

会算成自证。DoD 说的是"接入 ≥2 个现成 MCP server"，occ 自己既不是"现成的"也不是"第三方的"。它作为 **server** 一侧的协议覆盖（含 modern 纪元）由存量用例 `src/entrypoints/__tests__/mcp.test.ts` 负责——**本文不复制它的结论，只在 §5 G-1 引用它来说明 modern 纪元的覆盖来自哪里**（指针不复制，CLAUDE.md §1.1⑧）。

### 1.3 故障夹具是夹具

`tests/integration/fixtures/mcp-crash-server.ts` 是我们自己写的约 80 行 MCP server（用树里已有的 `@modelcontextprotocol/server` + `serveStdio`），三个工具：`ping` / `die`（不回包直接 `exit(1)`）/ `hang`（永不 resolve）。

**它不是"第三方现成 server"，不计入 DoD 的那个 2。**它存在的唯一理由是：没有哪个行为正常的 server 能按测试的要求在指定时刻自杀或装死，而 D3 与超时两条用例需要那样一个对端。夹具文件顶部有同样的声明。

### 1.4 核验的边界

- **不接模型。**用例直接拿 occ 构造出来的 `Tool` 对象调 `Tool.call`，走的是真进程、真 stdio、真落盘，但没有任何一次模型推理。"模型能不能挑对工具"是 P1.4 已经证过的事，在这里重复一遍只会把一个确定性用例变成一个要付 token 的抽卡用例。
- **只覆盖 stdio 传输。**http / sse / OAuth 未测，见 §5 G-3。
- **零 mock。**本文件没有任何 `mock.module`。被测的恰好是"真的能不能连上真的进程"，任何替身都会把结论掏空。

### 1.5 脚手架纪律（为什么这些用例不会污染分片）

`tests/integration` 是 CI 的一个分片，分片内所有测试文件**共用一个进程**（`scripts/test-shards.sh` 的说明）。因此：

- 三个临时目录（配置 / filesystem 沙箱 / memory 库）、`OCC_CONFIG_DIR`、`MCP_TIMEOUT`、`originalCwd`、`unhandledRejection` 监听器，全部 `beforeAll` 设置、`afterAll` 成对还原。
- 每个连上的 server 都登记进 `liveConnections`，`afterAll` 逐个 `cleanup()`。`connectToServer` 按 `name + config JSON` memoize 并挂在全局清理表上，不清就会跨用例串味 + 泄漏子进程。
- spawn 一律 `process.execPath` + dist 绝对路径，不用 `node_modules/.bin` 下的 shebang 软链——那玩意在不同安装布局下指向不同解释器，失败时的报错还会伪装成协议错误。
- 每条用例显式 60s timeout（bunfig 默认 10s，spawn 一个真 server 就能吃掉大半）。
- 时序断言遵守 a8b06a9 的教训：**正向结论一律等真实事件 / Promise，只有"某事不该发生"这类反向结论才睡固定窗口**。全文只有一处固定窗口（D3 之后等 250ms 看有没有漏网的 unhandled rejection）。

## 2. 怎么发现的（走的是哪条生产路径）

```
getMcpToolsCommandsAndResources(cb, configs)      src/services/mcp/client.ts
  └─ connectToServer(name, config)                 memoize(name + JSON)
       └─ StdioClientTransport(spawn)              真子进程
       └─ createMcpClient({capabilities:{roots,elicitation}})
       └─ client.setRequestHandler('roots/list')   ← §5 G-2 的坑就在这
  └─ fetchToolsForClient(client)                   listTools → 转成 occ 的 Tool
       └─ Tool.call → ensureConnectedClient → callMCPToolWithUrlElicitationRetry
```

第二个参数直接吃 config record，所以**整套用例不落盘任何 `.mcp.json`**，也就不会碰到开发机上真实的 MCP 配置。`OCC_CONFIG_DIR` 指到临时目录，`isMcpServerDisabled` 读到的是一份空配置。

## 3. 实测数据：发现与调用

跑批环境：macOS (darwin 25.5.0, arm64) / Bun 1.3.13 / 2026-08-15。

```
$ bun test tests/integration/qianmo-mcp-conformance.test.ts
 10 pass
 0 fail
 111 expect() calls
Ran 10 tests across 1 file. [4.49s]
```

逐条耗时（`--reporter=junit`）：

| # | 用例 | 耗时 |
|---|---|---|
| ① | filesystem 工具被发现，并带上 occ 侧的 MCP 元信息 | 92.9 ms |
| ② | filesystem 写—读闭环（MCP 通道 + `node:fs` 双重证据） | 13.3 ms |
| ③ | roots 互操作：roots 顶掉命令行允许目录 | 68.0 ms |
| ④ | memory 工具被发现 | 56.0 ms |
| ⑤ | memory 写—读闭环 + JSONL 落盘证据 | 7.9 ms |
| ⑥ | 两个 server 同时在线，互不串扰 | 2.6 ms |
| ⑦ | D1 进程根本不存在 | 1.5 ms |
| ⑧ | D2 启动即退出（ConnectionClosed 快路） | 54.6 ms |
| ⑨ | D3 在飞调用时对端被杀 + 自愈 | 358.6 ms |
| ⑩ | `request_timeout_ms: 3000` 生效 | 3061.0 ms |

> 后面的用例比前面快，是因为 `connectToServer` 的 memoize：同名同配置的连接只 spawn 一次。⑩ 的 3061ms 就是被测的那个 3000ms 超时本身。

### 3.1 连上之后两台 server 是什么样

| server | 协议纪元 | serverInfo | capabilities | occ 侧工具数 |
|---|---|---|---|---|
| filesystem | `legacy` | `secure-filesystem-server` 0.2.0 | `{"tools":{"listChanged":true}}` | 14 |
| memory | `legacy` | `memory-server` 0.6.3 | `{"resources":{"subscribe":true,"listChanged":true},"tools":{"listChanged":true}}` | 9（+ occ 自己的 `ListMcpResourcesTool` / `ReadMcpResourceTool`，因为它通告了 resources） |
| 故障夹具 | `legacy` | `qianmo-mcp-crash-fixture` 0.0.0 | `{"tools":{}}` | 3 |

工具名（occ 的规范化前缀 `mcp__<server>__<tool>`）：

```
mcp__fs__read_file  mcp__fs__read_text_file  mcp__fs__read_media_file
mcp__fs__read_multiple_files  mcp__fs__write_file  mcp__fs__edit_file
mcp__fs__create_directory  mcp__fs__list_directory  mcp__fs__list_directory_with_sizes
mcp__fs__directory_tree  mcp__fs__move_file  mcp__fs__search_files
mcp__fs__get_file_info  mcp__fs__list_allowed_directories

mcp__mem__create_entities  mcp__mem__create_relations  mcp__mem__add_observations
mcp__mem__delete_entities  mcp__mem__delete_observations  mcp__mem__delete_relations
mcp__mem__read_graph  mcp__mem__search_nodes  mcp__mem__open_nodes
```

### 3.2 调用是真的做了事

- **filesystem**：`write_file` 写入 `阡陌 P6.3 round trip\nsecond line\ttab\n`，`read_text_file` 读回**逐字节相等**；再用 `node:fs` 的 `readFile` 直读同一路径，同样相等。第二重证据不是冗余——只信 `read_text_file` 的话，一个把写入丢进内存的 server 也能让用例变绿。
- **memory**：`create_entities` 建一个实体，`read_graph` 与 `search_nodes` 都命中；再直读 `MEMORY_FILE_PATH` 指向的 JSONL 文件，里面有该实体。

> **`MEMORY_FILE_PATH` 必须覆盖。**memory server 的默认库路径是它自己的 `dist` 目录（`path.dirname(fileURLToPath(import.meta.url))/memory.jsonl`）——不覆盖就会往 `node_modules` 里写，既污染依赖目录，又让两次跑批互相看见对方的数据。用例通过 stdio config 的 `env` 字段把它指到临时目录（occ 的 stdio 传输把 `subprocessEnv()` 与 config 的 `env` 合并后交给子进程）。

### 3.3 两台同时在线互不串扰

一次 `getMcpToolsCommandsAndResources` 调用同时给两个 config，断言：

- `fs` 的工具全部 `mcp__fs__` 前缀、没有一个 `mcp__mem__`，反之亦然；
- 同一批里对两台各写一次：filesystem 的内容落进沙箱文件（`node:fs` 复证），memory 的实体落进 JSONL，且 **JSONL 里没有 filesystem 那个 marker**；
- 反向再查一遍：`list_directory` 列出沙箱，里面**没有** `memory.jsonl`。

## 4. 实测数据：降级

DoD 的"server 不可用时降级不崩溃"拆成三种真实故障形态。**三条的共同断言是同一句话：坏的那个坏了，好的那个照常。**只断言"坏的坏了"是不够的——降级的价值全在后半句。

| # | 形态 | 怎么造出来 | occ 的反应 | 实测证据 |
|---|---|---|---|---|
| **D1** | 进程根本不存在 | `command` 指向一个不存在的可执行文件 | 发现流程正常 resolve（不 reject）；该 server `type='failed'`、`tools.length===0` | `error: ENOENT: no such file or directory, posix_spawn '<path>/nope'`；耗时 1.5ms |
| **D2** | 启动即退出 | 真的 filesystem server + 一个不存在的允许目录（它自己会在 connect 之前 `process.exit(1)`） | 同上，`type='failed'` | `error: Connection closed`；用例 ⑧ 整条 **54.6ms**——走的是传输层 ConnectionClosed 快路，不是超时兜底（另跑一次 5 个 server、其中 2 个故意坏的批，整批 138ms） |
| **D3** | 在飞调用时对端被杀 | 夹具的 `die` 工具：收到请求后不回包、直接退进程 | 在飞的 `Tool.call` **抛错但不挂死**；**再调用同一个 Tool 对象会自动重连成功** | 抛 `TelemetrySafeError… \| Connection closed`；紧接着 `ping` 返回 `[{"type":"text","text":"pong"}]`；`unhandledRejection` 收集器为空 |

D2 的用例把"快"钉成了断言（`elapsedMs < 4000`，而 `MCP_TIMEOUT` 兜底被设成 5000ms）。**具体错误文本不断言**——那是 SDK 的措辞，会随版本变；要钉的是走哪条路。

D3 的自愈机制：连接的 `onclose` 处理器清掉 `connectToServer` 的 memoize 缓存，于是下一次 `ensureConnectedClient(client)` 会重新 spawn 一个进程。**注意副作用**：重连出来的是一个新的连接对象，Tool 闭包里那个已经死了——用例显式把活的那个捞出来登记，否则 `afterAll` 关不掉它。

### 4.1 超时：默认等于没有

```
$ 用 request_timeout_ms: 3000 调夹具的 hang
THROWN after 3003ms: MCP server "slow" tool "hang" timed out after 3s
```

**不配 `request_timeout_ms` 的话，这个调用会挂 27.8 小时。**详见 §5 G-4。

## 5. 缺口清单（这次没覆盖到什么）

| # | 缺口 | 影响 | 建议处置 |
|---|---|---|---|
| **G-1** | **两个第三方对端都只跑 legacy（2025）纪元。**两个包都依赖 `@modelcontextprotocol/sdk@^1.29.0`（v1 SDK），实测 `getProtocolEra()` 三个对端都是 `legacy`。modern（2026-07-28）纪元在本仓库**只有 occ 自己的 `mcp serve` 有覆盖**（`src/entrypoints/__tests__/mcp.test.ts`，它对同一个 factory 分别用 v1 客户端与 pin 到 `2026-07-28` 的 v2 客户端各跑一遍并比对工具集）——那证的是 **occ 作为 server** 的 modern 能力，**不是 occ 作为 client 连一台 modern 第三方 server**。 | 「occ 作为 MCP client 在 modern 纪元下的互操作」目前**零第三方证据**。生态里 v2 SDK 的现成 server 还很少，这是生态状态，不是我们的实现缺陷 | 等生态出现 v2 SDK 的现成 server 后加一台进同一套用例（用例结构不用改，加一条 config 即可）；或者退而求其次，用夹具 + `@modelcontextprotocol/server` v2 造一台 modern-only 的对端——但那样测的又是我们自己写的 server |
| **G-2** | **roots 通告会整体顶掉 filesystem server 命令行上的允许目录。**occ **无条件**通告 `roots` 能力，并用 `file://${getOriginalCwd()}` 回答 `roots/list`（`src/services/mcp/client.ts` 的 roots/list handler）；filesystem server 的 `updateAllowedDirectoriesFromRoots` 是**替换**而不是合并。于是 `.mcp.json` 里 `args` 上写的允许目录**在连接建立的一瞬间就被 occ 的 cwd 顶掉了** | 部署上是个**真坑**：运维照官方 README 写 `args: [/srv/data]`，实际生效的却是 occ 进程的 cwd。轻则"配了没用"，重则把不该暴露的目录暴露给了 server。用例把它钉住了：命令行给 A 目录、roots 给 B 目录，`list_allowed_directories` 只回 B，读 A 下的文件报 `Access denied - path outside allowed directories: …A/x.txt not in …B` | **本次不改**（P6.3 是核验性质，且改动落在基座核心文件）。真要改有两条路：① 让 roots 通告可按 server 关掉（配置项，扩展点够用）；② 部署侧约定"用 roots 而不是命令行参数"并写进运维文档。**建议先做 ②**，把 ① 留给需要它的任务包 |
| **G-3** | **只覆盖 stdio 传输。**http / sse / websocket / OAuth 授权流全部未测 | 阡陌节点未来要连的**远端** MCP server 走的正是 http/sse + OAuth，那条路上的失败面（401 缓存、token 刷新、SSE 重连、限流）与 stdio 完全不同，本文一条都没证 | 单开任务包。远端传输需要一个真实端点或一台本地 OAuth 桩，成本比本文高一个量级，塞进 P6.3 会把它拖成实现任务 |
| **G-4** | **MCP 工具调用的默认超时 ≈27.8 小时，等于没有超时。**`DEFAULT_MCP_TOOL_TIMEOUT_MS = 100_000_000`（`src/services/mcp/client.ts`），`MCP_TOOL_TIMEOUT` 环境变量未设时就是它 | 常驻节点上，一个装死的 MCP server 会把一次工具调用**永久**挂住。用例证明逐 server 的 `request_timeout_ms` 生效（3000ms 配置 → 3003ms 抛错），但那是**要显式配才有**的 | **部署纪律**：每个接入的 MCP server 都必须在配置里写 `request_timeout_ms`。这条要进节点的部署清单，不是代码改动 |
| **G-5** | **`packages/mcp-client` 是一份平行的、未接线的实现。**它自带 `createMcpManager` / `callMcpTool` / `discovery`，但 `grep` 全树只有 `src/services/mcp/client.ts` 引用它的 **4 个小工具函数**（`getMcpHttpStatus` / `isMcpSessionExpiredError` / `MAX_MCP_DESCRIPTION_LENGTH` / `recursivelySanitizeUnicode`）；`createMcpManager` 与 `callMcpTool` **零调用者** | 本文测的是 `src/services/mcp/client.ts` 那条**线上路径**。那个包里的降级网（如果有）**一条都没测**。谁将来误以为"MCP 客户端逻辑在 packages/mcp-client 里"并去改它，改完不会有任何用例变红 | 不在 P6.3 范围内。若阡陌将来要用那个包（比如给 `@qianmo/*` 提供一份不依赖 occ 全局状态的 MCP 客户端），必须**先**给它补一套等价的降级用例 |
| **G-6** | **`structuredContent` 会整体顶掉 content 数组。**只要 server 回了 `structuredContent`，occ 的 `transformMCPResult` 就优先用它，把整个结构 `jsonStringify` 成**一个字符串**交出来，`content` 数组根本不看 | 不是缺陷，是既定行为，但**接第三方 server 时会反直觉**：这两台 server 的工具几乎都声明了 `outputSchema`，所以拿到的是 `{"content":"…"}` 这样的 JSON 串而不是 text block。用例里的逐字节比对因此要先取字段再比 | 记录即可。真要注意的是**下游消费者**：任何按"MCP 结果是 content block 数组"写的解析代码，遇到声明了 `outputSchema` 的 server 都会拿到字符串 |

## 6. 复现步骤

```bash
# 0. 装依赖（两个 server 是 devDependencies，精确 pin）
```
