### D-1 AC-2 的「休眠态」认不认 Dormice 的 frozen？

**实测依据（新）**：E4 证明 frozen 下进程连同 200 MiB 状态字节级完好、PID 不变、端口保持监听；E2 给出唤醒代价：`unpause` 50 ms + 工作集换回 9–10 秒（400 MiB）。机制是 `docker pause` + cgroup `memory.reclaim`，**不是快照，所以 CRIU 的限制一条都不适用**。

**冲突**：AC-2 判据写「进程**不在内存**、状态仅落盘」，字面对应 `stopped`（SIGKILL）。而 frozen 是进程仍在、页被换出（实测常驻 373 MiB → **1.4–5.1 MiB**）。

**决议**：**认 frozen**，并按「进程不占用可分配内存、且不消耗 CPU 配额」的口径改写判据。理由：AC-2 想验证的是「休眠不烧资源、唤醒够快」，不是「进程表里没有这一项」，实测数据支持这个改法。**判据修订文本见 `charter.md` §4，本文不复制。**

**决议日期**：2026-08-12

**状态**：负责人已拍板，按章程 §7.3 属验收标准调整，**待 S0 P0.8 全员评审确认；未通过则回退原判据**。

### D-2 AC-3 的「首次回访节点即切断」是否改为处理者粒度？

**事实**：RFC 3261 附录 A 把节点粒度回访检测定性为规范级 bug。另有两个独立缺陷：起始节点不自我播种、自动回复乒乓三个开关全抓不到。

**决议**：**改**，判环粒度改为「同一处理者地址（node/agent）+ 同一任务标识」，`maxHops`（数值见 `LIMITS`）仅作兜底。这不是放松验收线，是修正一个会误杀合法路由的设计。**判据修订文本见 `charter.md` §4，本文不复制。**

**决议日期**：2026-08-12

**状态**：负责人已拍板，按章程 §7.3 属验收标准调整，**待 S0 P0.8 全员评审确认；未通过则回退原判据**。

### D-3 AC-2 的「连续 10 次 P95 ≤ 60s」进不进 CI 门禁？

**事实**：n=10 的 P95 就是**第 2 大的观测值**，等于「去掉最差一次后的最差值」。CodSpeed 实测 GitHub runner 变异系数 2.66%，据此 2% 门禁假阳性率 **45%**；Google 的经验是逼近 1% 抖动测试就失去价值；MongoDB ICPE'20 记录静态阈值造成高达 **99%** 假阳性；Criterion.rs FAQ 原话：「你大概不该这么做，真做了也别信结果」。

**决议**：**不进门禁，改双层**。CI 里只放**超时兜底**（Bazel 式，抓死锁/挂起，对抖动免疫）；延迟测量挪到**独立非阻塞 job**，跑 N≥5、同机同 job 测基线、报**相对中位数差值**并留档。判据措辞相应调整（改为以基准报告为准）。**判据修订文本见 `charter.md` §4，本文不复制。**

**决议日期**：2026-08-12

**状态**：负责人已拍板，按章程 §7.3 属验收标准调整，**待 S0 P0.8 全员评审确认；未通过则回退原判据**。

### D-5 E1 暴露的安全面要不要现在加固？

**事实（实测）**：AC-6(c) 目前**只靠一件事**成立：daemon 绑在 `127.0.0.1`。而 `iptables -P INPUT ACCEPT`、`DOCKER-USER` 只挡云元数据、宿主 `0.0.0.0:22/80` 从沙箱内可达、API key 无权限分级（`destroySandbox` 与 `execCommand` 同一把 bearer）。`sites-available` 里还躺着一份指向 3676 的 nginx vhost（含一份 `.as-synced` 副本），**启用即全开**。

**决议**：**加固，三件小事全做**——① 往 `DOCKER-USER` 加一条禁止 docker0 网段访问宿主 3676 的规则（纵深防御，不再是单点）；② 把那两份 dormice vhost 移出 `sites-available` 或改名加 `.disabled` 后缀；③ 把「daemon 只绑 `127.0.0.1`」写成一条 CI 可断言的不变式，而不是靠人记。落实为 roadmap **P0.7**（任务包与 DoD 见 `roadmap.md`）。

**决议日期**：2026-08-12

**状态**：负责人决议（技术决议，负责人可定），2026-08-12。**①②③ 已于 2026-08-12 在实验/演示服务器上真机落地并验证，其中对 D-5 的具体手段做了一处实测纠正，见下。**

**落地记录与手段纠正（2026-08-12，真机实测）**：

- **②vhost 已 disabled**：两份 dormice vhost 加 `.disabled` 后缀，`nginx -t` 通过；`sites-available` 内已无 `.conf` 再引用 3676。原本它们未启用（`sites-enabled` 只有 kiln），改名不影响任何运行服务。
- **①防火墙——D-5 原文「加到 `DOCKER-USER`」经实测纠正为「INPUT 链为主、`DOCKER-USER` 作纵深冗余」**。根因：容器访问宿主本机端口的流量走 **INPUT 链**，不走 `FORWARD`/`DOCKER-USER`。从 docker0 沙箱容器（`dormice-base` 镜像 + node）探测宿主 3676，用连接三态区分 `ECONNREFUSED`（端口无监听、内核回 RST）与 `TIMEOUT`（被 DROP 静默丢弃）：
  - 加固前：**`3676 ECONNREFUSED`**（daemon 绑 `127.0.0.1`，容器够不到）
  - 仅加 `DOCKER-USER` 规则：**`3676 ECONNREFUSED`（不变）——实证 D-5 原方案对此威胁无效**
  - 加 INPUT 规则后（`-i docker0 --dport 3676 -j DROP`）：**`3676 TIMEOUT`——实证 INPUT 上那条才是生效项**
  最终两层都加（INPUT 生效 + `DOCKER-USER` 纵深）；全程宿主 `80 REACHABLE` 不变，加固精准无误伤。
- **持久化**：加固写成幂等脚本 `harden-dormice-host.sh`（装于 `/usr/local/sbin`）+ systemd unit `dormice-harden.service`（`PartOf=docker.service`，绑 docker 生命周期，因 docker 重启会 flush 并重建 `DOCKER-USER` 链）。实测：手动删两条规则后 `systemctl restart` 自动重加成功。
- **③不变式**：`check-daemon-bind.sh` 断言 daemon 仅监听回环。两态实测均正确——对真实 daemon `127.0.0.1:3676` 绿灯退出 0；对临时 `0.0.0.0:39999` 监听红灯退出 1（报「违反不变式」）。**接入 CI 仍留 P0.7 正式做**：当前仓库无 daemon 集成代码、CI 也够不到部署环境，本脚本是服务器侧运行时自检与 P0.7 的入库草稿。
- 三个脚本均不含主机名 / 公网地址 / 凭据，符合 P0.7 DoD；服务器 `/tmp` 的临时副本已清理。

### D-6 AC-4 的来源标注机制怎么选？（与 AC-5 冲突）

**冲突**：调研推荐用 Anthropic 原生 `search_result` 引用块实现「标注来源 ID 与写入时间」。但**它与结构化输出互斥（同用报 400，已用官方 API 参考核实）**，且**只在 Anthropic 线存在**——而 AC-5 要求模型中立、换供应商只改配置不改代码。照此实现，AC-4 与 AC-5 会在 S1 之后互相打架。

**三条出路**：① 在适配层自建引用协议（跨供应商，工作量最大）；② AC-4 只在 Anthropic 线验收并写入豁免；③ **全量注入 + 工具层强制引用**，不依赖原生块。

**决议**：**选 ③（全量注入 + 工具层强制引用）**。理由：调研实测显示纯确定性检索在对抗查询上只有 8/10（最致命的失败是词表不匹配：查「语义搜索」而条目写「向量数据库」→ 0 结果）；条目 < 50 条 / < 20k tokens 时**全量注入**让 5/5 成为结构性保证而非概率；基座自己的 `MEMORY.md` 全量加载就是先例。

**决议日期**：2026-08-12

**状态**：负责人决议（技术决议，负责人可定），2026-08-12。

### D-7 新增技术风险 T-7：跨节点消息 = prompt injection 攻击面？

**事实**：跨节点消息最终会进入对端智能体的 LLM 上下文——等价于把不可信输入喂给 LLM。它有三重独立性：独立的**信任边界**（节点间）、独立的**放大机制**（恶意 prompt 在互联 agent 间自复制）、独立的**失效模式**（confused deputy 式伪授权）。OWASP 2025-12 单发的《Top 10 for Agentic Applications 2026》中 **ASI06 Memory & Context Injection** 直接命中阡陌的记忆系统。

**要点**：AC-3 目前只测了「对端声称已获授权」**一种**攻击。判定基准必须写死：**不以「模型是否被说服」验收**——OWASP / OpenAI / Anthropic 三家 2026 年口径一致认为此类攻击不会被解决，只能提高成本。

**决议**：**采纳**，登记为章程 §6.1 的技术风险 **T-7**。风险条目正文（影响/概率、对策、责任人）以 `charter.md` §6.1 为准，本文不复制。

**决议日期**：2026-08-12

**状态**：负责人决议（技术决议，负责人可定），2026-08-12。

### D-8 M0 的 capability 用不用每节点 Ed25519 签发？

**事实**：纯预共享密钥（PSK）是**对称**的——持有它的任何节点都能伪造**任意节点**签发的令牌，**包括伪造「用户已确认」凭证**。于是 C-5「消息不能替用户授权」从结构性保证退化为约定。该原则的理论对应物是 confused deputy / ambient authority，正确形态是 capability（designation 与 authority 合一）。

**决议**：**用每节点 Ed25519 密钥签发 capability，PSK 只做接入门禁**。`node:crypto` / WebCrypto 均已实测可用、零依赖，M0 自研约 200 行。Macaroons 的 JS 实现已全部烂尾，Biscuit / SPIFFE / UCAN 对 M0 过重。

**决议日期**：2026-08-12

**状态**：负责人决议（技术决议，负责人可定），2026-08-12。

### D-9 协议对齐 A2A 到什么程度？

**事实**：A2A v1.0 规范中**完全不存在** hop / TTL / 过期 / 环路检测 / 去重键字段（已逐词检索确认）——阡陌 AC-3 的全部核心字段在 A2A 里都得塞进 `metadata` 或自定义扩展。但任务状态机名、`taskId`/`contextId` 分离、Agent Card 形状这三处对齐是**免费的**。

**决议**：**自研协议 + 概念对齐，不采用 A2A 子集**。并把 `trace_id` 直接改用 W3C `traceparent` 格式——MCP 2026-07-28 已把它写进规范（SEP-414），免费获得生态互通。

**决议日期**：2026-08-12

**状态**：负责人决议（技术决议，负责人可定），2026-08-12。

| 实验 | 问的是 | 结果 |
|---|---|---|
| **E1**<br>（证实） | 沙箱能否够到宿主 daemon（AC-6(c) 的唯一依靠） | **不能。**五个地址全部 `ECONNREFUSED`（0 ms 返回，是主动拒绝而非丢包）。**但基础比预期薄**：唯一屏障就是 daemon 绑在 `127.0.0.1`——同一时刻宿主 `0.0.0.0` 上的 22/80 从沙箱内**完全可达**，`DOCKER-USER` 链只挡云元数据，**没有任何一条规则限制 docker0 → 宿主**。且 `sites-available` 里躺着一份 `proxy_pass http://127.0.0.1:3676` 的 nginx vhost（当前未启用）——**一旦启用，沙箱不需要 DNS 就能打到全量 API，含 `destroySandbox`** |
| **E2**<br>（部分证伪） | ~50 ms 唤醒是不是「恢复到全速」 | `unpause` 实测 **46.6–55.5 ms**（厂商说法对，但只对这一个系统调用）。**400 MiB 工作集换回全速另需 9.0–10.2 秒**，三次一致。期间 `echo` 仍在 ~130 ms 内返回——**迟滞只落在触碰旧工作集的代码上**。另有一个稳定的**永久回归**：稳态 29–31 ms → 36–40 ms（**+25%**），此后不再劣化。冻结耗时 2.40 s（首次）/ 0.19–0.23 s（后续，swap slot 未释放） |
| **E3**<br>（完全证实） | 沙箱内自主工作会不会被静默冻结 | **会，且不能自行恢复。**一个 100% CPU 忙碌的进程在启动 **110 秒**后被冻，**411 秒零推进**，ledger 状态始终 `frozen`。空闲判据只由 API 入口的 `touch` 刷新，对容器内 CPU/IO **零可见性**。**并且 `stopAfterSeconds: null` 不但救不了，反而把故障从「掉到 stopped、下次冷启重来」升级为「永久静默冻在半途」** |
| **E4**<br>（假设证伪） | freeze/unfreeze 会不会破坏长驻 Bun 进程 | **不会。**三轮冻醒后 PID 恒定、200 MiB 状态字节级完好、端口保持 LISTEN、定时器 121–307 ms 内恢复，无退化。**但时钟会集体跳**：`CLOCK_MONOTONIC` 在冻结期间**照常前进**（34 s 与 97 s 两种量级上 `gap_mono` 与 `gap_wall` 差 < 10 ms）——**换单调时钟躲不掉**。`setInterval` 不补跑：34.7 秒的空档只产生 1 个 tick |

> **两条必须写进设计的新结论。**
>
> **①** 常驻配置**不能**用 `stopAfterSeconds: null`。要么整条冷却链关掉（`freezeAfterSeconds: null`，等于放弃 Dormice 的核心价值），要么**自建外部心跳，周期严格小于 `freezeAfterSeconds`，且必须打 API——沙箱内自己动没用**。这个心跳与 §5 的 activator 是同一个组件的两张面孔，且它**绝不能暴露 `destroy`**。
>
> **②** 唤醒瞬间，所有「距上次见到 X 多久」的判据会**同时**越阈值一起触发。必须有显式的时间跳跃检测与宽限窗口（例如任一 tick 的 `gap > 2×period` 即判定刚解冻、重置全部截止时间），否则常驻 occ **每次醒来都会自我判死一次**。

### Bun 侧实验 E5 ~ E6

| 实验 | 问的是 | 结果（Bun 1.3.13 / macOS arm64） |
|---|---|---|
| **E5**<br>（不复现） | Bun issue #24690：`stdout:'pipe'` 在 `bun test` 内是否返回空 | **不复现，测试 harness 不受此限制。**三种捕获方式（`new Response(proc.stdout).text()` / `for await` / `spawnSync`）在 runner 内外都拿到完整输出；加压后仍全绿：**200 KB 输出完整（200,014 字节）**、**10 路并发 10/10**、`--isolate` 与 `--parallel` 下同样通过 |
| **E6**<br>（推断被推翻） | per-test 超时会不会杀掉派生的子进程 | **会杀。**此前的推断是「不杀，症状是 `bun test` 在收尾时挂住」——**错的**。实测 Bun 显式打印 `killed 1 dangling process`，超时后子进程已死。Bun 自带 dangling-process 追踪，是一层免费的安全网；但**它只覆盖直接子进程**（孙进程仍需 `detached` + 进程组处理） |

### E2 对 AC-2 60 秒预算的换算（含未实测的外推）

400 MiB 工作集吃掉约 10 秒，占 60 秒预算的 **~17%**。占用近似线性于工作集大小，occ 常驻堆通常显著大于 400 MiB；按线性**外推**，1.5 GiB 量级会吃掉 30–40 秒——余量不足以再叠加一次冷启动或一次模型往返。**该外推未实测，只测了 400 MiB 一个点位。**

**但这个数字高度依赖 ack 的实现方式**：若 ack 路径只回一个「收到」而不触碰旧堆，成本接近 130 ms；若它要读旧状态，就要付上面那笔。预算设计必须显式区分这两类 ack——这是 P1.1 协议草案要定的事。

下列不需要评审：证据链完整，且不触碰验收判据。

| 领域 | 选定 | 依据 |
|---|---|---|
| 传输 | 单条 **wss 长连接**；消息语义用「ack 帧 + 稍后 result 帧」解耦 | 语义上不能挂住 HTTP 请求 5 分钟；而回调式 POST 要求两端互相可达，M0 部署在 NAT 后的学生机 |
| 常驻宿主 | **ACP**，不是 daemon worker | 已有多会话表、`loadSession`、per-session 失效，且绕过 `main.tsx` 全部冷启动重活 |

| 备份 | **自研，不用 Dormice 归档** | 它的归档是**移动不是备份**：restore 成功后 S3 对象即删，全程单副本无时间点。AC-6(b) 零覆盖 |
| 常驻保活 | **宿主侧极薄 keepalive 代理**，周期 < `freezeAfterSeconds` | E3 实测：沙箱内自主工作对空闲判据零可见，会被静默冻死。心跳必须打 API，且**只暴露 `touch`/`acquire`，绝不暴露 `destroy`** |
| 记忆召回 | 确定性检索 + **小规模全量注入**，不上向量 | 实测纯检索在对抗查询上 8/10；全量注入让 AC-4 的 5/5 成为结构性保证。基座纯文件式路线正是行业收敛方向（Letta 正废弃 `core_memory_*` 转向 git 支撑的文件式记忆） |
| 记忆字段 | 抄 **Graphiti** 的双时间轴语义 | `valid_at`/`invalid_at`（事件轴）+ `created_at`/`expired_at`（摄取轴），**只标记不删除**。注意 mem0 在 2026-04 的 v3 删掉了 ADD/UPDATE/DELETE 决策流改为只追加——按旧文档设计会得到相反行为 |
| 测试传输 | 单机集成测试走 **unix domain socket**；跨机 e2e 才用 TCP | 绕开端口分配、TOCTOU 与 `reusePort` 陷阱（实测两个 server 绑同端口无报错，Linux 上会非确定性分流）。`bun test` 默认**不并行跑文件**，端口冲突问题本不存在 |
| 测试清理 | `await using proc = Bun.spawn(...)` 为主，模块级注册表 + 信号兜底 | `Subprocess extends AsyncDisposable`，是唯一在断言抛错时仍确定性执行的清理；`afterAll` 在 timeout/`--bail`/SIGINT 下是否执行官方无文档 |
| 测试隔离 | **`bun test --isolate`** | 实测**消灭了让基座 CI 连红 55 次的那类 mock/env 跨文件污染**，且**在阡陌自有包上零开销**。这是本次调研里性价比最高的一条 |

## 5. 新识别的必需组件：跨节点 activator

> **跨节点 activator ——「接住请求 → 唤醒目标节点 → ready 后转发」这一层，现有任务包里没有它。**
> 内核 accept queue 的缓冲**只在同机有效**（socket activation 解决不了跨机），Dormice 的 daemon 也只听本机、不提供这一层（实测确认）。它的角色等同 Knative 的 activator、等同 `systemd-socket-proxyd` 的跨节点版，**是阡陌唯一必须自己写的基础组件，且 AC-2 直接压在它上面**。

E3 之后可以确定：它与常驻保活心跳**是同一个组件的两张面孔**——都要在宿主侧、都要代表沙箱去打 daemon 的 API、都必须**只暴露 `touch`/`acquire` 而绝不暴露 `destroy`**（否则 AC-6(c) 立刻不成立）。这是 M0 里唯一没有先例可抄、又同时压着两条验收标准的组件，须单独立一个任务包并给足工时。
