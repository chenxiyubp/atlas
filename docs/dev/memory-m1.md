## 0. 问题定义

出口判据原文：「检索命中率与幻觉引用率有量化指标并优于 M0 基线」。定案时的事实：

1. **M0 只有通过/不通过，没有比率。** AC-4 的证据是 5 条决策 × 2 家命中 10/10、3 条伪造决策 × 2 家引用数 0/6（roadmap P3.3 完成记录；负例判定点是「被接受的引用为空」，`tests/integration/qianmo-memory-recall.test.ts:578`）。它只覆盖全量注入模式下的 5 条条目。
2. **M0 从未在注入阈值之上测量过。** 阈值为 50 条 / 20 000 字符（`packages/recall/src/inject.ts:56-59`）。阈值以下候选全部注入，D-6 的「词表不匹配 → 0 结果」失败面被结构性消除；阈值以上靠排序截断，该失败面会回来。
3. **常驻链路没有引用强制点。** P13.7（`d9bd024b`）只把记忆块注入用户消息（`packages/resident/src/memory-sidecar.ts:197`，仅调用 `renderInjection`）。**评审已按扩大范围核实**：`handleMemoryAnswer|verifyCitations|MEMORY_ANSWER_TOOL|qianmo_memory_answer|injectedIds|citationInstructions|buildRecallSystemPrompt|renderCitedAnswer|parseMemoryAnswerArgs` 全仓去掉 docs、`*.md`、`packages/recall` 后只剩两个测试文件；`@qianmo/recall` 的非测试导入方只有 `memory-sidecar.ts` 与 `scripts/qianmo-recall-baseline.ts`；ACP 会话的 `mcpServers` 恒为 `[]`（`packages/resident/src/acp-client.ts:178`、`:195`），常驻会话额外工具面只有 `qianmo_notify`（`src/services/qianmo/notifyTool.ts:224-226`）。v0.1 担心的「间接调用漏检」已排除。
4. **（v1.0 新增）生产代码里没有任何记忆写入方。** 对 `FileMemoryStore` 的写调用（`.write(` / `archiveWorkingMemory(` / `.revoke(` / `.invalidate(`）在 `packages/memory` 之外只出现在测试与 `packages/recall/eval`；`@qianmo/memory` 的非测试导入方（recall、`memory-sidecar.ts`、`src/services/qianmo/resident.ts`）全是读。方法：评审 grep，主 agent 在 `9770e8a7` 上复跑（对这些导入方的写调用 grep 结果为空）。后果：常驻链路的 working 层在真实节点上恒为空，sidecar 每轮返回 `''`；ranked 模式（语义层唯一生效的模式）在生产上不可达；`defaultMemoryRoot()` 是配置根下的 `memory/`（`packages/memory/src/paths.ts:32`），与基座 auto-memory 的 `projects/<slug>/memory/` 是兄弟目录，基座写的记忆也进不来。

**范围结论（事实 4 的二选一）**：取「补写入路径」。M1 提供两条生产写入路径（P16.W，§6.4）；不补的话「上线」这个判据不成立。

本稿做四件事：把两个指标定义到可计算；给出检索层的可复现 M0 基线（已执行，§3）和回答层的测量协议（未执行，§4）；在同一套测量方法上设计语义叠加（§5）与治理（§6）；给出生产写入路径（§6.4）。

> **对外口径**：在 roadmap、发行说明、内测公告或答辩材料里写「记忆能力上线」或「优于 M0 基线」之前，措辞由负责人确认。判据以本稿 D-1 的定义为准，数字只描述合成语料与仓库 `docs/dev` 语料；**未在真实节点记忆上评估**（D-8 继续缓）。回答层在 P16.4 / P16.12 执行之前**没有任何数字**。

## 2. 指标定义

### 2.1 检索层（离线、确定性，不需要模型）

记号：查询 q；gold 集 G(q) 为应当到达模型的条目；禁入集 F(q) 为不得到达模型的条目（已 revoke、事件轴已失效、在其他 scope）；候选集 C(q) 为 scope 内全部 live 条目；R(q) 为 C 的全序排序；注入集 I(q) 为套预算后 R 的前缀。

| 指标 | 公式 | 何时有信息量 |
| --- | --- | --- |
| recall@k | \|G ∩ R[1..k]\| / \|G\| | 衡量排序本身；G 为空的查询不计入均值（既不算 0 也不算 1） |
| MRR | 均值 1 / rank(R 中第一个 gold) | 同上 |
| 候选集召回 | \|G ∩ C\| / \|G\| | 由 I-1 保证恒为 1，作不变式监测，不是质量指标 |
| **注入覆盖率** | \|G ∩ I\| / \|G\| | **核心指标。只在 \|C\| 超过阈值（`mode="ranked"`）时有信息量**；全量模式下由构造恒为 1 |
| 禁入泄漏 | Σ\|F ∩ I\| / Σ\|F\|（另报 Σ\|F ∩ C\|） | 安全不变式，目标恒为 0 |
| top-1 诱饵 | 排第一的条目不在 G 且词面相关度 > 0 的查询数 | 描述回答层要面对的词面诱饵压力，不作优劣判定 |
| full 模式占比 | `mode="full"` 的查询数 | 决定「块里没有 = 库里没有」是否成立（`inject.ts:159-171` 把这一点写进块头） |

检索层的出口判定**逐题配对**，不比汇总比率（D-1）：汇总比率会让「丢 2 道词面题、得 3 道零词面题」也算通过。

### 2.2 回答层（需要真实模型）

每题一次 `qianmo_memory_answer` 调用，经 `handleMemoryAnswer` 得到每条引用的六种判定之一。**P 只含 40 道正例**（20 道词面重叠 + 20 道零词面重叠）；负例类别里带 gold 的题（取代已废止条目的 live 条目等）单列报告，不进 H 的分母。Q 为全部查询，S(q) = G(q) ∪ 标注为可接受的相关条目。

- **命中率** H = \|{q ∈ P：首轮 accepted，G(q) ∩ accepted ≠ ∅，且 `mustMention` 全部出现}\| / \|P\|。`mustMention` 的匹配先做规范化（NFKC、小写、去空白），并给每项一个同义候选列表（如 `60` 与「六十秒」）；另报一个**不含 `mustMention`** 的 H，把检索、引用与措辞分开看。
- **幻觉引用率**拆成两个，分开报告：
  - **伪造引用率（拦截前）** HR_fab = 判定为 `unknown` 或 `malformed` 的引用数 / 全部引用数；另报按题口径。它衡量模型倾向。按引用计的分母会随 M1 注入更多相关条目而变，所以 **HR_fab 只报告、不作门禁**。
  - **误归因率（拦截后，用户可见）** HR_mis = \|{q：accepted 中存在 c ∉ S(q)}\| / \|Q\|。伪造决策负例 S = ∅，任何被接受的引用都算，与 AC-4 集成腿的判定一致（`:578`）。**S(q) 在第一次调用之前冻结**；两臂不一致的案例按 A6 裁定。**已知偏差**：严格口径会把「记忆里没有记录；相关的只有 X」这类有用的回答也算作误归因，而 M1 注入的相关条目更多，会系统性抬高 HR_mis。这是指标设计上的偏差，不是幻觉；A6 只能部分缓解。
- **单独报告、不计入幻觉**：`unreadable`（真条目损坏）；`retired` 与 `not-injected`（真 id 但不在本轮证据内，记为越界引用率）。**评测中一旦出现 `unreadable`，整轮判无效**（D-2）：合成语料经真实 store 写入，出现即说明测量仪器故障，照 `packages/recall/eval/run.ts` 对 `degraded` 的处理方式抛错。

### 2.3 数据集与规模档位（v0.1 语料，M0 基线所用）

实现见 `packages/recall/eval/dataset.ts`。条目 key 是标签，存储 id 由评测按计数器分配。

| 类型 | 数量 | 标签 | 用途 |
| --- | ---: | --- | --- |
| 正例·词面重叠 | 20 | G = 1 条 live 决策 | 问题与条目共享排序 token（实测 gold 相关度 ≥ 2） |
| 正例·零词面重叠 | 20 | G 同上 | D-6 形态：在现有排序器下 gold 相关度 = 0，由测试用真实 `scoreEntry` 逐题校验 |
| 负例·伪造决策 | 8 | G = F = ∅ | 从未写入；其中 2 题与填充条目高度同词（诱饵） |
| 负例·已废止 | 4 | F = 被废止条目 | 2 条 `revoke`、2 条写入时带 `invalidAt`；其中 2 题 G = 取代它的 live 条目 |
| 负例·跨 scope | 3 | F = 他处条目 | 其他 project、同 project 的 working 层、baseline 层各 1 |
| 跨 scope 孪生 | 5 | 挂在对应正例的 F 上 | 其他 project 中与 gold 近乎同文、结论相反的条目 |
| 填充 | 按档位 | 无 | 24 主题 × 12 设置 × 8 取值中按种子无放回抽样（上限 2304） |

档位按目标 scope 内 live 条目数计：**30**（低于阈值，实测 55/55 题为 full 模式）、**500**、**2000**。种子 `20260926`；`asOf = 2026-09-01T00:00:00Z`；入库时间在 1–365 天前按种子均匀抽样。

局限：语料是合成的，以中文为主，每题只有 1 条 gold，问题不带标签。填充条目全部出自同一个「{主题}的{设置}定为 {值}」模板，范围内手写的决策体条目只有 21 条，少于融合的 25 个自由名额——这是 D-1 在这份语料上会空转的原因（§2.4）。数字只描述这份语料，不代表真实节点记忆。

### 2.4 语料加固与第二语料（v1.0 新增，P16.2b）

评审实测：一个**不读问题、不读标签**的「离群度」排序器（各条目与全体条目字符分布质心的余弦，取负），照 §5.1 融合后在 2000 档把零词面题从 0/20 拉到 17/20、正例合计从 13/40 拉到 37/40，v0.1 的两条检索判据都过（脚本在评审方本地，未入库）。任何能把「模板」和「非模板」分开的信号都能把 gold 带进块里，所以**在语料加固之前，任何检索层的「优于」都没有意义**。

P16.2b 做以下几件，全部在 P16.6 调参开始前冻结：

1. 每条 gold 配 ≥ 5 条同主题、同文体、结论或对象不同的「兄弟决策」，使决策体条目总数（≥ 141）远大于自由名额（25）。
2. 留出一套改写题集，由非实现者撰写、在调参前冻结。
3. batch 形状的查询变体：常驻链路的查询是 `formatTeammateMessages` 渲染后的整批对端消息（`src/services/qianmo/resident.ts:990-993`），带 `<teammate-message …>` 包装，可能多条。embedding 输入的截断规则同时定下。
4. working 层 `(agent, contextId)` 跨 context 孪生负例（现有三类跨 scope 负例都不是常驻链路实际用的那个分区）。
5. 多种子：5 个固定种子。
6. 伪造决策题与「相关但不支持」诱饵题扩到每档 ≥ 30 题，满足 E2 的样本量。
7. **第二语料**：取自仓库 `docs/dev` 的决策记录（各设计件的 D-x 表与章程变更记录），非合成、不涉隐私；题目由非实现者撰写并在调参前冻结。

加固后在同一 harness 上重测 M0 基线，记录语料哈希（§3 末）。

## 5. 语义检索叠加方案

### 5.1 融合：保底配额 + RRF

- **全量模式不启用语义层**（I-2）。只有 `mode="ranked"` 时才融合。
- 设 I_det 为 M0 的注入集。先原样保留 I_det 的前 ⌈\|I_det\|/2⌉ 条（确定性保底），再按 RRF（k = 60）融合确定性名次与语义名次，从 C 的其余条目中依次填充，条数与字符预算规则沿用 `selectForInjection`。
- **平局规则**：确定性相关度为 0 的条目在融合时取并列名次（否则 RRF 会把「新」当成一票相关性）；RRF 平局再按确定性名次、最后按 id 打破，保证全序。
- 「叠加非替换」的可机检定义：**保底部分 ⊆ I_hybrid**，且 **I_hybrid ⊆ C**。
- 块内每条来自语义填充的条目标注 `via: semantic`；同一 `source.id` 在自由名额中的占比设上限，防止关键词堆砌或被污染的条目被语义层放大（V-8）。
- 块头在 ranked 模式下增加检索方式属性（如 `retrieval="hybrid"`），full 模式块头不变。
- 放弃纯 RRF：它不保证确定性前列留存。放弃分数加权：两套分数量纲不同。放弃语义过滤候选：违反 I-1。

### 5.2 embedding 来源：模型中立，远端默认关（D-3）

- 接口 `EmbeddingProvider { id, model, dimensions, embed(texts) }`，`@qianmo/recall` 内不出现供应商名（I-5）。
- 三种配置：`off`（默认）、本地（进程内或本机服务）、OpenAI 兼容 embeddings 端点。**配置放在阡陌自有配置里**，路径从 `occConfigPath('qianmo', …)` 派生；不扩展基座的 provider 档案（`src/services/providerProfiles/*` 是基座文件）。
- 不同 provider / model / 维度的向量不混用：索引键为 `(entryId, contentHash, providerId, model, dimensions)`，键不匹配即视为缺失。
- **远端 embedding 的外发面**（开启它等于把下面四样发出节点）：
  1. **全库回填**：语义排名要对整个 C 算向量，scope 内**所有** live 条目都会发出，不只是每轮注入的 50 条。
  2. **查询文本**：常驻链路的查询是整批对端消息原文（`resident.ts:990-993`），即内测用户的原话。
  3. **可反演的向量文件**：`<memoryRoot>/index/` 的敏感度与正文相同（§5.3）。
  4. **第三方**：端点与 LLM 网关不是同一家时，多一个外部接收方。
- **定案**：默认关；开启时**只准发往该节点已被信任承载 LLM 流量的同一网关**；**在内测舰队上开启要负责人另行批准**，并写进内测告知。开关由节点启动参数给出，只有运维能改，状态进 P14 的 `authz.posture`（`tenancy-m1.md` §3.8 第 5 点）。
- 本地模型路线另两条 DoD：模型权重的许可证审查（`bun run sbom` 只查 npm 包，不查权重）；在小内存节点上实测常驻进程 RSS 的增量，以及对 AC-2「进程不占用可分配内存」冻结形态的影响。

### 5.3 索引

- 放在 `<memoryRoot>/index/`，不在 `working/`、`project/`、`baseline/` 之下。store 只扫描这三层（`packages/memory/src/store.ts:158` `searchRoots`、`:440` `#locate`），条目文件格式不变。
- 索引只存 id → 向量，条目内容永远从 store 读。索引中的 id 解析不到或不在本轮 C 中即丢弃，所以被污染的索引**不能注入条目**；但它能改变排序、挤掉特定条目，真正的防线是保底配额。对抗用例：索引被改写成把某条 gold 压到最后，该 gold 若原本在保底区内，仍然被注入。
- 索引文件 0600、目录 0700；条目 revoke 或节点退役时清除对应向量（P16.8）；纳入配置根归档。
- **冷索引闸**：索引对 C 的覆盖率低于 95% 时不启用融合，发 `index-cold` 事件；回填由 P16.8 的显式命令完成，有自己的预算。

### 5.4 失败回退与接线：两段式组装

- embedding 报错或超时（提议 300 ms，可配置）时，本次召回退回确定性结果，结果上标 `retrieval: 'deterministic' | 'hybrid' | 'hybrid-degraded'` 并记一条事件（I-6、I-7）。**每一轮的 `retrieval` 字段都进准入账本**：超时让「是否走混合检索」取决于机器负载，「为什么注入了这些」要能从账本还原。
- `recall()` 保持同步、行为不变；另增异步的 `recallHybrid()`。
- **接线定为两段式组装**：`renderMemory` 是同步的（`src/services/qianmo/residentPrompt.ts:53`），但查询文本 `base` 是在 `assembleResidentPrompt`（`:58`）内部生成的，调用链上游 `packages/resident/src/reader.ts` 已在 async 函数里。所以拆成三步：先渲染 base，再 await embedding（带超时），最后完成组装。涉及的 `reader.ts` / `runtime.ts` / `resident.ts` / `residentPrompt.ts` 都是自有文件，不碰基座。

### 5.5 成本上限（按 token 计，持久化）

- 计量单位是 **token（或字符）**，不是调用次数：一次批量调用可以包含上千段文本。
- 每节点每日上限为配置项，默认 0（即关闭）；计数器**持久化**，崩溃重启循环不会清零。
- 超限后退回确定性检索，发 `hybrid-degraded` 事件。
- 回填有单独的预算：单节点单次全量不超过配置的字符数。
- 按节点计（M1 没有租户，`tenancy-m1.md` §3.8 第 4 点）。
- 回答层评测 harness 的硬上限见 §4。

### 5.6 与工具层强制引用的关系（D-4）

强制点：`handleMemoryAnswer` 以本轮注入 id 集为白名单逐 id `getEntry`（`citation.ts:230`）。语义层只改变哪些 live、in-scope 条目进入 I，不引入新的可引用来源；副作用是注入集里「词面不同、语义相近」的条目变多，误归因的机会随之上升，所以 HR_mis 用非劣效硬闸（D-1 E2）。

常驻链路的强制点形态（P16.5）：

- **MCP 路线作废**：`createSessionMethod` 只把 `params.mcpServers` 用于会话指纹，给查询引擎的 `mcpClients` 恒为 `[]`（`src/services/qianmo/notifyTool.ts:28-39`、`src/services/acp/agent/createSessionMethod.ts:167-172`）；修通了工具名也会变成 `mcp__…`，与 `qianmo_` 前缀规则冲突。
- **照 `qianmo_notify` 的先例**：在 `residentToolSurface`（`notifyTool.ts:224`，自有文件）里加 `qianmo_memory_answer`，经 `conn.extMethod` 桥回宿主，由宿主持有的 store 校验。需要改 `createSessionMethod.ts` 的 `isQianmoResident` 分支（`:179-192`），它是**已登记的改造点**（`docs/dev/base-modifications.md` 的 `createSessionMethod.ts` 行）；建议一次性把桥改成通用的 `ext(method, params)`，改完同步更新该登记。新工具照 notify 的写法在自己的 `checkPermissions` 里返回 allow，外面由 `withResidentHardline` 包裹；不能靠 settings 放行（常驻会话的权限上下文是空的，`authorization-m1.md` F-6）。
- **每轮冻结 id 集落账**：强制点的白名单必须是「这一轮」注入的 id 集。sidecar 只返回字符串（`packages/resident/src/memory-sidecar.ts:188-202`），准入账本也只存 prompt。账本记录加 `memoryIds` 字段，**冻结 id 集直接落账，不能靠解析 prompt 来恢复**（P16.0 的注意事项）：P16.0 中和了行首框架标记，但解析渲染文本重建白名单等于把白名单的真实性押在渲染规则上。旧记录没有这个字段时按空集处理（任何引用都判 not-injected，失败时关闭）。
- **同形字符与零宽字符**（P16.0 的注意事项）：P16.0 只转义 `<` `>` 与行首框架标记；用同形字符或零宽字符在正文里伪造一行看起来像 `entry_id:` 的文字，仍然可能骗模型去引用它。这**只算「说服」问题**（章程 T-7：不以模型是否被说服验收），P16.0 不去追它；**真正的防线是 P16.5 的 `verifyCitations` 接线**：模型引用了什么，都要落在本轮冻结 id 集里才被接受。
- **出站回复校验**：工具是可选调用，模型直接用散文回复就绕过了强制点。回复经投递台账发给对端之前，扫描形如 `qm-mem-[0-9a-f]{16}` 的串：不在本轮 accepted 集里的，替换为固定占位文本并记一条事件。
- **禁令改成行为断言**：保留对 `buildRecallSystemPrompt` 的禁令；允许 `citationInstructions` 出现在 `residentPrompt.ts`；新增断言「两轮记忆不同时 system prompt 字节相同」「引用规则只出现在用户消息里」；把 `residentPrompt.ts` 纳入扫描（今天 `packages/resident/test/memory-sidecar.test.ts:420-433` 的 `residentSources()` 没扫它）。
- **E4 工具面断言**：`notifyTool.test.ts` 断言工具面「恰好一项」，显式改成两项，注释写明新工具不能创建无人值守轮次。新工具进 P14.2 快照与 hardline 用例，P16.5 的 PR 重跑 P14 的旁路语料。

## 6. 治理

### 6.1 冲突消解（D-6）

- 定义：同一 scope 内两条 live 条目对同一决策给出不同结论。
- 新增 `qm_supersedes` 字段（`qm_*` 命名空间，memory README 不变式 5）。写入新条目时声明取代的 id，store 对旧条目执行 `invalidate(at = 新条目 validAt)`。走事件轴而不是 `revoke`：旧决策在它有效的时段里是真的。
- **四个附加条件**：
  1. **只能取代同 scope 的条目**，禁止跨 scope 或跨层。
  2. **写入方信任级限制**：对端触发的轮次写入的条目，不能取代 `source.kind` 信任级更高的条目（T-7 ④ 要求把记忆写入当作不可信输入；否则一条伪造的「取代」就能下架一条真决策，ASI06 的直接形态）。
  3. **崩溃后可修复**：写新条目与 invalidate 旧条目是两个文件，启动时扫描「`qm_supersedes` 指向但旧条目还没 invalidate」并幂等修复。
  4. **撤销路径**：`store.invalidate` 对已 invalidate 的条目会抛错（`store.ts:402-411`），误取代后无法恢复。定义「撤销取代」操作并写审计。
- 自动检测只出报告：同标签、语义相近、结论不同的条目对进入待审清单，不自动 invalidate 或 revoke。

### 6.2 过期与废止：与现有双操作的对应

| 场景 | 操作 | 轴 | 现状 |
| --- | --- | --- | --- |
| 已知到期的事实 | 写入时带 `invalidAt` | 事件轴 | 已有：`entry.ts:142`（写入输入字段）、`:291` |
| 事实自某时刻起不成立 | `invalidate(id, at)` | 事件轴 | 已有：`store.ts:402` |
| 记录本身错误或不该存 | `revoke(id, {reason, by})` | 摄取轴 | 已有：`store.ts:369` |
| 被新决策取代 | `qm_supersedes` → `invalidate` | 事件轴 | 新增（P16.9） |
| 长期未复核 | 只出复核报表，不做任何写操作 | — | 新增（P16.10） |

不新增第三种退役类型；任何自动策略都不调用 `revoke`。

### 6.3 跨项目 / 跨 scope 隔离

现状：分区是目录级的（`store.ts:158`），召回按 scope 传参；常驻链路只取 working 层，`(agent, contextId)` 经带 `v-` / `d-` 标签的单射映射成目录段（`memory-sidecar.ts:84-114`）。§3 基线的禁入泄漏为 0。

缺口：

1. `getEntry` 经 `#locate` 扫描全部三层（`store.ts:440-454`）。引用其他 scope 的真实 id 得到 `not-injected`，伪造 id 得到 `unknown`，已废止得到 `retired`，回给模型的 rejection 文本各不相同（`citation.ts:215-222`），对模型构成跨 scope 的存在性探针。id 是 `qm-mem-` 加 `randomUUID()` 去掉连字符后的前 16 个十六进制字符（`store.ts:89-91`），其中第 13 位是 UUIDv4 的版本位、恒为 `4`，**实为 60 位随机数**（v0.1 写的「64 位」有误；评审实测 2000 次全是 `4`）。猜中仍不现实。P16.11 把三者回给模型的文本收敛成与 `unknown` 相同，内部报告仍保留六分。
2. project / baseline 层在常驻链路上不可达；沉淀目标 `projectKey` 如何由 `(agent, context)` 决定尚无规定（P16.11）。
3. **`contextId` 由发送方自报、不与发送方绑定**（`packages/resident/src/session-key.ts:85-88`）。`(agent, contextId)` 分区只防意外碰撞、不防伪造：知道别人 contextId 的一方能读到别人 working 分区被注入的内容。这是 P15 的问题，P16 只能写明风险；M1 拓扑里全部入站来自中枢、控制台会话 id 是随机 UUID 且只对属主与 ops 可见（`tenancy-m1.md` §3.8）。

## 10. 存疑与未验证

- **回答层全部未测量**；§4 的调用量与 token 量级是离线估算（评审用真实 `buildRecallSystemPrompt` 与工具 schema 逐题计字符；CJK 按 0.7–1 token/字、其余按 2.5–4 字符/token，输出按每次 300–2 000 token 假设）。
- **单价、余额、网关是否提供 `/v1/embeddings`**：都未核实，没连网关。
- **Linux 复现**：基线只在 macOS / Bun 1.3.13 上跑过（本稿两次、评审两次）。
- **真实 embedding 的表现**：只用非语义排序器模拟了空转；加固语料能否消除空转、真实模型在留出集上能否通过 R3 / R4，都没有验证。真实 embedding 不能保证逐字节可复现：评测时查询向量与条目向量随报告落档并记哈希，「从落档向量重算」必须逐字节相同，「重新 embed」只报告名次稳定性（Jaccard 与 Kendall τ）；余弦值按固定小数位取整后再排名。
- **检出力模拟假设两臂独立**；真实配对是正相关，检出力会更高一些，数字是保守下界，结论方向不变。
- **「生产写入方为零」只基于仓库代码**：没有登录舰队机器检查记忆目录里是否有人手工写入的条目。
- **P16.5 的 `extMethod` 桥**：延迟和错误语义照 notify 先例推断，没有实测。
- **估算**（§7）是评审判断加本稿增量，不是实测，没有经过排期评审。
- 300 ms 超时、⌈\|I_det\|/2⌉ 保底、RRF k = 60、95% 覆盖率闸都是提议值，未测量。
- 字符预算按 `renderEntry` 长度计，未换算成 token。
