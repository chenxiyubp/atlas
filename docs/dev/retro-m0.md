## 本文性质

1. **本文是复盘记录 + M1 排期输入，不是范围依据，也不是排期承诺。**范围依据仍是 [`charter.md`](./charter.md) §3，排期与任务包仍是 [`roadmap.md`](./roadmap.md)，完成状态的唯一出处仍是 roadmap 的「完成状态速查」表。凡本文与这三处冲突，以它们为准。
2. **charter 版本升级不在本文范围内。**roadmap P9.2 的交付物里有「charter 版本升级」一项，那是负责人的动作（章程 §7.3）；本文只产出可评审的材料。
3. **本文不复制任何已有结论。**§2 / §3 的每一条都指向 roadmap 变更记录、章程条款或某个文档的某一节；要细节请去那里。
4. **§4 的「排期偏差」用的是提交日期，不是工时。**提交日期能证明「这件事在哪天落地」，**不能**证明「花了几个小时」——本项目从未记过工时。凡是把日历换算成人力的地方，本文一律给区间并写清换算假设（§5.3）。
5. **本文引用的两份文档在本文成稿当天仍在推进**：[`baseline-m0.md`](./baseline-m0.md) v0.2-draft（提交 `005d6888`，启用 ARM 降级方案、数据表分**栏 A x86_64 / 栏 B aarch64** 两栏，栏 B 吞吐四轮已 pass、24 h 长跑**运行中**，**栏 A 全部仍【待真机】**）、[`acceptance-m0.md`](./acceptance-m0.md) v0.2-draft（提交 `ba95527d`，含 2026-08-15 本机腿走查记录与 `demo/walkthrough.sh`）。两文定稿后若数字变动，以它们为准。

## 2. 做对了什么

每条一个证据指针。**只列在 M0 里被证明有效的**——被证明有效的意思是：它至少改变过一次结论，或者拦下过一次错误。

### 2.1 「测量而非宣称」抓到了四次假绿 —— 本项目最值钱的一条纪律

这四次的共同形状是：**判据本身写对了，但喂给判据的观测是假的**，所以报告是绿的而系统是坏的。四次都是在落地审计里抓到、当场改成真观测后重跑：

| # | 假绿的形态 | 抓到之后 | 指针 |
| --- | --- | --- | --- |
| 1 | P6.1 的报告里 `uncaught` / `skipped` 是**硬编码字面量**，判据因此恒为真 | 改成真处理器计数与计划/派发差集推导，在 `87c4609b` 上 SHA 锚定重跑三轮 3/3 | roadmap v2.31 ① |
| 2 | 混沌注入的 `fill-disk` 往一个**空的** 1 MiB 卷追加 200 字节，每次都成功——**一次什么都没注入的注入** | 改为先真填满再写，写居然成功时主动记 `unmapped` | roadmap v2.29 ④ |
| 3 | P5.1 首轮总体 90% 看着很好，但 **OOM 只有 5/10**——Bun 撑爆内存被 SIGKILL 且零输出，文本规则无从下手 | 补的不是阈值是**一条事实**（「本进程的看门狗没发过这个信号」），重跑 50/50 | roadmap v2.24 ④ |
| 4 | AC-3 协议层预算在慢机器上判红，原因是 601 条突发跨过 100 ms 令牌回补步长——**量具的隐含假设，不是系统缺陷** | 判据改按突发用时算「顶」，同机复跑 4/4 绿（accepted=602, allowance=2） | 提交 `9736ddca` / `5b98e6e8` / `e74df9d8`；`demo-env.md` §7.5 |

同族的还有两条**判据设计**上的预防，值得一起记：P5.1 的「**被跳过的类别直接判不通过，而不是缩小分母**」（roadmap v2.24 ⑤）、P6.2 的「**探测器确实带电**」正向用例（roadmap v2.32）——都是防「弃权式假绿」的。

> **给 M1 的规则**：任何报告字段，**先问它是被测出来的还是被写上去的**。这四次里有三次，写报告的人和写判据的是同一个人。

### 2.2 「先验成本，再排期」——v2.9 立下的纪律，在 v2.15 上收回了本钱

- **立规**：P2.2 交付后逐行核实，发现「基座有 5,300 行可改造传输代码」这条降级依据**不成立**（直接 import 行数 = 0）。结论侥幸成立，理由是错的。据此定下纪律：**此后任何以「基座已有」为由下调的估算，开工第一件事先做可改造性评估**（roadmap v2.6 报警条 + v2.9 关键路径复核结论）。
- **兑现**：P3.1 开工前照此做了评估，**结论是原估算偏低**，并当场推翻两处前提（roadmap v2.15）。若没有这道前置，P3.1 会按一个建立在两个错误前提上的估算开工。

这一条的价值不在于省了多少时间，在于它把「侥幸对了」和「判断对了」分开了。

### 2.3 扩展点优先，被上游同步演练量化证实

- 基座 `src/` 总共只改了 **56 个文件**（修改 32 / 新增 24），逐文件的「为什么扩展点不够用」在 [`base-modifications.md`](./base-modifications.md) §2，三类归因在 §3。
- 演练实测：对上游 v2.46.0 三方应用，**5 文件 / 7 块冲突 = 1784 个上游 hunk 的 0.39%**；其中 **`@qianmo/*` 17 包零冲突**、**P0.3 身份隔离 9 个改动文件零冲突**（被演练评为模范样板），**冲突大头是文档**（`CLAUDE.md` / `README.md` 占 4/7 块）。指针：[`upstream-sync-drill.md`](./upstream-sync-drill.md) §3.1 / §3.2 / §5，章程 §5.7。
- 反例也被量到：唯一一处**代码语义冲突**出在「就地替换」那一族（`FreezeAwareWatchdog` 替换掉基座三处裸 `setTimeout`），因此演练的行动项③点名要把它抽成注入点（`base-modifications.md` §2.2 与 §4 的对应表）。**「加法零成本、就地替换有成本」这句话现在有数字了。**

### 2.4 边界用例库 + 混沌，分工写清楚了

- 分工写在文件头，不靠默契：**混沌跑批找没想到的组合，确定性用例防已知失效回归**；一条跑一小时才碰一次的失效，不该由随机去守（roadmap v2.29 ①）。
- 数字：边界目录 **39 条**（AC-8 要 ≥12、每类 ≥2）；60 min 正式跑批 seed `2145259399`，177 次四类注入、7,389 条成功投递、四类 `stalled` 全 0、0 未捕获 / 0 unmapped、审计链完好（roadmap v2.29 ⑤）。
- **顺带修掉一个「本地绿 + CI 绿而第二个绿没有意义」的缺口**：`scripts/test-shards.sh` 的分片名单不含新目录，`demo/lib` 的报告核心用例自 P4.1 起**从未在 CI 里跑过**（roadmap v2.27 ③）。这类缺口的价值在于它**只能被主动找**，不会自己冒出来。

### 2.5 诚实边界随处如实记 —— 而且它真的被下游用上了

M0 的每个任务包都在变更记录里留了「边界如实记」。它不是姿态，是有消费者的：

- P2.5 真机 10/10 之后立刻写明「**这批数字不能当 P3.1 的休眠唤醒基准**——被唤醒的是 94 KB 测试桩」（roadmap v2.16 ②），于是 P3.1 老老实实又测了一遍常驻 occ。
- P4.4 写明「**沙箱挂载边界本机测不到**」（roadmap v2.23 ⑦），这句话直接变成 [`acceptance-m0.md`](./acceptance-m0.md) §4.1「最可能需要豁免的一条」的事实基础。
- P6.1 写明五条边界（脚本化授权、逻辑双节点、unix 演示不冒称 TLS 等，roadmap v2.30），P8.3 的答辩口径与 13 镜分镜直接照抄它，不用重新盘。
- P7.2 把「不可改」拆成三句**只认前两句**，并**专门写一条用例**钉住第三句做不到（roadmap v2.28 ③）。

> 反向的证据是：这些边界句子后来**没有一条被推翻**。写得住的边界才是省事的边界。

## 3. 估错了什么

格式统一：**当时估计 → 实测 → 差多少 → 为什么错**。按「错得最贵」排序。

### 3.1 事前能力盘点里没有 P2.5 这一项（最贵的一处）

- **当时估计**：`base-adoption.md` §3.1 / §3.2 的两张能力表逐项判定了 21 项能力，**没有任何一行对应「跨节点 activator + 常驻保活」**。
- **实测**：`selection-m0.md` §5 单列一节把它识别出来——「接住请求 → 唤醒目标节点 → ready 后转发」这一层现有任务包里没有它；内核 accept queue 的缓冲**只在同机有效**，Dormice daemon 也只听本机。原文定性：「**是阡陌唯一必须自己写的基础组件，且 AC-2 直接压在它上面**」。
- **差多少**：它成了 `packages/` 里最大的一块（`packages/activator` 约 8,834 行，实跑 `git diff 3380c88..HEAD --numstat` 按目录归并），并被 roadmap v2.2 直接推上关键路径长杆位置。
- **为什么错**：能力盘点的方法是「**逐条问基座有没有**」，而 activator 是一个**基座和阡陌都没有、但拓扑要求必须有**的东西。**「基座缺什么」这个问法找不到「拓扑缺什么」。**

> **给 M1 的规则**：能力盘点做完之后，再做一遍**拓扑走查**——沿着一条真实请求从发起到落地走一遍，每一跳问「这一跳的代码在谁那里」。

### 3.2 P2.2「基座有 5,300 行可改造传输代码」

- **当时估计**：roadmap v2.2 据 `selection-m0.md` §2 把 P2.2 从「从零造」降级为「实现一个 Transport + 自建服务端半边」，并因此把它从关键路径最长杆的位置挪下来。
- **实测**：逐行核实——基座 `Transport` 钉死在 SDK 控制协议 zod 联合上（信封不可能是它的成员）、**全仓没有任何 WebSocket 服务端**（仅有的两处 `Bun.serve` 在 `SSHAuthProxy.ts`，该文件 `websocket` 零命中）、且与会话面硬耦合。**直接 import 行数 = 0**。
- **差多少**：**工时没爆，但不是因为基座帮上了忙**——是因为阡陌只需要单条 wss + PSK。真正复用的是设计（退避公式、10 分钟预算、「休眠检测阈值 = 2× 上限」、「代理不数控制帧」）。
- **为什么错**：把「**有形状相似的代码**」当成了「**可复用**」。roadmap v2.6 报警条给的定性最准确：**降级的理由不成立，降级的结论侥幸成立。**

### 3.3 P3.1「休眠改核心」的成本，以及两处方向相反的前提错误

- **当时估计**：`base-adoption.md` §3.1「休眠与唤醒」判 **无**，原文「**全部自研**。可复用的只有 supervisor 骨架，挂载方式是往 worker 注册表加一种 kind」；章程 v2.7 后改判「部分」（唤醒四条通道已核实存在）。
- **实测**（roadmap v2.15 的可改造性评估，两处前提被代码推翻，**方向相反**）：
  - 「唤醒半边有四条现成通道」——在 **ACP 宿主下一条都不通**（正解是 ACP 自带的 `session/prompt`，仍是零核心改动）；
  - 「全仓没有通用 idle 事件」——**是错的**，有四个，`sessionActivity.ts` 正是要的形状；真正的理由是**基座没有任何进程内扩展点**。
  - 更早还有一处：「往 `DAEMON_WORKER_KINDS` 加一种 kind 即可挂载」——`runDaemonWorker()` **没有 dispatch 表**，只会让 worker 以退出码 78 退出并被永久 parking（`selection-m0.md` §2）。
- **最大的一笔是 roadmap 此前零覆盖的**：常驻宿主选 ACP，把 P2.1 / adapter 已验收的 **AC-2 最后一跳的读者拿走了**（`useInboxPoller` 是 REPL 专有），得给 ACP 补一个读者。
- **差多少**：净效应是**增量**（v2.15 原话）。落到代码上，P3.1 是基座改动最大的一族：**16 个修改 + 13 个新增**（`base-modifications.md` §1 归因族表）。
- **为什么错**：三态判定（已有/部分/自研）是「**基座给了什么**」，**不是工时折扣**——章程 v2.7 已经把这句话写进条文，但写进条文和排期时真的不打折是两件事。

### 3.4 Dormice API：按「合理形状」写的假设全错

- **当时估计**：P2.5 首版按 REST + 「`touch` 方法」+ 状态 `running` 实现。
- **实测**（roadmap v2.8，主 agent 真机核实）：API 是 `POST /{methodName}` + JSON body 的 **RPC 而非 REST**；**`touch` 方法根本不存在**（31 个真实方法里没有）；状态取值是 `active` 不是 `running`。保活改用实测会刷新 `lastActiveAt` 的 `acquireSandbox`。
- **差多少**：一次返工，外加**一处防护丢失如实记录**——真实 API 中保活与唤醒是同一操作，原类型窄化保证不再成立（`destroy` 不可达这条核心性质不受影响）。
- **为什么错**：**对第三方 API 的形状做了推断而不是核实**，且这个推断进了已交付代码。同一天定下的纪律（`selection-m0.md` §6「凡文档与代码冲突，以代码为准」）在这里应当扩写成「凡未核实的第三方接口，不得进已交付代码」。

### 3.5 「跨节点传输基座给的是零」—— 一次来回

- **当时估计**：`base-adoption.md` §3.2 判「**基座起点为零**」，理由是远程控制传输层已于 2026-07 整体删除（约 45k 行）。据此 roadmap v2.0 把 P2.2 推上关键路径长杆。
- **中途推翻**：`selection-m0.md` §2 以代码推翻——删的只是 `src/bridge/`，基座仍有数千行在用的传输代码，`RemoteIO extends StructuredIO` 意味着主循环已能跑在网络传输上。章程 v2.2 据此把 C-3 由「自研」改判「部分」。
- **再纠回**：见 §3.2——**可复用的直接 import 行数是 0**。
- **差多少**：结论上，`base-adoption.md` 的「零」在**可复用代码**这个意义上是对的；错的是它给的**理由**（「45k 行被删所以是零」）恰好也不准确。**两次判断都是对结论对、理由错。**
- **为什么错**：两次都用**行数**当可复用性的代理指标。行数既证明不了「有」，也证明不了「没有」。

### 3.6 AC-3 量具的隐含假设（判据对，量具错）

- **当时估计**：协议层入站预算的判据是「打满 `LIMITS.ratePerMinute = 600` 后第 601 条回 `E_RATE_LIMITED`」，实现上默认 601 条突发能在令牌回补步长内打完。
- **实测**：慢机器（Debian 13）上 601 条突发**跨过了 100 ms 回补步长**，于是 accepted 变成 602，判红。
- **差多少**：一次「系统没坏、报告说坏了」的假红，加上一次被撤回的错误修法（`c7a02607` 冻结接收方时钟 → `7e83649a` 撤回，改为按突发用时算「顶」）。
- **为什么错**：**判据把「600 条」当成了绝对上限，而令牌桶的语义是速率**。写判据时脑子里那台机器是开发机。

### 3.7 P8.1 runbook 漏了两样东西，都是在全新机器上才暴露的

- **当时估计**：干净 clone 实测 **87 s**（热 bun 缓存 + 本地 clone + 开发机），距 30 min 预算 20 倍余量。
- **实测**：第一台全新机器（Debian 13 x86_64、冷缓存、公网）**2 min 40 s**，runbook 补 bun / node / make 装法与最低内存（提交 `da98d86f`）；第二台全新机器（2 vCPU / 1973 MB / 无 sudo）净 **105 s**、含操作者往返墙钟 **8 min 19 s**，**唯一硬卡点是 bun 官方安装器要 `unzip`**，minimal 镜像不带、无 sudo 装不上（提交 `840b934d`，`demo-env.md` §2.1 / §4.1 busybox 垫片 / 故障表）。

### 3.8 举证命令 `848ad8c2..HEAD` 跑不通（写进答辩预案之后才发现）

- **当时估计**：章程 v1.x ~ v2.3 一直用 `git diff 848ad8c2..HEAD` 作为成果边界的举证命令，且它已经写进 P8.3 的答辩 Q&A。

- **还有一层**（roadmap v2.35 ⑥(b)）：**本机主检出里 `848ad8c2` 居然能解析**——它是 pack 中不被任何 ref 可达的悬空对象，干净 clone 里不存在。**结论不变，但本机预演会误以为旧命令能跑，还会给出另一组数字。答辩机必须用干净 clone。**对象来源已坐实：P7.4 演练用的 worktree 与主检出共享对象库，上游 fetch 的对象因此进了主 pack（`BASE.md` 勘误 `a626eb95`、`upstream-sync-drill.md` 勘误 `856d0ff8`）。
- **为什么错**：**举证命令从未被实跑过**。一条写进答辩预案的命令，和一条被跑过的命令，是两种东西。

### 5.3 结论（可以直接念的三句话）

> **第一，「省下/多花多少工时」这一问在本项目里无法给出数值答案**——事前估计是六个量级词，事后没有工时记录。任何数值都是造出来的。
>
> **第二，定性对账的结果是：省下的都在产品线 ①（会话持久化、多模型适配、编程闭环、上下文压缩）与工程门禁，量级与事前的「大 / 中」大体吻合；多花的集中在事前根本没有条目的地方**——跨节点 activator（能力盘点方法的漏项）、被两次修正的休眠改造、以及举证 / SBOM / 许可链这一整条「说清楚自己做了什么」的成本。
>
> **第三，路线变更引入了一笔事前没有量级概念的长期经常性成本：上游同步。**演练把它量成了 10–20 人时/次；按建议节奏**算术外推**，年化约 **130~520 人时 ≈ 16~65 人日**，即 M1 起每年三到十三个人周的固定开销（区间这么宽是因为节奏本身还没定稿）。**这笔账事前是空的，现在有数字了，M1 排期必须把它当成一条常设任务而不是一次性动作。**

### 5.4 给 M1 的方法论修正（这一节的真正产出）

1. **量级词不是估计。**M1 的能力盘点如果还写「大 / 中 / 小」，就必须同时写「按什么类比得出」——例如「与 P0.3 同量级（9 文件改动 + 一个派生层）」。可类比的锚点现在已经有 17 个包 + 56 个基座文件了。
2. **能力盘点之后加一遍拓扑走查**（§3.1）。
3. **「基座已有」永远不折扣工时，先做可改造性评估**（v2.9 纪律，M0 已验证有效，M1 继续）。
4. **凡未实跑的命令不得写进对外材料**（§3.8 的教训）。
5. **上游同步进常设任务**（§5.3 第三句）。
