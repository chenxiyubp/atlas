## §0 一页纸：十四条定案

读完这张表就知道这套装机面长什么样；每条的理由在对应小节。**每条都给「为什么不是另一种」。**

| # | 问题 | **定案** | 在哪 |
|---|---|---|---|
| 1 | 凭据存什么形态 | **只存私钥**（Ed25519）+ 主机公钥指纹 + 用户名 + 端口。**不存口令** | §3.1 |
| 2 | 凭据存哪、加不加密 | **H 上信封加密的 0600 文件**，主密钥另放一个 0600 文件、与密文库分处两目录，并被四条既有拷贝路径显式排除 | §3.3 |

| 4 | 私钥怎么交给 `ssh` | **`ssh-add -` 从 stdin 进一次性 agent**（socket `srw-------`），`ssh -o IdentityAgent=`；**明文私钥不落盘、不进 argv** | §3.5 |

| 7 | 「不留任意命令」由谁保证 | **两层：我们的执行器 + 目标机 sshd 的 `command=` 强制。**长期 key 上钉 `command="…dispatch.sh",restrict,port-forwarding,permitopen="127.0.0.1:38625"` | §5.1 |

| 9 | 「复制文件过去」复制什么 | **源码 tar（tracked 文件）+ 目标机自建**。分发 `dist/` 只在「同架构 + 同 libc + 同 major 内核」时作为**可选加速**，且必须重跑一次 ripgrep 落位 | §6 |
| 10 | 装的前置检查 | 规格清单（架构 / 内存 / 磁盘 / `unzip` / Bun pin）**是必要不充分条件**；**判据是一次真自检**（符号链接解析 + 一次真拨号），不是一张表 | §5.3 |
| 11 | PSK 谁生成 | **H 生成，同一次 SSH 会话里写进节点的 0600 文件**。装机流程把 `beta-env.md` §8.3 的时序**扳回来**：先有 PSK 才有节点，不是先起节点再补钥匙 | §5.3 |
| 12 | 隧道是干什么的 | **控制面 + 「没有直连时的数据面兜底」**。`qianmo://` 的跨节点直投是节点↔节点的数据面，**不常态经 H** | §7 |
| 13 | 第三枚 token | `provision`。与 view / admin **互不包含**——**admin 不是 provision 的超集**。`resolveTokens` 三条策略**一条不改**，第三枚走一个新纯函数，且**永不自动生成**（回环也不） | §8 |
| 14 | 装机的审计落在哪 | 目标节点此刻**还没有审计链**，所以 H 侧自己有一本**装机账本**（append-only NDJSON + 哈希链，形状照 `@qianmo/audit`），并按 `audit-witness.md` §4.1 每日锚一份到 H 之外 | §9 |

**一句话概括这套面的能力边界**：它能把一台**你已经能 SSH 进去的**机器变成一个内测节点，并在之后起停它、给它建隧道、把它的审计镜像拉回来。它**不是**一个远程执行器，**不是**一个云厂商弹性扩容对接（章程 N-7），**不是**账号体系（章程 N-2，见 §10.1）。

**它新增了一条必须被明确接受的风险**：H 从「持有全部 PSK 与归档 token 的机器」升级为「**能在每一台节点上执行代码的机器**」。这是本设计引入的单点，写在 §4.3，评审要对它单独表态。

## §1 为什么是 SSH，以及今天这件事有多贵

### 1.1 SSH 是现场唯一可靠可达的门（这是事实，不是偏好）

内测拓扑里四台常驻节点的入站 WebSocket 端口（38625）**在三台上被云厂商安全组挡死**；另探 8080 / 8443 / 3000 / 5000 / 8000 / 9000 / 10000 / 30000 / 38620 / 50000 **全不通**，只有 **22 / 80 / 443** 通。而 `beta-env.md` §2.6 那句「38625 在无 sudo 的 VPS 上必然对全网开放」描述的是**主机侧**的事实（没有 root 就没有包过滤），它挡不住**厂商侧**的安全组。

两者不矛盾，但合起来的后果很硬：

- 从 H 到节点的**控制通路**只能建立在 22 上；
- 「节点被 H 拨得通」这件事在三台机器上**不是靠 38625 直连成立的**，而是靠 SSH 正向隧道成立的（H 已实测 `-L` 可用）。

**所以本设计不是「顺手用一下 SSH」，是「除了 SSH 没有别的门」。**这一条同时决定了 §7 里隧道不是可选功能，而是数据面在当前现场的唯一落地形态。

### 1.2 今天装一台节点要人做什么

`demo/env/beta/README.md`「首次装机的完整顺序」是五步，其中第 ①②③ 步各自还展开成 `demo-env.md` §4.1 的一串命令：装 Bun（pin 1.3.13）、装 node、取代码、`bootstrap.sh`（`bun install` + `bun run build` + 自检）、在 H 上生成 PSK 再拷过去、起节点、把节点打印的入站端点**回填**进 H 的 `peers.conf`、再在 H 上起宿主腿。

**两处人肉环节是这套设计要吃掉的主菜**：

1. **PSK 的生成与投递**（§8.3 要求 H 生成后分发；现场这一轮的时序走反了——先起了节点再补钥匙，于是那把钥匙短暂地是节点自己生成的）；
2. **入站端点的回填**（一次人肉抄写，抄错的表现是「节点起来了、名册上在线、H 拨不通」——正是 `beta-env.md` §9.1 那条最会骗人的限制）。

装机面的价值判据因此可以写死：**它必须让这两件事都不再经过人的手，否则它只是把 runbook 换了个皮。**

## §2 十二项实测事实（本文所有定案的地基）

照 `key-distribution.md` §2 的做法逐条实测，不推断。复现命令见附 A。**§0 第 5 条教训在这里再说一次**：本文最重要的两个结论（「规格清单不能当前置检查」「不留任意命令可以由 sshd 强制」）**只能靠实测得到**，靠读文档会得到相反的答案。

| **P-5** | 那 `SSH_ASKPASS` 呢？ | **可用。**`SSH_ASKPASS=<助手> SSH_ASKPASS_REQUIRE=force ssh …` 时助手**确实被调用**并拿到 prompt（实测助手向 stderr 打出了 `ASKPASS-CALLED prompt=[<user>@<host>'s password: ]`） | 口令**不是完全不可能**，代价是再写一个持有明文口令的助手程序。§3.1 仍然否决它，理由是「多一个持密进程」换来的只是一种更弱的凭据 |
| **P-6** | `sshpass -p <口令>` 会不会泄进进程列表？ | **会泄长度，值被抹掉。**实测 `ps -eo args` 看到的是 `sshpass -p zzzzzzzzzzz`（11 个 `z` 对应 11 字符的口令）——sshpass 读完自己改写 argv | 抹得再干净也有抹之前的窗口，且这是**第三方二进制**。与 P-4/P-5 一起把口令这条路彻底关掉 |

| **P-8** | `StrictHostKeyChecking` 各档在首见主机上到底怎么表现？ | `accept-new` + `BatchMode=yes`：**静默接受**，只在 stderr 留一行 `Warning: Permanently added …`，命令照常执行；`yes` + 空 `known_hosts`：`No ED25519 host key is known … Host key verification failed.`，**拒绝连接** | `accept-new` **就是 TOFU**，而且是没有人看的那一种（`console.md` §4.2 与 `key-distribution.md` §5.3 都用同一条论证否决过这种形态）。§3.6 因此取「指纹必填 + `StrictHostKeyChecking=yes`」 |
| **P-9** | 私钥能不能不落盘？ | **能。**`cat <私钥> \| ssh-add -` 直接从 stdin 装进 agent（实测 `Identity added: (stdin)`），agent socket 是 `srw-------`，随后 `ssh -o IdentityAgent=<sock>`（**不给 `-i`、不给 `IdentityFile`**）认证通过 | **这一条把「凭据永不落明文盘」从口号变成可实现的。**代价是每次动作多一个子进程，以及 UNIX socket 路径长度上限（实测：放在深目录里直接 `path … too long for Unix domain socket`），socket 只能落在短路径的 0700 目录里 |
| **P-10** | `authorized_keys` 的 `command=` 能不能把「任意命令」这件事**从我们的代码里拿走**？ | **能。**给一把 key 钉 `command="…/dispatch.sh",restrict,…` 之后，客户端发 `rm -rf /tmp/whatever; echo ARBITRARY-RAN` 得到的是 `DISPATCH-RAN original=[rm -rf /tmp/whatever; echo ARBITRARY-RAN]`——**原命令一个字都没执行**，只是作为 `$SSH_ORIGINAL_COMMAND` 传给了那个脚本 | **动作集闭合可以由目标机的 sshd 强制**，而不只由我们的执行器强制。这是负责人第②条要求能拿到的最强形态（§5.1） |
| **P-11** | 加了 `restrict` 之后隧道动作还活不活？ | **活。**`restrict,port-forwarding,permitopen="127.0.0.1:38625"` 下 `ssh -N -L …:127.0.0.1:38625` 会话正常存活 | 五类动作可以共用**同一把**受限 key，不必为隧道单开一把宽 key |
| **P-12** | `permitopen` 是在哪一刻拦的？ | **在 channel 打开的那一刻，不是建立转发的那一刻。**转发到未授权端口时会话照常活着、本地监听照常在，一旦真有连接穿过去，客户端立刻收到 `channel 2: open failed: administratively prohibited: open failed` | 写实现时不要用「`-L` 建得起来」当判据（`ExitOnForwardFailure` 在这里不会触发）；判据必须是**真穿一次**。这也是 §5.6 的隧道就绪判据不能写成「进程还在」的原因 |

> **P-2 + P-3 合起来判死了最省事的那个方案**（「H 上构建一次，把 `dist` 发给四台节点」）：跨架构时它不是「跑不起来」而是「**跑起来了但工具悄悄少了一件**」——最难在验收里发现的一类。
>
> **P-4 + P-5 + P-6 合起来判死了第二个最自然的方案**（「凭据存口令，反正用户就是那么登录的」）：口令在非交互 SSH 上要么根本不可用，要么要一个额外的持密进程或第三方二进制。**私钥不是「更麻烦的口令」，它是这条路上唯一能直接用的东西。**
>
> **P-7 判死了第三个**（「前置检查写一张规格清单就行」）。这一条最值钱，因为它推翻的是一个**看起来已经被现有文档背书过**的做法：`demo-env.md` §2.1 那张依赖表是**真的**，只是**不完备**——它列的每一项 spare-A 都满足。
>
> **一处如实记的未决**（不写进任何定案，留给落地首日）：`command=` 与 `-N`（不请求命令）同时出现时，强制命令**不会**被执行（`-N` 本来就不请求命令），所以隧道动作在受限 key 上走的是「不触发 dispatch」的那条路。本文的对策不依赖这个细节（§5.6 用 `permitopen` 收窄，而 P-12 已实测它有效），但**实现时要留档确认**，理由与 `key-distribution.md` §2 那条 ws 路径未决同源：一条建立在未测清楚行为上的防线不是防线。

## §3 定案一：凭据存什么、存哪、怎么用

### 3.1 存什么：**只存私钥**，不存口令

| 字段 | 存不存 | 理由 |
|---|---|---|
| **SSH 私钥**（Ed25519） | **存** | P-4/P-5/P-6：它是非交互路径上唯一能直接用的凭据形态 |
| **主机公钥指纹**（`SHA256:…`） | **存，且是登记时的必填项** | §3.6。少了它，第一次连接就只能 TOFU |
| 用户名 / 端口 | 存 | 现场四台里端口并不都是 22（有一台在非标准端口上），所以端口是字段不是常量 |
| **登录口令** | **不存** | P-4：存了也用不了。P-5 的 askpass 路要多一个持有明文口令的助手进程，P-6 的 sshpass 要多一个第三方二进制且泄长度。**用一个更弱的凭据去换更多的持密面**，两头都亏 |
| sudo 口令 | **不存** | 装机全程不需要 root（`beta-env.md` §2.1：四台里三台本来就无 sudo，全部装在家目录）。**「不需要」和「存着以防万一」在失陷分析里不是同一件事** |

**为什么不是「两者都存，用户给什么用什么」**：那会让「这台机器怎么登录的」变成一个运行时分支，而**每多一个凭据形态就多一条要被审查的持密路径**。现场的四台机器 SSH 公钥本来就已经装好了（H 上那把已实测可用），把口令这条路加回来买不到任何现在没有的能力。

**如实写一条现场债**：H 上现在是**一把 key 服务全部四台节点**。本设计要求**每节点一把**（§4.3 缓解②），理由与 `beta-env.md` §8.2「PSK 每节点一把」逐字同源，也正是 `audit-witness.md` §4.1 那条 ⚠️ 在说的事。**换成每节点一把这件事本身，就是 `install` 动作的第一个用户**（§5.2 的两阶段 key 顺带把它做掉）。

### 3.2 三个存储方案

| 方案 | 挡得住什么 | 挡不住什么 | 经常性成本 |
|---|---|---|---|
| **(a) H 上 0600 明文文件**（照 `secrets/peers/<node>.psk` 的既有形态） | 同机其他账号 | 任何一条**误拷贝**路径：审计镜像拉取、配置根 tar 快照、备份 store、把日志打包发给别人 | 0 |
| **(b) H 上信封加密** ← **选它** | 上面全部 + 误拷贝路径（拷走的是密文） | **H 上有读权限的人**（主密钥就在同一台机器上） | 近 0 |
| (c) 复用 H 上的 OpenBao | 上面全部 + 磁盘上真的只有密文（seal 状态下） | 见 §3.4 | 一条跨项目依赖 |

### 3.3 定案：(b) 信封加密，**并且明写它不是一道独立防线**

**形态**：每份凭据用一把随机数据密钥加密，数据密钥用一把主密钥包起来；主密钥是 H 上一个 0600 文件，**与密文库分处两个目录**。加解密用 `node:crypto` 的 AES-256-GCM，零新增依赖（与 `key-distribution.md` §6.1「校验零依赖可做」同一条纪律）。

**它买到的是什么，如实写**：这个环境里**误拷贝路径特别多**——`beta-env.md` §4.3 的审计镜像拉取、§5 的备份 store、§6 L2 的配置根 tar 快照、`beta-reset.sh --archive-config` 的改名归档。这四条路径每一条都是「把一堆文件原样搬到另一个地方」，而其中任何一条不小心覆盖到凭据目录，明文方案就是一次泄漏。信封加密把这四条的后果从「泄漏」降到「多了一堆没用的密文」。

**其中第一条已经不是 rsync 了，这对本节是收紧不是放松，所以要在这里点一句**：审计镜像的落地
实现是**单向只读拉取**——**只可能搬走那一个审计链文件**，凭据目录不在它够得到的范围里。硬结论
是 **「镜像只能是拉取式」**，理由是 §5.1 那把受限 key 的强制命令会忽略客户端发来的命令，于是
`rsync` 协商不到远端 `--sender`（完整表述在 `beta-env.md` §4.3 与
`demo/env/beta/ops/mirror-pull.sh` 的文件头，本文不复制）。

**另外三条路径一条都没变**：备份 store、配置根 tar 快照、`--archive-config` 的改名归档仍然是
**整目录搬运**，所以下面那条硬规矩的 ②③④ **一个字不改**；① 变成什么形态见那一节末尾。

**它买不到什么，同样如实写**：**主密钥与密文在同一台机器上，所以对「H 被拿下」这条它一点用都没有。**把主密钥放在别处（另一台机器、运维每次输入）都有真实的运维代价，而那个代价买回来的边界，§4.3 已经用「SSH 信任严格单向」这条结构性约束更便宜地守住了一部分。**这里不做「加密了所以安全」的宣称**——它是一条针对误拷贝的防线，不是针对入侵的。

**为什么不是 (a)**：不是因为明文「看起来不专业」，而是因为上面那四条拷贝路径**是这个环境已经存在的、写进设计文档的、会定期自动跑的**动作。一个会被定时任务定期搬运的秘密，和一个只躺在那里的秘密，不是同一个风险等级。

**配套硬规矩（缺一条则 (b) 白做）**：凭据库与主密钥两个目录必须被**显式**排除在——① 审计镜像拉取的源之外；② 配置根快照 tar 的路径之外；③ 备份 store 的输入之外；④ `beta-reset.sh` 全部 purge 类参数的作用域之外（`--purge-logs` / `--purge-state` / `--purge-links`，外加 `--archive-config` 的改名归档）。**四条都要写成配置里的显式排除，而不是「它们本来就不在那些目录里」**——理由与 `beta-env.md` §2.5 那条反代 allowlist 同源：没配和配了拒绝，在下一个人接手时不是同一件事。

**① 是这四条里唯一一条已经被结构性满足的**：镜像拉取的「源」现在是一个由 `authorized_keys` 的强制命令钉死的**单文件路径**，凭据目录不在它够得到的范围里（见上）。允许它以「结构上不可能」代替「显式排除」，理由是强制的那一方不是我们自己的代码，而是节点上的 sshd。**但它没有因此消失，只是换了形态**：那一行选项住在一个我们不拥有的文件里，被改写之后 key 照样能认证、只是不再受限（`beta-env.md` §8.3），所以 ① 转成一条**巡检项**——定期确认那一行还在、还是那个形状。

### 3.4 关于复用 H 上那个 OpenBao：评估与结论

**现场事实**：H 上确实跑着一个 `openbao/openbao:2.4.0` 容器（属于同机另一个项目的 compose 栈），健康，**只把 `8200/tcp` 暴露在 compose 网络里，没有映射到宿主端口**（同栈里另有几个服务是映射到 `127.0.0.1` 的，它不是）。

**复用它能买到什么**（不要低估，这几条是真的）：

1. **真正的审计日志**——谁在什么时候取了哪个 secret，这是 (b) 方案完全没有的东西；
2. **KV v2 的版本化与软删除**——换一把 key 之后旧值还在、可回滚，而 (b) 方案里「轮换时旧值立即删」（`beta-env.md` §5）是靠纪律保证的；
3. **seal / unseal**——封印状态下磁盘上真的只有密文，主密钥不在盘上。这正是 §3.3 明说自己买不到的那一条；
4. **它已经在跑，且已经有人在运维它。**

**代价，逐条**：

1. **耦合到另一个项目的部署节奏。**那个栈的一次容器重建、一次升级、一次 unseal key 轮换，都会让阡陌的装机面不可用；而 unseal key 不在阡陌手上。**「阡陌坏了要去问另一个项目」是一条会在最不方便的时候生效的依赖。**
2. **接线要往别人的部署里伸手。**端口没映射，接它要么改那个项目的 compose（改别人的部署），要么把 provision 进程塞进它的 docker network（把阡陌进程放进别人的网络命名空间）。两条都不是「复用」，是「合并」。
3. **供应链与依赖边界。**`packages/console` 是**零第三方依赖**包（硬约束）；OpenBao 客户端即使落在 host 侧，也是一条新的运行时供应链 + 一条新的 SBOM 条目（章程 §5 / `sbom-m0`）。而本设计其余部分（AES-GCM、Ed25519、`spawn ssh`）**新增依赖为零**。
4. **成果边界。**把阡陌的凭据库放进另一个项目的组件里，软著与竞赛成果举证时要额外解释这条依赖（章程 §5.5、风险 L-1）。
5. **规模不匹配。**4 台节点 × 每台 1 份凭据 = 4 条记录。这是章程 N-6「注册中心允许单点」的同一条克制理由的另一次应用：**不值那个复杂度。**

**结论：不复用。**用 §3.3 的 (b)。

**升级触发条件（写死，免得将来靠感觉判断）**——三条任一成立即重新评估 (c)：

- 节点数 **> 20**（与 `key-distribution.md` §6.2「> 20 就上两级 CA 结构」同一个门槛，理由也同一条：人工动作的频率越过了「不要求人做周度杂务」那条线）；
- 凭据种类超过「私钥 + 指纹」两类（例如引入了要定期轮换的第三方 API 凭据）；**2026-10-03 补注**：这一条已因中枢持有模型密钥而成立，按本节的写法重评过，结论仍然是不复用 (c)，理由与替代做法见 [`providers-console-m1.md`](./providers-console-m1.md) §1.3 O-5；
- 出现「需要给**第三方**临时授权装机」的需求——那时需要的是租约与吊销，而那正是 (b) 完全没有、(c) 天生就有的东西。

### 3.5 私钥怎么交给 `ssh`：一次性 agent，**明文私钥不落盘**

**定案**：每次动作起一个**只服务这一次动作**的 `ssh-agent`，把解密出来的私钥经 **stdin** 用 `ssh-add -` 装进去（P-9 实测），然后 `ssh -o IdentityAgent=<sock> -o IdentitiesOnly=…` 拨号；动作结束（含异常与信号）杀掉 agent、删掉 socket 目录。

**为什么不是「解密到一个 0600 临时文件再 `-i`」**：`ssh` 的 `-i` 只收路径，没有「从 fd 读私钥」的入口——所以临时文件方案里，明文私钥**一定**会在磁盘上存在一段时间，而那段时间正好覆盖了一次可能失败、可能被 kill、可能崩溃的远程操作。agent 方案里明文私钥只进内存。

**两条必须写进实现的细节**：

- **socket 路径要短。**UNIX domain socket 路径有长度上限（实测：放在深目录里直接 `path … too long for Unix domain socket`）。socket 落一个短路径的 **0700** 临时目录，不要落在 `QIANMO_BETA_ROOT` 底下那几层深目录里。
- **清理要挂在信号上，不只挂在 happy path 上。**长驻控制台上漏掉的 agent 是一张只增不减的持密进程表——与 `console.md` §6.6 那条「漏掉的订阅是一张只增不减的监听器表」是同一类账。

### 3.6 首次连接的主机身份：**指纹必填，不 TOFU**

**定案**：登记一份凭据时，**主机公钥指纹是必填字段**。H 侧用它自己写一份 `known_hosts`（只给装机面用，**不是** `~/.ssh/known_hosts`），全部 SSH 调用带 `-o StrictHostKeyChecking=yes -o UserKnownHostsFile=<那一份>`。

**为什么不是 `accept-new`**：P-8 实测它在 `BatchMode` 下**静默接受**首见主机，只留一行没人在看的 stderr 警告。这正是本仓库已经两次书面否决过的形态：

- `nodeIdentity.ts` 的 `parseTrustedKey` 注释：「从第一个宣称它的 peer 学密钥，等于让先开口的人变成那个节点」；
- `key-distribution.md` §5.3：**TOFU 一律不做，包括「首次连接时提示指纹让人确认」这种弱化形态**，理由是「一个只在有人认真看提示时才生效的防线，不是防线」。

`accept-new` 连提示都没有，比那条被否决的弱化形态还弱一档。

**这会不会新增一件带外分发的东西？**——会，而且要说清楚：`key-distribution.md` §5.1 的定案是「带外的只有一件：CA 根证书」。主机指纹是**第二件**。但它**不新增带外信道**：拿到一台机器的 SSH 凭据的那个人，就是有权限在那台机器上跑 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 的人，指纹和私钥走的是**同一条**渠道、**同一个**动作。所以准确的表述是：**带外的信道仍然只有那一条，只是这一次它多运一个字段。**

**指纹拿不到时怎么办**（必须给,否则实现会偷偷退回 `accept-new`）：**拒绝登记**，并在错误里写清怎么拿（在目标机上跑一条 `ssh-keygen -lf` 并把输出抄过来）。这与 `console.md` §4.2 那条「宁可起不来」的规则是同一个取舍：**「忘了填指纹所以登记不了」是一个当场就会被发现的失败；「静默接受了一把不知道谁的主机公钥」不是。**

## §4 失陷分析

### 4.1 控制台被拿下（admin token 泄漏）

| | 今天 | 加了装机面之后（**admin ⊉ provision**） | 如果偏序写反了（admin ⊇ provision） |
|---|---|---|---|
| 能做什么 | 注册 / 注销 / 心跳 / 唤醒 / 对话 | **一模一样** | **四台机器上的用户级代码执行** |

这就是 §8.2「admin 不是 provision 的超集」那条定案的**全部**理由，用一张表说完。补一条量级感：admin token **会**出现在查询串里（`console.md` §4.1 / §6.8：浏览器导航与 `EventSource` 都带不了 header）、**会**出现在 cookie 里、**会**出现在 50 个人之外那 2 个人的浏览器历史里。**一个会在地址栏里出现的字符串，不该同时是能在四台机器上装软件的字符串。**

### 4.2 凭据库被读走

密文库单独被读走 → 无用（主密钥不在里面）。**但主密钥就在同一台机器上，所以「凭据库被读走」的现实含义就是「H 被拿下」**，见下条。§3.3 已经如实写明：凭据库不是一道独立防线，它挡的是误拷贝。

### 4.3 H 被拿下 —— **本设计新增的单点，必须被评审明确接受**

照 `key-distribution.md` §11 T-E 的写法单列。

**H 今天已经持有**：全部四把传输 PSK（`beta-env.md` §8.3）、备份归档 token（§2.7）、控制台两枚 token（§3.2）、注册中心与控制台本身。**它本来就是最高价值目标。**

**本设计给它新增**：四台节点的 SSH 私钥。这把 H 从「能读、能唤醒、能注销」升级成「**能在每一台节点上以那个账号执行代码**」。用一句话说清增量：

> **H 从「网络的大脑」变成了「整张网的横向移动枢纽」。**拿下 H 之前，攻击者需要分别攻陷四台机器；拿下 H 之后，四台是一次的事。

**缓解，五条，且每一条都是可检查的**：

1. **SSH 信任严格单向：H → 节点，节点上不放任何指向 H 的凭据。**节点的 `authorized_keys` 里有 H 的公钥；**H 的 `authorized_keys` 里没有任何节点的公钥**，节点上也不存 H 的私钥。这条不只是纵深防御——它是 `audit-witness.md` §4.1 那条前提（**见证方与被见证的节点必须处在不同的失陷域**）在本设计下**仍然成立**的唯一理由：见证机制的攻击模型是「攻击者拿到某个节点的本机写权限」，而单向信任意味着**节点被拿下不能反向到 H**。**这条一旦被破坏（比如为了方便让节点能 rsync 回 H），机外见证就一起失效了**，而那件事在代码里看不出来。
2. **每节点一把 SSH 密钥，不是全网一把。**理由与 `beta-env.md` §8.2「PSK 每节点一把」逐字同源：一把通用密钥意味着任何一次误发等于四台全开。`audit-witness.md` §4.1 的那条 ⚠️ 说的正是这个。**现场现在是一把服务四台，这是一笔要还的债**（§3.1 末）。
3. **目标账号非 root、无 sudo。**四台里三台本来就无 sudo；**剩下那一台是 root**，它的失陷等级与其余三台不同，要在运维单页单独记一行，并优先给它建一个专用的非特权账号。
4. **长期 key 上钉 `command=` + `restrict` + `permitopen`（§5.1，P-10/P-11/P-12 实测有效）。**这条把「拿到私钥 = 任意远程执行」降级成「拿到私钥 = 能跑那五类动作」。**它是本设计里唯一一条能在 H 已经失陷之后仍然生效的缓解**，因为它的强制点在**目标机的 sshd**上，不在 H 上。
5. **装机账本 + 每日机外锚点（§9）。**它不阻止任何事，它保证「H 上发生过一次装机」这件事在 H 之外留有痕迹。

**残余风险，如实写**：§5.2 的引导阶段（第一次装机、以及每次换 key）必然要一把**没有 `command=`** 的 key，那一小段窗口里凭据就是一个通用远程执行能力。**这个窗口不能被消掉，只能被压短并被记账**——它的开始与结束都必须是账本上的两条独立记录。

### 4.4 一条硬要求：凭据的六个禁地

**凭据（私钥、主密钥、以及 provision token 本身）永不出现在以下任何一处**：

1. **任何控制台读路由的响应体**——包括「已配置 / 未配置」之外的任何派生值（指纹只回显前 8 位，且只对 admin）；
2. **任何日志**（stdout / stderr / 进程日志）——**推论：生产路径上禁止开 `ssh -v`**，因为 verbose 输出会打出身份文件路径与 agent 协商细节；诊断需要 verbose 时是一个显式的、会被账本记一条的动作；
3. **审计正文与装机账本**（账本记 node、动作、结果、耗时、指纹前 8 位，不记凭据本身——形状与 `packages/audit/src/record.ts` 只记 id / code / 计数同源）；
4. **命令行**。这条现在有本机实测：H 上 `/proc/<pid>/cmdline` 是 **444**（全机可读），`/proc/<pid>/environ` 是 **400**（只有属主）。这正是 `consoleTokenSources.ts` 模块注释写的那条，也是它把优先级排成 **文件 > 环境变量 > 命令行** 的依据；
5. **URL / 查询串 / cookie**——provision token 与其他两枚不同，它**连查询串位置都不许用**（§8.3）；
6. **备份 store、审计镜像、配置根快照、`beta-reset` 的归档**——§3.3 末尾那四条显式排除。

## §5 定案二：五类动作，各自的契约

> **2026-10-03 补注（章程 v2.22）**：动作集已由负责人决定扩为六类。本节只写前五类（装机面）的契约；第六类「下发模型配置」的契约、强制命令与权限见 [`providers-console-m1.md`](./providers-console-m1.md) §2.5、§7.4。第六类用**单独一把**受限 key，不与本节五类共用：同一把公钥在 `authorized_keys` 里只有第一行的选项生效，强制命令不同就必须是不同的 key。

### 5.0 为什么不留任意命令字段（把负责人第②条的理由写出来）

一个 `command: string` 字段会让这个面**变成一个远程执行器**，而远程执行器的攻击面不由它自己的代码决定，由**调用它的凭据的门槛**决定。`console.md` §4.4 已经用同一条论证把唤醒目标钉死在启动参数上——「admin token 的门槛远低于能改本机 systemd 单元」。装机面比那更甚：它动的是**四台别的机器**。

所以本设计取的形态是：**参数不是自由字符串，命令不是参数。**

- 每类动作对应一个**固定的远端脚本**，脚本随交付物装在节点上（`<内测根>/bin/qm-provision-<verb>.sh`）；
- 参数逐个过既有校验器：node 段与 agent 段过 `@qianmo/protocol` 的地址段校验（**不另写一份正则**，与 `key-distribution.md` §4.2「编码只此一种」同一条纪律）、端口是 0–65535 整数、**路径一律由 H 侧从 `QIANMO_BETA_ROOT` 派生，从不由请求给**；
- **`install` 是唯一一个把脚本送过去的动作**，它送的是一个内容哈希已知的 tar，远端只做「校验哈希 → 解开 → 跑入口脚本」，不接受任何来自请求的命令字符串。

### 5.1 闭合由 sshd 强制，不只由我们强制（P-10/P-11/P-12）

**定案**：长期 key 在节点 `authorized_keys` 里的形态钉死为

```
command="<内测根>/bin/qm-provision-dispatch.sh",restrict,port-forwarding,permitopen="127.0.0.1:38625" ssh-ed25519 AAAA…
```

三段各自的实测依据：

| 段 | 实测（§2） | 它保证什么 |
|---|---|---|
| `command="…"` | **P-10** | 客户端发什么命令都不会被执行，只会作为 `$SSH_ORIGINAL_COMMAND` 传给 dispatch 脚本，由脚本自己决定认不认 |
| `restrict` | P-11 | 关掉 agent 转发、X11、TTY、`user-rc`——一次关全，之后按需逐个开回来。**比列一串 `no-*` 更不容易漏** |
| `port-forwarding` + `permitopen="127.0.0.1:38625"` | **P-11 / P-12** | 隧道动作照常成立；转发到别的地址在 **channel 打开的那一刻**被 sshd 拒（`administratively prohibited`） |

**为什么这一条值得单列**：它是本设计里唯一一条**在 H 已经失陷之后仍然生效**的约束。我们代码里的白名单，攻击者拿到私钥之后可以绕过（他不用我们的执行器）；`authorized_keys` 里的这一行他绕不过，因为强制点在目标机上。**「不留任意命令字段」这条要求，只有落到这一行上才是结构性的；只落在我们的执行器里，它是一句约定。**

**但这一行放在一个我们不拥有的文件里，而它的失效是静默的。**`authorized_keys` 归目标机的那个账号所有，可能被别的东西改写——云厂商的元数据服务、别人的配置管理、同事的一次手工编辑。**被改写之后那把 key 照样能认证，只是不再受限**，于是五类动作照常工作、页面全绿、账本全绿，而唯一一条能在 H 失陷后救命的约束已经没了。**一个失效之后长得和成功一模一样的防线，必须有人定期去看它还在不在。**

**因此配一条定期复核（这是本节的第二条定案，不是建议）**：每次 `start` 之前、以及每天一次，用受限 key 发一条**故意不合法**的探测命令；预期回答是 dispatch 脚本那句 `DISPATCH-RAN original=[…]`（P-10 的那一行）。**拿到别的回答就说明限制没了**——记账本、控制台红条、并在人处置之前拒绝执行任何装机类动作。判据是**回答的形状**，不是「连得上」：连得上恰恰是限制消失之后的表现。

### 5.2 引导：两阶段 key（这是本设计最脆弱的一段，写在前面）

第一次装机时节点上还没有 dispatch 脚本，所以第一次**不可能**用受限 key。定案：

```
① H 生成一把一次性引导 key（无 command=，仅 restrict）
② 人把引导公钥装进目标机 authorized_keys ← 这一步不在装机面里，见下
③ install 用引导 key：送交付物 → 装 → 自检 → 写 dispatch 脚本
④ install 的最后一步：把长期受限 key 写进 authorized_keys，并把引导 key 那一行删掉
⑤ 账本上记两条独立记录：引导窗口开始、引导窗口结束
```

**第 ② 步为什么不在装机面里**：把「往一台还没有任何阡陌信任关系的机器上装公钥」也做成一个按钮，需要那台机器已经接受某种凭据——那就回到了先有鸡还是先有蛋。**这一步保持人工，是有意的**：它是整条链上唯一一次「人确认这台机器要加入这张网」的动作，与 `key-distribution.md` §5.1 里 CA 根证书的首次装载是同一种性质的、**全网每台只发生一次**的带外动作。

**残余风险，明写**：③ 与 ④ 之间那段时间里，引导 key 就是一个通用远程执行能力。**如果 `install` 在中途失败**，那一行会留在 `authorized_keys` 里。因此 `install` 的失败回滚**必须**包含「删掉引导 key 那一行」，且回滚失败要在账本上留一条**红色**记录并在控制台上显示到有人处置为止——**一个静默失败的清理，等于一个永久的后门。**

### 5.3 动作 `install`

| 项 | 内容 |
|---|---|
| **输入** | 凭据句柄（不是凭据本身）、节点段、agent 段（1~N 个）、team、入站端口、绑定地址 |
| **前置检查（机器可判）** | ① 架构 ∈ {x86_64, aarch64}；② `unzip` 或 `busybox unzip` 在（`demo-env.md` §2.1 那个唯一硬卡点）；③ 可用内存 ≥ **2 GB**（含 swap）——`bun run build` 峰值实测 1563 MB；④ 家目录可用磁盘 ≥ **3 GB**（Linux x64 上 `node_modules` 1.4 GB + `dist` + 交付物 + 余量）；⑤ Bun 不在则装 **1.3.13**（pin），在则版本核对（低于 `engines` 下限失败，与 pin 不一致警告并继续——照 `bootstrap.sh` 的既有处置） |
| **前置检查（P-7 逼出来的那一条）** | **⑥ 一次真自检**：解开交付物后先跑一个最小的符号链接解析用例，再跑一次 `bun test` 的最小子集。**这一条不能省成规格清单**——spare-A 通过了 ①~⑤ 全部五项，`bun --version` 也正常，而它的内核让 `node_modules` 的符号链接一律 `EISDIR`，整个仓库不可用 |
| **幂等语义** | **以「自检通过」为完成标志，不以「文件在那儿」为完成标志。**依据是 P-7 之后那次实测：一次失败的 `bun install` 会留下一个 1.4 GB 的 `node_modules`，而**再跑一次 `bun install` 会报「no changes」**——它认为装完了，随后的构建以一串看不出因果的错误失败。所以重跑 `install` 必须能识别「上一次没到自检」并**先清干净再来**，而不是接着上一次的残骸往下走 |
| **失败回滚** | ① 删引导 key 那一行（§5.2，**最高优先级**）；② 半成品目录改名成 `<内测根>.failed-<ISO>` 而**不是删除**（照 `beta-env.md` §6 L2「配置根只改名不删」的同一条纪律——里面可能已经有审计链的头几条）；③ 账本记一条 `failed` 并带上失败在哪一步 |
| **副作用** | 目标机：家目录下多一个内测根、一份交付物、`node_modules` 与 `dist`、一个 0600 的 PSK 文件、`authorized_keys` 多一行受限 key（少一行引导 key）。H：凭据库多一条、账本多两到三条、`peers.conf` 多一行 |
| **审计落点** | **H 侧装机账本**（§9）。节点侧此刻还没有审计链——那条链是常驻进程第一次跑起来才有的 |

**PSK 的时序，在这里扳回来**（`beta-env.md` §8.3 的要求 + 现场这一轮走反的那一步）：

```
install 内部的固定顺序，不许调换：
  ① H 上生成本节点那一把 PSK（H 侧动作，节点还没被碰过）
  ② 落进 H 的 secrets/peers/<node>.psk（0600）
  ③ 在同一次 SSH 会话里写进节点的 secrets/transport-psk（0600，经 stdin 写入，不经命令行）
  ④ 之后才允许 start
```

**为什么顺序是硬的**：反过来（先起节点、节点自己生成、再报给 H）会得到一个**短暂地由节点单方面决定的共享密钥**，而那正好是 `handshake.ts` 模块注释里那句「任何持钥者可冒充任何节点」在部署面的对应物。而且 `demo/env/beta/README.md` 已经写明「在节点机上本地重新生成一把，得到的是一个 H 永远拨不通的节点」——**顺序走反的代价不只是安全，还是一次必然的返工。**

### 5.4 动作 `start`

| 项 | 内容 |
|---|---|
| **输入** | 凭据句柄、节点段 |
| **前置检查** | 交付物在且自检标记在；PSK 文件在且 0600；配置根三件套齐（`OCC_IDENTITY` / `OCC_CONFIG_DIR` / PSK，`beta-env.md` §4.1） |
| **幂等语义** | **已在跑的不重起**，判据是 pid 文件里的 pid 还活着（照 `demo/env/beta/common.sh` 的 `beta_running`，不另发明）。**就绪判据是「按名解析 + 真拨通」，不是「进程还在」**——这条是 `demo-env.md` §1 第 3 条已经证明过的，也是 P-12 给出的同一条教训 |
| **失败回滚** | 不回滚（起不来就是没起来）。**但要把 `logs/<node>.err` 的末 20 行拉回 H 并写进账本**——`beta-env.md` §6 L0 第②步那句「不看就重起 = 下次同样死法」在这里同样成立，而装机面比人更容易犯这个错 |
| **副作用** | 目标机多一个常驻进程、一个 pid 文件、一对日志文件；节点侧的审计链**从这一刻起才存在** |
| **审计落点** | H 侧账本（动作本身）+ 节点侧审计链（从此刻起接管） |

### 5.5 动作 `stop`

| 项 | 内容 |
|---|---|
| **输入** | 凭据句柄、节点段 |
| **前置检查** | 无（停一个没在跑的东西是成功，不是失败） |
| **幂等语义** | 先 `TERM`，10 s 不走再 `KILL`（照既有 `beta_stop_one`）。**重复停是成功** |
| **失败回滚** | 无（没有「回滚一次停机」这种东西） |
| **副作用** | **会中断在跑的 turn。**这一条要在控制台上作为确认文案出现，不能只在文档里 |
| **审计落点** | H 侧账本。**注意 `stop` 之后节点侧审计链的最后一条与账本这一条之间有一段没人记的时间**，这是正常的，不要在验证工具里把它当断链 |

**一条与拆机排空的关系**：常驻侧已经有「拆机前排空在途回复回执」的处理。`stop` 走的是 `SIGTERM`，也就是走那条排空路径；**`KILL` 那一档会绕过它**，所以账本必须区分「TERM 停下」与「KILL 停下」两种结果——它们对在途消息的后果不同。

### 5.6 动作 `tunnel`

| 项 | 内容 |
|---|---|
| **输入** | 凭据句柄、节点段、本地端口（H 侧，从一个固定段里分配，**不由请求给**） |
| **前置检查** | 该节点的受限 key 上有 `permitopen`；本地端口未被占 |
| **幂等语义** | 同一节点已有活隧道则复用，不再起第二条 |
| **就绪判据** | **必须真穿一次**——建立转发之后从 H 侧对本地端口发起一次真拨号。P-12 实测：转发到未授权目标时会话照常活着、本地监听照常在，错误只在**真有连接穿过去**时才出现（`administratively prohibited`）。**用「`-L` 建起来了」当判据会得到一个假绿** |
| **失败回滚** | 杀掉隧道进程、释放本地端口、账本记一条 |
| **副作用** | H 上多一个长驻 `ssh -N` 进程与一个回环监听端口 |
| **审计落点** | H 侧账本（建立与拆除各一条，带持续时长） |

### 5.7 动作 `mirror`（拉审计镜像）

| 项 | 内容 |
|---|---|
| **输入** | 凭据句柄、节点段 |
| **前置检查** | H 侧目标目录存在且**只有 H 能写**；节点侧链文件存在（不存在是「还没产生审计」，不是错误——与 `console.md` §7.1 `AuditPort` 的处置同一条） |
| **幂等语义** | 单向覆盖（`beta-env.md` §4.3：**节点侧只读、H 侧只写**）。可重复跑，跑多少次结果一样 |
| **失败回滚** | 无。**镜像随时可重建，所以永不备份镜像**（`beta-env.md` §5 已定） |
| **副作用** | H 上 `mirror/<node>/trail.ndjson` 被覆盖 |
| **审计落点** | H 侧账本，记「拉到多少条、末条 seq 与哈希、链验通过与否」 |

**两条必须写死的边界**：

1. **镜像不是权威副本**（`beta-env.md` §4.3 已定，这里只是把它落到动作上）。装机面在页面上显示镜像时**必须**标注「镜像 · 滞后 ≤ N 分钟」；
2. **这个动作只允许读节点侧的审计链文件，不允许读配置根里的任何其他东西。**受限 key 的 dispatch 脚本对 `mirror` 只暴露一个固定路径，路径从节点侧的 `occConfigPath()` 派生而不是由请求给——否则这个动作就是一个「读任意文件」的原语，而那和留一个任意命令字段没有本质区别。

**这个动作的手工形态已经在现场落地，可以照抄**：`demo/env/beta/ops/mirror-pull.sh`（由 `beta-up.sh --role host` 从仓库派生，5 min 一次的 `systemd --user` timer 触发）。三处值得直接搬过来：**必须是拉取式**（强制命令下 `rsync` 协商不到远端 `--sender`，见 §3.3）、**拉到零字节不覆盖**（节点侧链文件还没建时 `cat` 给空内容而退出码仍是 0，覆盖上去等于用一次网络抖动抹掉整条镜像，而 `occ audit --verify` 对空文件不报错）、**先落临时文件再原子替换**（`--verify` 永远不会读到半个文件）。

## §6 「复制文件过去」到底复制什么

### 6.1 三个候选

| 候选 | 跨架构 | 目标机成本 | 主失效模式 |
|---|---|---|---|
| **(甲) 源码 tar + 目标机自建** ← **选它** | ✅ 天然成立 | `bun install` + `bun run build`，要 ≥ 2 GB 内存 | 目标机太小 / 太老（P-7） |
| (乙) H 上建好 `dist` 分发 | ❌ **不成立**（P-2） | 极低 | **跨架构时静默降级**（P-3），最难发现 |
| (丙) 混合：同架构同 libc 时发 `dist`，否则自建 | ✅ | 视情况 | 判定条件写错 = 退化成 (乙) |

### 6.2 定案：**(甲)**，(丙) 只作为**可选加速**且必须重跑 ripgrep 落位

**为什么不是 (乙)**：P-2 实测——`dist/vendor/ripgrep/` 的内容来自 `bun install` 时**按当前平台**下载的那一份，它不在仓库里；H 是 x86_64，三台 aarch64 节点从 H 拿到的 `dist` 里**不会有** `arm64-linux/rg`。而 P-3 说明缺了它**不会报错**，只会静默回落到系统 `rg`（多半也不存在）。**一个跑得起来、拨得通、搜索能力悄悄少一块的节点，比一个起不来的节点难查得多。**

**顺带解掉一个观察**：「四台节点的 `dist/` 树哈希互不相同、文件数同为 1403」——P-2 至少解释了其中一部分：那个 ripgrep 目录是**累积**的（H 上两棵 `dist` 里都是 `arm64-darwin` + `x64-linux` 两项，因为仓库先从 mac 同步过去、又在本机 install 过一次），所以「同一份代码在两台机器上构建出的 `dist` 内容不同」在**不做任何跨架构分发时就已经成立**。**推论：不要拿 `dist` 树哈希当「两台机器版本一致」的判据**，那个判据本来就不成立；版本一致性判据应该是交付物 tar 的哈希 + 自检结果。

**为什么 (丙) 只是可选加速**：它的判定条件要同时卡住架构、libc、以及（P-7 之后）内核大版本，而**判定条件写错的表现正好是 (乙) 的表现**——静默降级。所以它的启用必须是显式的、每次都要在账本上记一条、并且**必须在目标机上重跑一次 ripgrep 落位**（`bun run scripts/postinstall.cjs`，实测幂等：已存在则 `skipping`）。

### 6.3 交付物形态与实测成本

| 项 | 实测 |
|---|---|
| 交付物 | `git archive HEAD` 的 gzip tar，**74 MB**（4669 个 tracked 文件），本机打包 1.5 s |
| 传输 | scp 到一台公网 VPS：**75.8 s**（≈ 1.0 MB/s，单流） |
| `bun install --frozen-lockfile --ignore-scripts` | 冷缓存下 1737 包；热缓存下 0.6 s |
| **一个必须绕开的坑** | **`git archive` 出来的 tar 没有 `.git`，而本仓库的 root `prepare` 脚本是 `husky`**——在那台机器上它以 `Cannot find module './index.js' from node_modules/.bin/husky` 失败，于是整个 `bun install --frozen-lockfile` 以 `error: prepare script … exited with 1` 告终；`HUSKY=0` **无效**（那不是 husky 的 no-git 分支）。**更糟的是它不是原子的**：失败之后 `node_modules` 有 1.4 GB，而再跑一次 `bun install` 报「no changes」，随后的 `bun run build` 以一串与 husky 毫无关系的错误失败 |

**由此产生 `install` 的两条硬规矩**（已写进 §5.3）：

- 走 **`--ignore-scripts`**，然后**显式**跑 `bun run scripts/postinstall.cjs`（那一步才是 ripgrep 的落位，实测幂等）。这样安装期不跑任何仓库脚本，`prepare` 的问题从根上不存在；
- **完成标志是自检通过，不是文件存在**；重跑必须能识别半成品并先清干净。

> **一处如实记的未决**（不写进定案）：`prepare`/husky 这条失败**只在那台机器上验过一次**，而同一条 `bun install --frozen-lockfile` 在 `demo-env.md` §4.4 的两台全新机器上是成功的——那两次走的是 `git bundle` + clone（**有 `.git`**）。所以「无 `.git` 是不是根因」本文**没有测清楚**，`--ignore-scripts` 那条对策**对两种情况都成立**，因此不依赖这个未决。落地首日补一次单变量对照并留档。

## §7 隧道：控制面与数据面的分工

### 7.1 三条线，各答各的问题，不许混

| 线 | 走哪 | 答什么 | 常态经过 H 吗 |
|---|---|---|---|
| **控制面** | SSH（22） | 装 / 起 / 停 / 拉镜像 | **是**（H 是唯一的发起方） |
| **数据面 · 首选** | `qianmo://` 直投，节点 ↔ 节点，38625 | 一条任务消息怎么送到对端 | **否** |
| **数据面 · 兜底** | SSH `-L` 隧道，经 H | 直连被安全组挡死时怎么送 | 是（**这是降级形态，不是设计形态**） |

### 7.2 为什么直投不能常态经过 H（这一条是硬的）

`beta-env.md` §2.6 的定案是「38625 直连、PSK 是唯一的门」。把跨节点直投改成「都经 H 转一道」，换掉的不只是一条链路：

1. **它换掉了 P4.2 的前提。**跳数、防循环、速率预算这三样都是按「A 直接说给 B」算的；每条消息多一跳，跳数预算的语义就变了，而防循环判据看的是路径而不是物理链路——**一个所有消息都经过同一个中转的拓扑，判环还成立，但它算的已经不是原来那张图**；
2. **它把 H 变成全网单点。**现设计里「注册中心挂了，已建连接仍然活着」（`beta-env.md` §2.4，实测过）——这条性质是数据面不经过 H 换来的。让直投经 H，这句话就不成立了：H 一挂，全网静默；
3. **它给 H 增加一条入站数据面。**H 现在只有两个 upstream 暴露在反代后面（控制台、备份服务，§2.5 的 allowlist），而那张 allowlist 是明写「注册中心不在里面」的。把消息转发加进去，等于给这张 allowlist 加第三项——**而它是三项里唯一会承载会话内容的**。

**所以定案是**：隧道是**控制面**，外加**「那三台被安全组挡死的机器在直连恢复之前的数据面兜底」**。兜底形态必须满足三条：① 在控制台与账本上**显式标注为降级态**（不能和直连长得一样）；② 每条经隧道的投递在审计上可区分（**不与直连合并成一栏**，理由与 `key-distribution.md` §7.3 那条「L0/L1/L2 必须是三个独立字段」同源）；③ **有退出条件**——安全组一旦放开 38625，兜底就要退役，而不是变成事实上的常态。

**为什么不是「干脆就用隧道，反正它工作」**：因为那会让「阡陌的节点之间能直接通信」这个产品线 ② 的核心主张，在内测环境里**从来没有被真正验证过**。一个所有消息都经过中心的网络，不是这个项目要证明的那个东西。

## §8 定案三：第三枚 token

### 8.1 与 `resolveTokens` 现有三条策略共存：**一条不改**

`packages/console/src/auth.ts` 的 `resolveTokens` 现在的三条是：① 回环且没给 → 自动生成；② 只要不是回环 → 两枚都必须显式提供，否则拒绝启动；③ 总是校验长度 ≥ `MIN_TOKEN_LENGTH` 且两者不同。

**定案：三条一个字不动**，第三枚走一个**新的纯函数** `resolveProvisionToken`，与 `resolveTokens` 平级、互不调用。它自己的三条：

| # | 规则 | 为什么 |
|---|---|---|
| P① | **永不自动生成，回环也不。** | 自动生成那条规则的全部理由是「操作者不付任何代价就拿到一个能挡住同机其他进程误闯的凭据」（`auth.ts` 原文）。装机面要挡的不是误闯——**一枚每次重启都变的装机凭据，会让「装机」这个动作变得比它应该有的样子更随便** |
| P② | 长度 ≥ `MIN_TOKEN_LENGTH`，**复用同一个常量，不新立一个** | 「指针不复制」（CLAUDE.md §1.1⑧）。装机 token 需要更长是运维纪律（用 `openssl rand -hex 32`），不是第二个常量 |
| P③ | 与 view、admin **都不同** | 与既有那条「view ≠ admin」同一条理由：相同就等于这个设计是一段注释 |

**没给 provision token 会怎样**：整个装机面**不存在**——照 `console.md` §6.7 对话面的既有形状：`/provision` 答 **404**，`/v0/provision/*` 答 **501**，**且两者都在 admin 判定之后**（先判角色再判存在性，否则匿名调用者能靠比较 401 与 501 探出哪台控制台接了装机面）。**不新发明缺席语义。**

### 8.2 三枚的偏序：**admin 不是 provision 的超集**

```
view  ⊂  admin        （既有，不动）
provision  与两者都不可比：admin ⊉ provision，provision ⊉ view
```

**为什么 admin 不是 provision 的超集**（负责人的倾向，本文给出理由）：

1. **admin token 会出现在地址栏里。**`console.md` §4.1 / §6.8：浏览器导航与 `EventSource` 都带不了 header，所以 admin token 必然经过查询串，并且现在还会落进一个 cookie。**一个会在地址栏、浏览器历史和 cookie jar 里出现的字符串，不该同时是能在四台机器上装软件的字符串。**
2. **本仓库已经有一次同型判例。**`key-distribution.md` §10.2 把 CA 签发**排除**在控制台之外，理由逐字是「admin token 的门槛应当比 systemd 单元还高」。装机比改 systemd 单元更重（它动的是别人的机器），所以要么照那条把它排除在控制台之外，要么**用一枚门槛更高的凭据把它买下来**。本设计选后者——因为把它排除在外，就等于放弃「智能体生命周期管理」这一行。
3. **失陷分析里它是一张两列的表**（§4.1）：偏序断开时 admin 泄漏的后果与今天完全一样；偏序不断开时它变成四台机器的代码执行。**这不是纵深防御的修辞，是一个可以填出来的差值。**
4. **反过来 provision 也不该包含 view。**装机凭据不该顺带能读全网审计。两条轴各自独立，是本仓库反复用的同一条纪律（`console.md` §6.1「协议速率与运行时速率是两列不是一个数」、`key-distribution.md` §7.1「三层不许压成一个布尔量」）。

**代价，如实写**：一个人要做装机，需要**同时**持有 admin（看得见页面）与 provision（做得了动作）。这与 `auth.ts` 里那句「一个人一份凭据是常态，逼他拿两份等于他只会拿一份」**表面上冲突**。化解在于两枚的用法不同（下一节）：admin 是**一次登录**，provision 是**一次一用的输入**。**它不是第二份要保管的凭据，它是一次确认动作。**

### 8.3 provision token 的位置：**只走 header 或动作自己的请求体**

**定案**：provision token **不许**走 `?token=`，**不许**进 cookie，**不许**被页面存进 localStorage。它只能出现在两个位置：`Authorization`（脚本调用）或**该次动作的表单提交体**（页面调用），且页面用完即丢。

**为什么**：这是让「第三枚 token」真的成为第三枚、而不是「admin 的另一个别名」的**唯一**结构性区别。三枚 token 如果都用同样的方式获得、存放、附带，那么它们的实际门槛就是一样的，偏序表只是一张纸。**把它钉在「一次一用的输入」这个位置上，装机就自动带上了一次人的确认**——而这恰好是 §5.2 引导窗口最需要的东西。

**与 CSRF 规则的关系**：因为它不走 cookie，它**不是** ambient 凭据，所以 `auth.ts` 那套针对 cookie 的规则（自定义头 + 不答 preflight）对它不适用也不需要——**理由与那份模块注释给 `Bearer` 与 `?token=` 豁免的理由逐字相同**：「a page that can supply either of them already knows the token, and CSRF is an attack by somebody who does not」。

## §9 装机的审计落点：H 侧要有自己的账本

### 9.1 为什么必须有

**装机发生时，目标节点上的审计链还不存在。**那条链是配置根建好、常驻进程第一次跑起来之后才有的（`start` 之后，§5.4）。所以「谁在什么时候把这台机器加进了这张网」这件事，**在节点侧的审计链上永远不会有记录**——它的第一条记录只能是它自己起来之后的事。

### 9.2 它是什么、谁写、能不能被篡改

| 项 | 定案 |
|---|---|
| 形态 | **append-only NDJSON + 哈希链**，形状**照 `@qianmo/audit` 的既有实现，不新建机制**（`O_APPEND \| O_NOFOLLOW` 的 fd、每条 `fsync`、每条带前一条的哈希） |
| 谁写 | H 上的 provision 进程，独占写 |
| 记什么 | 时间、node 段、动作、结果、耗时、失败在哪一步、主机指纹前 8 位、**引导窗口的开与关各一条** |
| **不记什么** | 凭据、凭据派生值、**操作者**（见 §10.1） |
| 能不能被篡改 | **三句承诺里只成立前两句**，与节点侧的审计链**完全一样**：写入方改不了 ✅、外部改动可检测 ✅、外部改动**没有被阻止** ❌。**一个有 H 写权限的人可以整篇重写并重算哈希** |

### 9.3 补第三句：直接用 `audit-witness.md` 的定案，不另发明

`audit-witness.md` §3 已经为完全相同的问题定了案（**定期锚定摘要**），§4.1 已经给出了锚点端点的形状（照抄 `packages/backup` 的三层：面 / 形状 / 存储）。本设计**不重新选型**，只补两条它在本场景下的特殊之处：

1. **主位置不能是 H 自己。**`audit-witness.md` §4.1 把锚点端点挂在内测宿主上，前提是「见证方与被见证的节点处在不同的失陷域」——那对**节点侧**的链成立。但**装机账本的写入方就是 H**，所以 H 给自己的账本做见证等于没做。装机账本的锚点**必须**走 §4.1 的那个「次位置」：**一个真正独立的失陷域**（私有 git remote 且禁 force-push，或负责人邮箱 / IM）。
2. **频率取「天」，不取 60 s。**`audit-witness.md` §4.2 给消息审计取 60 s，理由是消息量大。装机是**低频高价值**动作：一天可能零条，也可能四条。**每次动作完成时立即锚一次**（触发式），外加每天一条空锚（证明「今天没有装机」也是一个需要被证明的事实——没有它，攻击者删掉当天全部记录之后，账本看起来就像那天什么都没发生）。

**这条同时回答了 §4.3 缓解⑤**：账本不阻止 H 上的任何事，它保证「H 上发生过一次装机」在 H 之外留有痕迹。

## §10 范围与边界

### 10.1 与章程 N-2（不做账号体系）的关系：**不触边界**

`beta-env.md` §10 包④ 讨论过同一条边界，它的 DoD④ 原文是：「页面与审计上出现『**哪一枚做的**』——这一条会触及 N-2 的边界，必须先确认它算不算『账号体系』」。

**关键在于那条边界的轴是什么。**包④ 会触边界，是因为它把 view token 从一枚变成**一张按人分的表**——一旦「哪一枚」能对应到「哪个人」，审计上就出现了 **principal**（主体），而主体正是账号体系的最小内核。

**本设计的第三枚 token 不在那条轴上**：

| | 包④（按人发 token） | 本设计（第三枚 token） |
|---|---|---|
| 轴 | **按主体分**（人 → token） | **按能力分**（动作类别 → token） |
| token 数 | 随人数增长 | **固定三枚** |
| 审计上多出什么 | 「**谁**做的」 | 什么都不多——账本**不记操作者**（§9.2） |
| 撤销单个人 | 是这个包存在的理由 | **做不到，也不试图做** |

控制台今天已经有两枚在「按能力分」这条轴上（读 / 写）。**在同一条轴上加第三枚，和把第一条轴换成另一条轴，不是同一种改动。**

**结论：不算账号体系，N-2 不需要解禁。**

**但要写死一条护栏**：一旦有人想在装机账本上记「是哪个人装的」，那**就是**包④的那条边界，必须先走那个包的边界确认，答案是「算」就整个挪进 M1「权限模型上线」那一行。**装机账本因此明写「不记操作者」，与 `console.md` §7.1 保持一致**；持有 provision token 的人只有 1~2 位，出事靠口头解决——与 `beta-env.md` §3.1「admin 为什么是 2 人」是同一个取舍。

### 10.2 roadmap 落点与是否回写章程

**roadmap 落点：M1「注册发现产品化」行的第三段「智能体生命周期管理」。**理由：那一行的三段分别是「最小 Web 控制台」（已由 `console.md` 落地）、「账号体系」（N-2 未解禁，不做）、「智能体生命周期管理」——而「一台机器从空白到成为网络里的节点，再到起停与退役」正是生命周期的头尾两端。**本设计不落在「权限模型上线」那一行**：它没有引入授权流、没有时效凭据、没有主动撤销。

**章程：需要负责人裁定，本文不替他定。**

- N-5 已于章程 **v2.14** 解禁，但那条解禁的措辞是**穷举式**的：「解禁的是什么」逐项列举了花名册与状态、消息链 / 审计查看、页面内注册、唤醒与限额视图。**装机不在那份清单里**；
- 章程 §7.3 的变更流程表里，「非目标解禁（§2.2）」要**全员评审 + 负责人签字**，记录方式是**回写本文 + 评估对排期影响**；
- **本文的建议**：按 §7.3 走一次 N-5 的**补注**（不是新解禁一条，是把 v2.14 那份清单加一项），升章程版本号，并在 roadmap 加一条记录。**理由是形式而不是实质**——实质上装机就是那一行里的「生命周期管理」，但 v2.14 的措辞是穷举的，穷举清单之外的东西默认在外，这是那种措辞方式自己带的后果。

**N-3（生产级加密）不受影响**：本设计不做 PKI、不签发证书、不做端到端加密、不做密钥托管。它搬运的是**已经存在**的 PSK（`beta-env.md` §8 的形态一字不改），只是把搬运动作从人换成了机器。

**N-7（不接公有云弹性 API）不受影响**：本设计的输入是「一台你已经能 SSH 进去的机器」，它不申领实例、不调用任何厂商 API。**这条边界要写在控制台的文案里**，否则「自动装机」很容易被读成「自动扩容」。

## §11 落地任务包草案

按「能不能独立评审、能不能独立回滚」切。四个包，**顺序不可交换**（②依赖①的凭据面与端口契约，③依赖②的动作执行器，④按需）。估算口径沿用 `retro-m0.md` §7.5（**主开发 + AI 协作**），**不是**章程 §6.3 的多人口径。

| 编号 | 名称 | DoD | 估算 |
|---|---|---|---|
| **①** | **凭据面与第三枚 token** | `resolveProvisionToken` 纯函数（P①②③，**`resolveTokens` 三条策略一字不改**，两函数互不调用，有对照单测）；凭据库的信封加密（`node:crypto` AES-256-GCM，**零新增依赖**）与四条拷贝路径的显式排除（**每条一个负向用例**）；`ProvisionPort` 契约进 `packages/console/src/deps.ts`（**包内仍零第三方依赖**），生产实现落 host 侧 `src/cli/handlers/`；`/provision` 404 / `/v0/provision/*` 501 且**在 admin 判定之后**（照对话面既有形状，有探测用例）；一条与 `check:identity-paths` 同形的扫描：**凭据字段名与凭据目录字面量不出现在 `packages/console/` 里** | **12–24 人时** |
| **②** | **五类动作的执行器** | `spawn ssh` + 一次性 agent（`ssh-add -`，**明文私钥不落盘**，socket 0700 短路径，信号上挂清理）；`StrictHostKeyChecking=yes` + 自有 `known_hosts`，**指纹缺失即拒绝登记**；五类动作各自的前置检查 / 幂等 / 回滚按 §5 逐条；**`install` 的完成标志是自检通过**，重跑能识别半成品并先清干净（**这一条要有一个把上一次打断在 `bun install` 中途的用例**）；PSK 时序按 §5.3 的四步固定；参数校验复用 `@qianmo/protocol` 的地址段校验，**不另写正则**；负向用例：任意命令字段不存在、路径不由请求给、`mirror` 只能读那一个路径 | **16–32 人时** |
| **③** | **sshd 侧闭合 + 装机账本 + 页面** | 受限 key 一行（`command=` + `restrict` + `port-forwarding` + `permitopen`）由 `install` 写入，引导 key 由 `install` 删除，**回滚路径含删引导 key 且失败要红**；真机复现 P-10 / P-11 / P-12 三条并留档（**换 OpenSSH 版本后必须重测**）；**受限状态的定期复核**（§5.1 第二条定案：每次 `start` 前 + 每天一次，判据是 dispatch 回答的形状而不是「连得上」，失败即红条并冻结装机类动作，**有一个把 `authorized_keys` 换回不受限那一行的负向用例**）；装机账本（照 `@qianmo/audit` 的形状，不新建机制）+ 触发式锚点 + 每日空锚，锚点**次位置在 H 之外**；控制台装机面（列表、登记表单含指纹必填、五个动作按钮、降级态标注） | **12–24 人时** |
| **④**（**按需**） | **同架构预构建加速** | **触发条件**：②③ 上线后连续 4 周，且 `install` 的构建段确实成为主要耗时（有账本数据支撑，不是预期）。判定条件同时卡架构 + libc + 内核大版本，启用是显式的、每次记账，**且必须在目标机重跑一次 ripgrep 落位**；一条负向用例：判定不满足时**必须**退回源码自建 | **8–16 人时** |

**合计 40–80 人时**（不含④），含④ **48–96**。比例参照：`key-distribution.md` 的设计包 12–24 人时对落地 40–80 人时，本包同一量级。

## 附 A · 探针复现命令

十二项事实（§2）跑出来的方式。**这些脚本不入库**——它们是一次性证据，落地包会把其中该长期存在的部分变成用例。主机身份一律用占位符，真值只在运维单页。

```bash
# P-1 / P-2 / P-3：交付物的平台相关面
find vendor -type f -name '*.node' -exec file {} \;      # 六个三元组，全在库
ls src/utils/vendor/ripgrep/                              # 只有本机那一个平台目录
grep -n "vendor" scripts/post-build.ts                    # 整目录复制进 dist/vendor/
sed -n '58,64p' src/utils/filesystem/ripgrep.ts           # <arch>-<platform>/rg，缺了回落系统 rg

# P-4：口令不从 stdin 读
echo 'anything' | ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no <host> true
#   → Permission denied, please try again.  ×3（管道内容从未被使用）

# P-5：askpass 助手确实被调用
printf '#!/bin/sh\necho "ASKPASS-CALLED prompt=[$1]" >&2\necho wrong\n' > askpass.sh && chmod +x askpass.sh
SSH_ASKPASS="$PWD/askpass.sh" SSH_ASKPASS_REQUIRE=force \
  ssh -o NumberOfPasswordPrompts=1 -o PreferredAuthentications=password -o PubkeyAuthentication=no <host> true
#   → ASKPASS-CALLED prompt=[<user>@<host>'s password: ]

# P-6：sshpass 自抹 argv，但长度还在
sshpass -p 'SECRETPW123' ssh <host> 'sleep 3' & sleep 1; ps -eo args | grep sshpass
#   → sshpass -p zzzzzzzzzzz ssh …   （11 字符 → 11 个 z）

# P-7：内核 4.9 上 Bun 解析不了 node_modules 里的符号链接（最小复现，单变量对照）
mkdir -p sl/real sl/app/node_modules
echo 'export const x=1' > sl/real/index.js
printf '{"name":"real","version":"1.0.0","main":"index.js","type":"module"}' > sl/real/package.json
ln -s ../../real sl/app/node_modules/real
echo 'import {x} from "real"; console.log("resolved", x)' > sl/app/main.js
cd sl/app && bun run main.js
#   kernel 4.9  → error: EISDIR reading "…/node_modules/real"        （bun build 同样）
#   kernel 6.1  → resolved 1                                          （同一个 Bun 1.3.13、同为 x86_64 Linux）

# P-8：StrictHostKeyChecking 两档
ssh -o UserKnownHostsFile=./kh -o StrictHostKeyChecking=accept-new -o BatchMode=yes <host> true
#   → Warning: Permanently added '<host>' (ED25519) …  然后命令照常执行  ← 这就是 TOFU
ssh -o UserKnownHostsFile=./kh2 -o StrictHostKeyChecking=yes -o BatchMode=yes <host> true
#   → No ED25519 host key is known for <host> … Host key verification failed.

# P-9：私钥经 stdin 进一次性 agent，明文不落盘
D=$(mktemp -d /tmp/qmag.XXXX); chmod 700 $D            # 路径要短：socket 有长度上限
ssh-agent -a $D/a.sock >/dev/null; export SSH_AUTH_SOCK=$D/a.sock
cat <私钥> | ssh-add -                                  # → Identity added: (stdin)
ls -l $D/a.sock                                         # → srw-------
ssh -o IdentityAgent=$D/a.sock -o BatchMode=yes <host> 'echo AGENT-AUTH-OK'

# P-10 / P-11 / P-12：动作集闭合由目标机 sshd 强制（加一行，测完删一行，先备份）
#   authorized_keys 追加：
#   command="<路径>/dispatch.sh",restrict,port-forwarding,permitopen="127.0.0.1:38625" ssh-ed25519 AAAA…
ssh -i <key> <host> 'rm -rf /tmp/whatever; echo ARBITRARY-RAN'
#   → DISPATCH-RAN original=[rm -rf /tmp/whatever; echo ARBITRARY-RAN]   ← 原命令一个字没跑（P-10）
ssh -i <key> -N -L 39997:127.0.0.1:38625 <host> &                        ← 会话存活（P-11）
ssh -i <key> -N -L 39995:127.0.0.1:22   <host> & sleep 2; nc -w 4 127.0.0.1 39995 </dev/null
#   → channel 2: open failed: administratively prohibited: open failed   ← 在 channel 打开那一刻拦（P-12）

# §4.4 第 4 条的旁证：/proc 的两个文件权限不同
bash -c 'exec -a "fake --token=SECRET_abc123" sleep 60' & sleep 1
stat -c "%a %U %n" /proc/$(pgrep -f SECRET_abc123)/{cmdline,environ}
#   → 444 <user> /proc/<pid>/cmdline      ← 全机可读
#   → 400 <user> /proc/<pid>/environ      ← 只有属主

# §6.3：交付物形态与那个坑
git archive --format=tar HEAD | gzip -1 > src.tar.gz    # 74 MB / 4669 文件 / 1.5 s
scp src.tar.gz <host>:                                   # 75.8 s ≈ 1.0 MB/s（单流公网）
#   tar 里没有 .git；此后 `bun install --frozen-lockfile` 在 root prepare（husky）失败：
#   error: Cannot find module './index.js' from '…/node_modules/.bin/husky'
#   error: prepare script from "…" exited with 1        （HUSKY=0 无效）
#   失败后 node_modules 有 1.4 GB，再跑一次报 "no changes"，随后 build 以无关错误失败
#   对策（对两种情况都成立）：
bun install --frozen-lockfile --ignore-scripts && bun run scripts/postinstall.cjs
```

**环境**：开发机 Darwin arm64 / OpenSSH 10.2p1；宿主 Linux x86_64 kernel 6.1 / Bun 1.3.13；备用机 Linux x86_64 kernel 4.9 / glibc 2.24 / 996 MB / 无 swap，与 Linux x86_64 kernel 6.1 / 961 MB。2026-08-17。

> **两条踩过的坑，记下来省得下次再踩**：① 判断 `permitopen` 是否生效**不能**用「`-L` 建起来了」当判据——`ExitOnForwardFailure` 在这里不会触发，必须真穿一次（P-12 就是这么才看见那行 `administratively prohibited` 的）；② 第一轮把「无 `.git`」和「husky 失败」当成因果关系写了，重跑单变量才发现**没测清楚**——`demo-env.md` §4.4 那两台机器上同一条命令是成功的，而它们走的是有 `.git` 的路。**多变量一起改会得出自相矛盾的观测**，这与 `key-distribution.md` 附 A 的第二条坑是同一条。

**换 OpenSSH 版本后 P-8 / P-10 / P-11 / P-12 必须重测**——它们是 §3.6 与 §5.1 两条定案的唯一依据，而它们依赖的是 OpenSSH 的实现行为而不是标准。**换 Bun 版本或目标机内核后 P-7 必须重测**，理由同上。
