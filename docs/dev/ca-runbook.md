## 1. 生产根证书（公开材料）

| 字段 | 值 |
|---|---|
| **`fingerprint256`** | **`C7:3B:47:E1:8C:71:CF:CF:0D:C3:C9:0A:BA:55:F7:5D:E2:FF:36:D6:22:D2:CA:D4:83:D2:03:23:02:BD:0E:A3`** |
| subject / issuer | `CN=qianmo-ca`（自签；CN 只是装饰，身份在 SAN 里，§4.2） |
| 算法 | 密钥 Ed25519，签名 ED25519（§4.1：根取 Ed25519，节点 TLS 叶取 EC P-256，F-5 / F-6） |
| 序列号 | `1CC6235D408FFF5F27C6E6B13BFF03ECED445B48` |
| 有效期 | `notBefore` 2026-09-27T03:20:01Z → `notAfter` **2036-09-24T03:20:01Z**（10 年兜底，§6.2） |
| 计划换根 | 2029-09 前后（§3.3：每 3 年主动换根，新旧根重叠 90 天）。步骤见 §6.2；新根的 CN 必须和这张不同，`qm ca init` 的默认 CN 带建根日期，不加 `--cn` 就不会同名 |
| 扩展 | `basicConstraints` critical `CA:TRUE`；`subjectKeyIdentifier` = `authorityKeyIdentifier` = `13:74:5C:0A:68:73:AD:04:38:45:68:CE:AA:D3:6A:37:31:50:8A:DA` |
| CA 公钥（43 字符 base64url） | `HiX77WSlX_dkCWdCt_DwVhdmXegp80zSBNYcewdboFU`：用来验吊销清单（RL）签名的那把，节点从根证书里读出，不单独分发（`caKeys.ts`） |
| 生成方式 | `qm ca init`，默认参数（Ed25519 / 3650 天 / `CN=qianmo-ca`，这是当时的默认 CN；此后默认 CN 改为 `qianmo-ca-<UTC yyyymmdd>`），OpenSSL 3.6.3，从源码运行，基点提交 `08095aac` |

**核对方法**（每台节点装根证书时做一次，§5.1 / §5.3）：

```bash
openssl x509 -in <配置根>/qianmo/trust/ca.pem -noout -fingerprint -sha256
```

输出必须与上表 **32 个字节逐个相同**，只比前几组不算核对过。对不上就停手，不装、不启动，先查这份 `ca.pem` 是从哪来的。

换根重叠期里 `ca.pem` 有两张根（§6.2），上面这条命令**只读第一张**。那时改用下面这条，逐张打印 subject 和指纹，每一张都要核对：

```bash
awk '/-----BEGIN CERTIFICATE-----/{c=""} {c=c $0 "\n"} /-----END CERTIFICATE-----/{cmd="openssl x509 -noout -subject -fingerprint -sha256"; printf "%s", c | cmd; close(cmd)}' <配置根>/qianmo/trust/ca.pem
```

**根证书 PEM 本身不入库**：它随节点入网从 CA 机器带外拷过去，这份手册里的指纹走另一条渠道（本仓库）。两条渠道分开，核对才有意义。如果 PEM 和指纹都从仓库里取，比对的其实是同一个来源。

## 2. 与演练 CA 的区别

2026-09-26 在内测舰队上做的 K-2 / K-3 / K-7 真机演练（`key-distribution.md` §12.1 的【真机演练回写】），用的是运维本机上的**演练 CA**，**不是**这里的生产 CA。

| | 生产 CA（K-1，本文） | 演练 CA（09-26 舰队演练） |
|---|---|---|
| 用途 | 生产信任根，K-2 起签发全部内测节点证书 | 只给 09-26 的演练签证书 |
| 指纹 | 见 §1，入库 | **不入库**，只留在运维本机的私有证据里（§12.1 原文） |
| subject | `CN=qianmo-ca` | CN 以 `qianmo-drill-` 开头，写明是演练 |
| 目录 | 与演练 CA 是两个不同目录，互不覆盖（`qm ca init` 不会覆盖已有的 CA） | 同一台机器上的另一个目录 |

**当前状态要记住**：演练时 K-2 行里的三个生产节点已经拿到了演练 CA 签的证书，`trust/ca.pem` 装的也是**演练 CA 的根**。K-2 正式签发时要**整套替换**：换成生产根、用生产 CA 重签节点证书。两套材料不能混用：演练 CA 签的证书用生产根校验不通过，反过来也一样。判断一台节点装的是哪一套，只看指纹；CN 只能用来一眼区分，不能当判据。

演练 CA 的私钥怎么处置（留着做以后的演练，或者销毁），由负责人决定，本手册不管。

## 3. CA 私钥的保管

**位置**：负责人工作机上的一个专用目录，在仓库和所有节点之外。具体路径不写进仓库（§3.3：私钥和它的托管形态不入库）。下文统一称 **`<CA 目录>`**；`qm ca` 在不给 `--ca-dir` 时用默认目录，放在别处就每条命令都加 `--ca-dir <CA 目录>`。

**权限**：目录 `0700`，`ca.key` `0600`，`ca.crt` `0644`。文件创建时直接带这个 mode，用 `wx` 独占创建，不是事后 chmod（`operations.ts` 的 `writeNew`）。2026-09-26 建成后逐个核过（§7）。

| `<CA 目录>` 里的文件 | 性质 | 何时出现 |
|---|---|---|
| `ca.key` | **私钥**，`0600`，永不覆盖 | `init` |
| `ca.crt` | 根证书，公开 | `init` |
| `ca.srl` | openssl 序列号 | 第一次 `issue` |
| `issued/<节点>.crt` | 最近一次签给该节点的证书，公开。已存在时 `issue` 默认拒绝；重签要加 `--replace`，被替换那张的指纹留在台账里 | `issue` |
| `issued-ledger.jsonl` | **签发台账**，公开。每签一张追加一行：节点、序列号、`fingerprint256`、`notBefore` / `notAfter`、签发时间。只追加不改写，写入是整文件原子替换。有一行读不通，`issue` 在签名之前就拒绝 | 第一次 `issue` |
| `issue.lock` | 一次 `issue` 运行期间存在，结束即删。残留说明上一次被中断；确认没有别的 `issue` 在跑，删掉即可 | `issue` 运行中 |
| `revoked.json` | 已吊销条目的累积状态，是 `refresh-rl` 的输入。换根时新目录用 `refresh-rl --import-from <旧目录>` 读旧目录的这份（§6.2 第 5 步） | 第一次 `refresh-rl` |
| `revocation-list.json` | 签好名、待发布的 RL，公开 | `refresh-rl` |

**私钥不得出现的地方**（§3.3，逐条对应机器守卫）：

| 禁区 | 谁来挡 |
|---|---|
| 任何身份的配置根（`~/.qianmo`、`~/.occ`、官方 CLI 的根，以及 `OCC_CONFIG_DIR` 指向的根）及其派生目录 | `caDirectory()` 运行时拒绝（`src/services/qianmo/ca/paths.ts`） |
| 仓库检出（当前工作目录所在的检出，以及目标路径所在的检出） | 同上 |
| 已配置的演示根（`QIANMO_DEMO_ROOT` / `DEMO_ROOT`）与已知 CI 工作区变量 | 同上 |
| 节点侧代码里出现 CA 目录或文件名字面量、`@qianmo/*` 包调用 openssl | 扫描断言 `src/services/qianmo/ca/__tests__/caScan.test.ts` |
| 控制台进程可达的路径 | **守卫证明不了**，靠 §10.3 的进程权限与部署纪律（`key-distribution.md` §3.3 原文已写明这一条的边界） |

**如实记的边界**：`0600` 只能挡住**其他系统用户**，挡不住以负责人同一身份运行的进程，包括这台机器上的开发工具、脚本和 AI 代理。所以 §3.3 说的"离线"，现在指的是一个离线用的目录，不是一台离线的机器。可以做的加固（负责人自己选，本次没做）：把 `<CA 目录>` 放进一个加密磁盘映像，只在签发和重签 RL 的那几分钟挂载，用完就卸载，其余时间盘上只有密文；命令加 `--ca-dir <挂载点>` 即可，守卫对 `/Volumes/…` 这类路径是放行的。

## 4. 离线备份（负责人做；本次**没有**做）

建成时私钥**只有一份**。丢了不等于泄露，但结果同样严重：签不出新证书，也签不出 RL，全网只能退回 `--trust` 手工信任撑到换根（§3.3「CA 私钥丢失」）。所以要尽快做一次加密的离线备份。

1. **准备两份离线介质**（例如两个 U 盘），分放在两个物理地点。
2. **在每个介质上建一个加密容器**，然后把整个 `<CA 目录>` 拷进去。macOS 自带的做法：

   ```bash
   diskutil image create blank --encrypt --size 32m --fs APFS --volumeName QMCA-BACKUP /Volumes/<介质>/qm-ca-backup.dmg   # 交互输入口令
   hdiutil attach /Volumes/<介质>/qm-ca-backup.dmg       # 或在访达里双击，按提示输口令；挂到 /Volumes/QMCA-BACKUP
   ditto <CA 目录> /Volumes/QMCA-BACKUP/qm-ca             # 保留 0700 / 0600
   ```

   旧版 macOS 上对应的是 `hdiutil create -size 32m -fs APFS -encryption AES-256 -volname QMCA-BACKUP <路径>`。新系统上它还能用，只是会提示 deprecated。2026-09-26 只拿假口令、空映像核过这两条创建命令的写法，**整套备份流程没有实际跑过**。

3. **校验备份是好的**，只比对公开的那一半，不显示私钥：

   ```bash
   openssl x509 -in /Volumes/QMCA-BACKUP/qm-ca/ca.crt -noout -fingerprint -sha256          # 应等于 §1
   openssl pkey -in /Volumes/QMCA-BACKUP/qm-ca/ca.key -pubout | openssl sha256             # 应等于下一行
   openssl x509 -in <CA 目录>/ca.crt -pubkey -noout | openssl sha256
   ls -l /Volumes/QMCA-BACKUP/qm-ca                                                        # ca.key 仍是 -rw-------
   hdiutil detach /Volumes/QMCA-BACKUP
   ```

4. **口令和介质分开放**。口令用高强度的，不要和 U 盘放在同一处，也不要存在同一台工作机上的明文文件里。
5. **禁止的做法**：私钥不经过 iCloud / 网盘 / 同步目录、聊天、邮件、剪贴板；不放进仓库、`/tmp`、证据目录；不 `cat ca.key`，也不把私钥内容放在命令行参数里。
6. **什么时候要补做**：私钥本身不会变，但 `revoked.json` 每次吊销都会变，`issued-ledger.jsonl` 每次签发都会变。`revoked.json` 丢了或者回到旧版本，下一次 `refresh-rl` 签出来的清单会少掉条目，节点会拒收（节点端的 RL 状态只增不减，§6.4）。台账丢了，被重签替换掉的旧证书指纹就只剩备份里那一份。所以**每次签发、每次吊销之后都要刷新一次备份**。`revoked.json` 万一丢了，可以从最近一次发布的 RL 重建：把 `payload` 按 base64url 解码，得到 JSON，里面的 `revoked` 数组就是 `revoked.json` 的内容。台账没有这样的第二来源。

## 5. 签发节点证书（K-2：7 天窗口之后）

**前提**：内测舰队的 7 天长跑窗口已经结束（2026-10-03T18:20:23Z），并且已经按长跑的收取流程收完。窗口内任何重启生产节点、改生产名册的动作，都会让长跑计时作废（§12.1）。签发对象是 `key-distribution.md` §12.1 K-2 行里的三个内测节点。

| 步 | 在哪 | 做什么 |
|---|---|---|
| 1 | **节点上** | 用节点实际的配置根运行 `qm cert request --node <节点> --host <对端实际拨号的地址>`。重跑会换掉演练时生成的 EC 私钥和 CSR，但**不会动 Ed25519 身份**，这正是 §6.2「每次重签用新 EC 密钥」要的结果。`--host` 必须覆盖对端实际拨的那个地址（F-9）：当前舰队数据面走隧道口，所以演练时签的是回环地址；拓扑一变，就按新的拨号地址签。命令会打印出现成的 `qm ca issue …` 整行 |
| 2 | 节点 → CA 机器 | 只带走 CSR 文件和第 1 步打印的 `--pop`、`--nodekey` 两个值，都不是机密。**EC 私钥留在节点上，不拷走** |
| 3 | **CA 机器** | `qm ca issue <节点> --csr <CSR 文件> --pop <签名> --nodekey <公钥> --host <地址> [--ca-dir <CA 目录>]`。这个节点在本 CA 下签过（`issued/<节点>.crt` 已存在，季度重签就是这种情况），要加 `--replace`，否则直接拒绝。`--out` 指向已存在的文件同样要 `--replace`；指向 CA 目录里面一律拒绝。被拒就是什么都没签：工具依次检查 CSR 自签名、密钥是不是 EC（F-5）、PoP（§4.3）、台账能否读通、是否会覆盖已有文件，签完还会把 SAN 读回来，并对根证书验一次签名 |
| 4 | CA 机器 | **核对签发台账**。工具已在写证书文件之前把这张证书追加进 `<CA 目录>/issued-ledger.jsonl`，输出里的 `ledger` 一行就是它的路径，`replaced` 一行是被替换那张的指纹。`qm ca ledger --node <节点> [--ca-dir <CA 目录>]` 列出这个节点签过的全部证书，含已被替换的。要吊销一张更早、还没过期的证书时，指纹从这里取；泄露排查时，它是判断「注册中心里有没有我没签过的证书」的依据（§6.3）。在台账出现之前签过、之后又被 `--replace` 替换的证书，替换时会以 `(imported)` 补记一行，签发时间取它的 `notBefore` |
| 5 | CA 机器 | 交付前自检：`openssl verify -CAfile <CA 目录>/ca.crt <CA 目录>/issued/<节点>.crt`；`openssl x509 -in <CA 目录>/issued/<节点>.crt -noout -ext subjectAltName`，确认三类 SAN 都在：`DNS:`/`IP:`、`URI:qianmo://<节点>`、`URI:qianmo-nodekey:<公钥>` |
| 6 | CA 机器 → 节点 | 证书拷到第 1 步输出里给的路径（`<配置根>/qianmo/identity/<节点>.tls.crt`）；`ca.crt` 拷到 `<配置根>/qianmo/trust/ca.pem`，**替换掉演练 CA 的那份**。然后**在节点上**按 §1 的核对方法比对指纹，对不上就停 |
| 7 | 节点 | 带证书重启，参数见下面的注意事项 |

**第 7 步的三条注意事项**（K-2 动手前先定方案，本手册不替 K-2 做决定）：

- **尾参会整份替换**。经 `beta-up.sh --role node --node <节点> -- <参数…>` 重启时，`--` 后面的参数会**覆盖**记录在 `state/<节点>.passthrough` 里的整份尾参（`demo/env/beta/README.md`「节点腿的尾参」）。所以要先读出现有的尾参，把新参数**追加**进去，再整体传。2026-08-26 就出过事：重启时漏了 `--trust`，节点表面一切正常，实际策略已经降级。
- **三件齐了就开 mTLS**。`--trust-ca`、`--cert`、`--key` 同时给、并且监听的是 TCP 时，监听方会开 mTLS（F-10 三件套），从此不出示客户端证书的拨号方会在 TLS 层被拒。控制台对话面、`resident-wake`、`watch` 构造传输客户端时**都不带客户端证书**（`consoleChat.ts` / `residentWake.ts` / `watch.ts`；K-3 行也写过 CLI 里没有会出示证书的 qianmo 客户端）。所以对一台还要被这些入口拨的节点，一次给齐三件，就等于切断这些入口。
- **只给 `--cert --key` 也有意义**：启动时仍会拿本机身份核对证书（`assertOwnCertificateAndKey`：节点名、公钥、证书与私钥是否成对），监听保持明文 ws://，并在 stderr 上明说。代价是不再核「证书是不是这个 CA 签的」，这一步要在节点上手工补：`openssl verify -CAfile <配置根>/qianmo/trust/ca.pem <配置根>/qianmo/identity/<节点>.tls.crt`。

另外两件 K-2 相关的事实：
- 注册中心 `certificate` 字段的登记：控制台的 registrations 文件目前只收 `publicKey`，不收 `certificate`（`src/cli/handlers/consoleRegistrations.ts`）。要登记证书，目前只能直接 `POST /v0/agents`。
- 监听方只在启动时读一次证书（K-7 行：`buildListenerTls`），换证书必须重启才生效。

## 6. 吊销清单、轮换与泄露处置

### 6.1 重签并发布 RL（`refresh-rl`）

| 情形 | 命令（在 CA 机器上） |
|---|---|
| 例行重签（每月一次；`nextUpdate` = 30 天，§6.2） | `qm ca refresh-rl [--ca-dir <CA 目录>]` |
| 吊销（**当场**做，不等月底） | `qm ca refresh-rl --revoke <节点>=<fingerprint256> --reason "<原因>"`（`--revoke` 可以重复给，冒号可省；已经吊销过的指纹再加一次不会重复记） |

**发布**：把 `<CA 目录>/revocation-list.json` 的内容原样 `PUT` 到注册中心的 `/v0/revocation-list`，例如 `curl -fsS -X PUT -H 'content-type: application/json' --data-binary @revocation-list.json <注册中心地址>/v0/revocation-list`。注册中心只监听回环，所以要在注册中心所在的机器上发，或者经 SSH 隧道发。注册中心不验签名，只查结构；签名由每个节点自己验（§5.2）。

**三条容易踩的**：

1. **注册中心不持久化 RL**，只持久化 agents 表（`packages/registry/src/registry.ts` 的 `#persist`）。注册中心每次重启后都要**重新 PUT 最新那份**。不重发的话，节点拉到 404 会继续用内存里的缓存；但注册中心重启之后才启动的节点手里没有缓存，会按「从没发布过」处理，退回只认 `--trust`（§6.4）。
2. **节点端的 RL 状态只增不减**。`issuedAt` 更早的清单会被拒，同一 `issuedAt` 但内容不同的会被拒，删掉已有条目的也会被拒（§6.4 末段）。所以不要发布旧清单，也不要想着「撤销一次吊销」：吊错了，就给那个节点签一张新证书，新证书指纹不同。换根后新根签的第一份清单同样受这条约束，见 §6.2 第 5 步。
3. **过了 `nextUpdate`，节点会 fail-closed 到 `--trust`**，不是全放行，也不是全断网（§6.4）。开了 `--trust-ca` 的控制台会在证书栏页头显示 RL 的签发时间和剩余时间，过期时变红，没发布过时显示「未发布」（`packages/console/src/view/certificates.ts`，§10.1）。例行重签要赶在到期**之前**做。

吊销只对经 CA 认证的链路有效：如果同一把公钥还钉在某个节点的 `--trust` 里，那条链路不受 RL 影响。停用一个节点时，要**同时**移除它在各节点上的 `--trust` 条目（§6.4）。

### 6.2 轮换

| 材料 | 节奏 | 做法 |
|---|---|---|
| 节点证书 | 90 天；每季度批量重签，新节点随到随签（§6.2）。控制台证书栏分四档：剩余 21 天及以上「有效」；不到 21 天「将到期」（黄）；不到 7 天「7 天内到期」（红）；过了 `notAfter`「已过期」（红，时间栏改显示到期时刻）。门限在 `consolePorts.ts` 的 `CERTIFICATE_EXPIRING_MS` / `CERTIFICATE_URGENT_MS` | 重走 §5 第 1~7 步，第 3 步加 `--replace`。每次都生成新的 EC 私钥，Ed25519 身份不变 |
| 根证书 | 每 3 年主动换（下一次约在 2029-09），10 年兜底。开了 `--trust-ca` 的控制台在证书栏页头为信任文件里的每张根各显示一条，四档与节点证书相同：有效 / 将到期（黄）/ 7 天内到期（红）/ 已过期（红）。根不经注册中心，注册中心不可达时照常显示 | 见下面的换根步骤 |
| 节点 Ed25519 身份 | **不轮换**（§6.5） | 身份泄露就作废这个身份，见 §6.3 |

**换根步骤**（§3.3 的 90 天重叠）：

1. **建新根**：`qm ca init --ca-dir <新目录>`。新目录不会覆盖旧目录。**新根必须和旧根不同名**：节点的 `--trust-ca` 文件里两张根同名会被整体拒绝，原因是 TLS 层按名字挑签发者，同名时叶证书不带 AKI 就会挑错根（Bun 1.3.13 实测，由 `residentRootOverlap.test.ts` 钉住）。默认 CN 是 `qianmo-ca-<UTC yyyymmdd>`（建根当天），现网生产根是 `CN=qianmo-ca`，所以不加 `--cn` 就已经不同名。要自定名字就加 `--cn`，同样不能与旧根相同。同一 UTC 日在两个目录各建一张根时，默认名会相同，这时要给其中一张加 `--cn`。
2. **新指纹入手册**：写进本手册的新版本，旧根标「退役中」。
3. **分发两张根**：每个节点和控制台的 `trust/ca.pem` 换成「旧根 + 新根」两段 PEM 直接拼接（`cat <旧>/ca.crt <新>/ca.crt > ca.pem`），用 §1 末尾那条逐张打印的命令核对两张根的指纹，然后重启。文件里只能有 PEM 证书块和空白；夹注释、夹私钥、有一块读不通、不是自签的 Ed25519 CA 证书、同一张根出现两次，节点和控制台都会拒绝启动，不会跳过坏的那块继续跑。多根支持是本手册 v1.1 这一轮加的，v2.46.3 及更早的版本证书目录只读文件里的第一张根，所以做这一步之前，节点和控制台要先升到包含它的版本。
4. **用新根重签全部节点证书**：走 §5，`--ca-dir <新目录>`。新目录下还没有 `issued/` 副本，第一次不需要 `--replace`。重叠期内新旧根签的证书同时有效。
5. **换 RL 签发根**：重叠期内两张根都能签 RL，节点接受任一张在期的根签的清单。改由新根签时运行 `qm ca refresh-rl --ca-dir <新目录> --import-from <旧目录>`，然后按 §6.1 发布。这条命令先把旧目录 `revoked.json` 里的条目按指纹并进新目录，节点、原因、吊销时间都原样保留，新目录已有的条目不会被覆盖，重复执行也不会重复记；然后用新根签名。输出里 `imported` 一行是这次并进来的条数。
   **为什么必须带上**：节点端的 RL 状态只增不减（§6.4）。新根的第一份清单只要少了旧根发布过的任何一条，节点就整份拒收，新根自己的吊销也一起不生效；旧清单过了 `nextUpdate`，节点退回 `--trust`。不要用 `cp` 覆盖 `revoked.json`：新目录在重叠期里自己吊销过的条目会被抹掉，结果同样被拒收。
   从这一步起，吊销和例行重签都只在新目录做。如果旧目录在这之后又吊销过，再跑一次同一条命令补上。
6. **重叠期结束**：确认每个节点都已换上新根签的证书并重启过（新目录的 `qm ca ledger` 覆盖全部节点），RL 已由新根签发，然后把 `trust/ca.pem` 换回只有新根的一份，再重启。此后旧根签的证书在证书目录和 TLS 层都被拒，旧根签的 RL 也不再被接受。

行为由用例钉住：
- `src/cli/handlers/__tests__/residentRootOverlap.test.ts`：两张根并存时新旧两根签的叶证书在证书目录和 TLS 层都被接受，移除旧根后旧叶在两层都被拒；文件里有坏块时证书目录、自检、TLS、控制台四处都拒绝启动；新根签的清单不带旧条目时节点拒收，带上后接受且新吊销生效。
- `src/services/qianmo/__tests__/trustAnchors.test.ts`：文件格式的每一条拒绝。
- `src/services/qianmo/ca/__tests__/ca.test.ts`：`--import-from` 后旧条目全部在新根签的清单里，重复导入不变，指错目录时在写入之前拒绝；默认 CN 按 UTC 日期取。
- `src/cli/handlers/__tests__/certificatePort.test.ts`：根的四档用 `ManualClock` 逐档走一遍。

TLS 层的拒绝在拨号方观测：Bun 1.3.13 的监听方不校验客户端证书链（`packages/transport/test/mtls.test.ts`）。

### 6.3 疑似泄露时的处置

**CA 私钥疑似泄露**（§11 T-E：整网身份的单点）：

1. 立刻停止用这把根签任何东西。如果怀疑是 CA 所在的工作机本身失陷，先让这台机器断网。
2. **RL 救不了这种情况**：攻击者手里同样有签 RL 的钥匙。真正把旧根的信任撤掉的动作是：先确认每个节点的 `--trust` 里都有它要信任的对端，然后在全部节点上去掉 `--trust-ca`（连同 `--registry-url`）再重启，全网退回显式 `--trust`（§3.3 的 (b) 形态）。
3. 在干净的环境里用**新目录**建新根，新指纹写进本手册（版本号 +1，旧指纹标「作废」，不删），带外重新分发 `ca.pem`，重签全部节点证书。
4. 拿注册中心里现存的证书和签发台账（§5 第 4 步，`qm ca ledger`）逐一比对指纹，找出可疑的证书。**这种情况下台账只作排查参考，不能当判据**：它和私钥放在同一个目录里，拿到私钥的人也能改它，比如删掉自己签的那几行。权威依据有两样：
   - 离线备份（§4）里的台账和 `revoked.json`，并且只认怀疑的暴露窗口之前做的那一份。备份之后新增的台账行要逐条确认是自己签的。
   - 节点侧已经持有的吊销状态。节点只接受条目不减的清单（§6.4），所以泄露之前已经下发到节点的吊销，攻击者拿着私钥也签不出能让节点删掉它们的清单。这层保证只对之后没有重启过的节点成立，第 2 步的重启也算：节点的 RL 状态只在内存里，重启后接受注册中心上当时那份验得过签名的清单，去掉 `--trust-ca` 之后则不再持有。
5. 另外记一份事件记录（时间、怀疑的暴露窗口、做了什么）。这份记录不进公开仓库。

**CA 私钥丢失**（不是泄露）：现有证书在到期前照常有效，但签不出新证书，也签不出 RL。用 `--trust` 撑住，同时按第 3 步建新根（§3.3）。§4 的离线备份就是为了不走到这一步。

**节点私钥泄露**（Ed25519 身份或 TLS 私钥）：按 §6.5 的四步做。先 `refresh-rl --revoke <节点>=<该节点证书的指纹>` 并**立即**发布；同时移除各节点上它的 `--trust` 条目；然后在那台机器上删掉 identity 重新生成；最后默认**换一个新的 `node` 段**重新入网。
