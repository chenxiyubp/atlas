## §0 结论摘要

**本版仍然不给结论，只给边界。**v0.1 列了四条，v0.2 加第五条（架构栏）。它们不是免责，
是读这份报告时必须先装进脑子的五件事；数据填进来之后，每一条结论都要在这五条边界之内成立。

栏 B 的吞吐数据（§4.6）已经可以引用，但**只能连同「1 vCPU / aarch64 / 无沙箱」一起引用**。

> **v0.3 注**：栏 A 的吞吐四轮（§4.0 ~ §4.5）与 t=0 唤醒阶梯（§3.1）已实测，同样规则——
> 引用必须带「4 vCPU / x86_64 / GCP 网络盘」这一栏。可以跨栏说的那两类（`LIMITS` 行为与
> 形状）本版拿到了双栏证据：天花板公式、按节点计的 3.00×、T1 拐点信号位置，两栏逐条一致。

### ① 长跑证明的是「至少跑了这么久」，而本次**没有跑满 24 h**

DoD 写的是「连续运行 24 h」。实际按负责人 2026-08-17 决议**提前停机**：栏 B 跑了
**22.13 h**、栏 A 跑了 **3.53 h**（计划内中断，§6.2；停机前判据全过、探针应答）。
所以本文能说的最强的话是：「在栏 B 那台机器上、L0 负载下，**连续 22.13 h** 内六条
稳定判据全部成立」——**不是** 24 h，更不是「可以稳定长期运行」。引用时如实带跨度。

真正能外推的不是「跑了多久」，而是**斜率**（§2.3）：栏 B 22 h 的堆曲线全程最小二乘
斜率 **+0.11 MB/h** 且 12 ~ 18 h 段为**负**（§5.5）——这条「不单调上涨」的形状，比
再多跑两小时更能说明问题；这也是决议判「已经可以了」在数据上站得住的原因。

### ② 吞吐数字**只有 T3 那一列**可以对外说

阶梯跑三个配置（§2.2）。T1 裸传输、T2 加路由、T3 生产形态。**只有 T3 是会真的被运行的
配置**，另外两个存在的意义是解释 T3 为什么是那个数字。

拿 T1 的数字对外，宣传的是一个没有审计、没有限流、没有人会部署的配置。这句话写在这里是
因为 T1 的数字必然最好看，而好看的数字会自己长脚。

> **v0.2 补一句**：栏 B 跑完之后 T1 多了一个用途，但**仍然不是对外的那个数字**。它是
> **对照组**——T1 在 400 档把四万八千条全投出去毫无压力，这一条把「T2 / T3 在同档崩塌」
> 从「1 vCPU 机器不行」里摘了出去（§4.6.3 ③）。**对照组的数字用来排除解释，不用来宣传。**

### ③ ACP 子进程**只有 RSS**，JS 堆未测得

常驻节点是父子两个进程。父进程（`occ resident`）的 JS 堆由 `--mem-sample` 从进程内采到；
**ACP 子进程的 JS 堆两条通道都拿不到**——进程内通道进不去它，`/proc` 通道看不见 JS 堆。

后果要说清楚：如果泄漏发生在子进程的 JS 堆里，这份基线**只能看到它的 RSS 在涨**，说不出
涨在哪儿。缺口登记在 §8。

### ④ n=100 的 **P95 是真分位数，P99 不是**

唤醒延迟采 n=100（理由见 §2.1）。最近秩（nearest-rank）下 n=100 的 P95 落在第 95 个样本上，
前后各有样本，是一个真的分位数。**P99 落在第 99 个样本，也就是倒数第二大**——它离最大值
只有一个样本的距离，形状上更接近 max 而不是分位数。

**所以这份报告不报 P99。**要报尾部就报 max，并说明它是 max。

### ⑤ **每一个数字都属于它那一栏**（v0.2 新增）

从 v0.2 起数据分两栏（§1.2）。**引用时必须带栏。**「阡陌的 T3 吞吐是 X」这句话不成立，
成立的只有「在栏 B 那台 1 vCPU aarch64 机器上、120 s 的档里，T3 的 X」。

有两类东西可以跨栏说，也只有这两类：

- **由 `LIMITS` 决定的**：限流在哪一档首现、桶公式 `B·(1/T+1/60)` 对不对得上、
  多身份是不是线性抬升。这些是协议行为，换机器不换。
- **形状**：曲线是平的还是涨的、拐点在不在预测位置。

不能跨栏说的：任何 msg/s、任何毫秒、任何 MB。**它们是这台机器的属性，不是系统的属性。**

### 1.5 本地 macOS 跑批**只做仪器校准，数据不入表**

开发机（macOS / arm64）上跑过全部三个采集器，目的**只有一个**：验证仪器本身没坏——
计数对得上、阶梯真的分了档、两条内存曲线在有背景分配时真的会动。

**这些数字一律不进 §3 ~ §6。**理由是硬的，不是谨慎：

- **没有 `/proc`**。`p73-sample.ts` 在 macOS 上退到 `ps -o rss=`，**采不到 `VmHWM`、
  `smaps_rollup` 的 `Pss`、以及整个 cgroup 通道**。判读因此把带 `ps` 通道的数据集直接判为
  不可用（`p73-report-core.ts` 的 `memoryChannelsIntact`）——这条检查就是为了防止校准数据
  在某次复制粘贴中混进正式表。
- **没有 Dormice、没有 gVisor**，因此**唤醒延迟在 macOS 上根本没有可测对象**（§8 缺口三）。
- 核数、内存带宽、文件系统与真机都不同，吞吐拐点的位置不可比。

校准跑的实测数字另附在 P7.3 的实施记录里，**不在本文**——放进来就迟早会被当成基线引用。

**一处例外，说明清楚**：§2.2 引了校准跑的一个具体数字（100 msg/s 档的 delivered=550）。
它出现在那里的身份是**「这条方法为什么要这样定」的证据**，不是基线数据——正式表里
不会有它，M1 也不该拿它跟任何东西比。凡是这样引用校准数字的地方都必须像这里一样
点名它是校准跑。

### 1.6 栏 B（aarch64）的数据**是正式数据**，与 §1.5 的校准跑不是一回事

容易混淆，所以写死：**开发机 macOS 的跑批是校准，降级机 aarch64 的跑批是正式数据。**
两者的分界不在「是不是主力验收机」，而在**仪器有没有降级**——这条线由机器判，不由人判：

| | macOS 开发机（§1.5） | aarch64 降级机（栏 B） | x86_64 验收机（栏 A） |
| --- | --- | --- | --- |
| `/proc` + `smaps_rollup` | ✗ 退到 `ps` | ✅ | ✅ |
| cgroup v2 三个文件 | ✗ 没有 | ✅（`memory.current` / `peak` / `events` 全读到） | ✅ |
| `p73-report-core.ts` 的 `memoryChannelsIntact` | **false** → `pass=false` | **true** | 预期 true |
| Dormice / gVisor | ✗ | ✗ | ✅ |
| 结论 | 只做校准 | **§4 / §5 / §6 入正式表；§3 仍测不了** | 三块全可测 |

也就是说，栏 B 唯一缺的是**沙箱**那一格，缺它只影响 §3；采样通道这一格是完整的，
所以 §5 / §6 的数字**不是**「凑合的本地数字」，它们过了机器强制的那道门（v2.34 ⑤
把「本地数据不进正式表」做成 `memoryChannelsIntact`，它挡的是降级通道，不是非 x86 机器）。

**栏 B 不能替栏 A 回答的问题**：1 vCPU 上的吞吐拐点位置、有沙箱时的唤醒延迟、
15 Gi 内存 + swap 下的长跑水位。这三样必须等栏 A。

## §2 测量方法

### 2.0 为什么方法先定稿

因为方法里的每一条都是**判读规则**，而判读规则必须在看到数据之前定下来。一条「p95 涨得
比档位快就算拐点」的规则，在看过数据之后再定，定出来的一定是让当天那批数据好看的那条。

### 2.1 唤醒延迟：样本数从 n=10 提到 **n=100**

AC-2 的验收跑 n=10（roadmap v2.20）。基线不能沿用这个样本数，理由是一条算术事实：

**`statsOf` 用最近秩分位数**（`packages/activator/src/stages.ts`）：
`rank = ceil(0.95 × n)`，取排序后第 `rank` 个样本。

- **n=10** → `rank = ceil(9.5) = 10` → **P95 恒等于 max**。v2.20 的验收记录里那句「P95 等于
  max 是因为十个样本的 p95 就落在最大值上」说的正是这件事。作为验收判据它没问题（判的是
  「每一轮都在 60 s 内」，取 max 反而更严）；**作为分布描述它一个分位数都没给出**。
- **n=100** → `rank = 95` → 第 95 个样本，前有 94 个后有 5 个，是真的 P95（§0 ④）。

**两次阶梯：t=0 与 t=24 h 各跑一遍 n=100。**

这一对不是为了「多测一次更保险」，它回答的是一个具体问题——**E2 的外推**。
`selection-m0.md` §3 的 E2 实测了 400 MiB 工作集换回需 9.0 ~ 10.2 s，并明确记下
「**E2 只测了 400 MiB 一个工作集点位，更大工作集的耗时是线性外推，未实测**」。

常驻节点跑满 24 h 之后工作集会比 t=0 大。**t=24 h 的那次阶梯就是在那个更大的工作集上重测
唤醒延迟**——两次的差值，是 E2 那条线性外推第一次拿到实测对照。

E2 同时记了一个**永久回归**（稳态 29 ~ 31 ms → 36 ~ 40 ms，+25%，此后不再劣化）。
两次阶梯的对比要把它算进去：t=24 h 更慢**不一定**是工作集变大，也可能是这个已知的一次性回归。

### 2.2 吞吐：三个配置、八档、**三道天花板要分清**

**配置**（`demo/lib/p73-throughput.ts`）：

| 配置 | 组成 | 回答的问题 |
| --- | --- | --- |
| T1 | `startTransportServer` + `onMessage` | 传输层本身的天花板 |
| T2 | T1 + `NodeRouter`（`InboundBudget` 生效） | 协议层预算从哪儿开始起作用 |
| T3 | T2 + 审计 trail 落盘 | **对外能承诺的那个数字**（§0 ②） |

**档位**：1 / 5 / 10 / 25 / 50 / 100 / 200 / 400 msg/s，每档 120 s，**档间静默 65 s**。

静默要同时满足两个条件，少一个档与档之间就不独立：

1. **> `LIMITS.defaultTtlMs`** —— 让去重表泄空。不然第 N 档测到的是第 N-1 档留下的表长，
   阶梯就不再是阶梯。
2. **≥ 60 s** —— 让入站预算的桶**重新填满**。这一条是本地校准跑当场撞出来的（§1.5）：
   35 s 静默只回补 `(B/60)·35` 个令牌，于是 50 msg/s 那档把桶抽干之后，100 msg/s 那档
   **带着一只半空的桶**开跑。实测该档 delivered=550，正好是「静默回补 350 + 本档 20 s 内
   回补 200」，而不是满桶推导的 800。桶从空到满恰好一个窗口（60 s），所以取 65 s。

**这条差点让正式跑批产出一张自相矛盾的表**：撞过预算的档位会压低它后面每一档的天花板，
而表上看起来像是「系统在高档位表现更差」。记在这里是因为下一个人一定会想把静默调短。

**计数走两个来源交叉核对**：发送端数回执，盘上审计数 `message_accepted`。对不上就说明有
一边在说谎，这一档的数字不能引用。T1 没有审计，如实记单来源。

**计数一律走 events sink 自累加，不读 `EventRecorder`**——它是 256 条的环
（`packages/transport/src/events.ts`），400 msg/s 跑 120 s 有四万多条事件，
`byType(...).length` 读出来的是「环里还剩几条」，而它长得非常像总数。

#### 三道天花板

**① 协议层入站预算——设计值，不是缺陷。**

`LIMITS.ratePerMinute`，**唯一出处是 `packages/protocol/src/limits.ts`**（CLAUDE.md §2.2）。
本文不复制它的数值，下面的推导用符号 **B**（每分钟条数）表示。按**发送节点**计。
撞上它的档位判为 `budget`。要记住两件事：

- 它是**每节点**的。多个发送身份并行时总吞吐应线性抬升——`--senders` 就是用来验这件事的；
  抬不上去说明限流粒度和文档写的不是一回事。
- **桶是满的起步。**`InboundBudget` 建桶即满（`packages/router/src/rate.ts` 的 `TokenBucket`），
  于是一段长 **T 秒**的档位总共能用的令牌是 `B + (B/60)·T`，**可持续速率上限**是

  ```
  R_max(T) = (B + (B/60)·T) / T = B·(1/T + 1/60)
  ```

  它随 T 单调下降 —— **一档跑得越短，越晚看到 `rate_limited`**。所以
  **「20 s 的档在某速率下没触发限流」不等于「没有限流」**，它等于「这一档的消息总数还没
  花光初始令牌」。判读时先把 `R_max(T)` 算出来再下结论；正式跑批的 T=120 s 与校准跑的
  T=20 s 得到的是两条不同的线。

**② 每条 fsync——刻意的耐久取舍，不是性能缺陷。**

`AuditTrail.append` 每写一条就 `fsyncSync`，注释写着理由：「Per record, not per batch: the
lines that matter most are the ones written just before something went wrong.」
（`packages/audit/src/trail.ts`）

这是 T3 与 T2 之间差距的主要来源。**它是被选择的**：崩溃前最后那几行才是最有用的几行，
批量刷盘正好会丢掉它们。所以 T3 的吞吐低于 T2 是**预期结果**，报告要写的是低多少，
不是「发现了一个性能问题」。

**③ 去重表全表扫描——已知的 O(N)，拐点预测在 R ≈ 333/s。**

`DedupTable.admit` 每次都先 `pruneExpired`，而 `pruneExpired` 遍历**整张** `byMsgId`
（`packages/transport/src/dedup.ts`）。表项在信封自己的投递时限到期，该时限默认取
`LIMITS.defaultTtlMs`（同样**只在 `limits.ts` 里有值**，这里记作 **D 秒**）。于是：

- 稳态表长 ≈ 速率 × D = **D·R**
- 每秒扫描代价 ≈ R 次 admit × D·R 次遍历 = **D·R²**

代入本仓库当前的 D，令这笔代价与每条消息的其它固定成本相当，**拐点预测落在 R ≈ 333/s
附近**。这是一个**推导值**，不是限额——**八档的最后两档取 200 与 400，就是为了把它夹在
中间**。D 若在 M1 变动，这个预测要重算。

**档位时长必须超过 D，否则这道天花板根本测不到。**校准跑（§1.5）用 20 s 的档撞出来的：
档比 D 还短的话，一档跑完**一条表项都还没到期**——`pruneExpired` 照样每次遍历全表，但
表长只到 `R × 档长`，永远够不到稳态的 `D·R`。这样的阶梯**在方法上无法证伪拐点假设**，
跑出一片绿色只说明「在没达到稳态表长的前提下没看到拐点」。正式跑批的 120 s 档远大于 D，
才是有效的。`p73-throughput.ts` 在档长不满足这条时会在 stderr 上警告。

**观测到了也不修（N-12）。**记进 §7，M1 决定要不要动。判读规则（`p73-report-core.ts`）：
`rateLimited` 与 `outboxFull` **全为 0** 且 p95 涨得比档位还快，才记为拐点候选——
先排除另外两道天花板，剩下的才可能是这一道。

> **v0.2 补一条推论（不是改规则，是把规则的后果写明白）：这道天花板只能在 T1 上测到。**
>
> 判据要求 `rateLimited == 0`，而 T2 / T3 从超过 `R_max(T)` 的那一档起**每一档都在限流**。
> 于是阶梯上 25 及以上全部判 `budget`，`usableAsBaseline` 为假，后面的档连比较基线都没有——
> **`kneeAt` 在 T2 / T3 上恒为空，与去重表实际有没有拐点无关。**
>
> 这不是判读的缺陷：一档被限流之后，它的 p95 反映的是被节流后的负载，拿它谈拐点本来就
> 没有意义。但它意味着**「T3 没观测到拐点」这句话不能写成「T3 没有拐点」**——正确的说法是
> 「在 T3 上这道天花板被预算挡在了观测范围之外」。想在生产形态上测它，得先把预算这一层
> 挪开（临时抬高 B，或按 `--senders` 把负载摊到多个发送身份上），那是 M1 的事。

### 2.3 内存：五条要先讲清楚的事

**① `process.memoryUsage().heapUsed` 在 Bun 下是冻结常量，不许用。**

`docs/zh/memory-peak-analysis.md`「测量方法上的五个坑」第 1 条：Bun 1.3.13 下分配 5 万个
字符串前后都报 ~212 KB。**用它采 24 h，得到的是一条完美的平线和一个完全错误的结论。**

正解是 `bun:jsc` 的 `heapStats().heapSize`。这条钉在
`src/cli/handlers/resident.ts` 的 `ResidentMemSample` 注释里，别改回去。

**② RSS 是高水位线，不作判据。**

同一份文档：Bun/JSC **不归还内存页**。所以 RSS 只涨不跌，一条 24 h 单调上升的 RSS 曲线
**什么都不能证明**——它既可能是泄漏，也可能是一次正常的峰值之后页没还回去。

RSS 有它不可替代的用处（第 4 条坑：`heapSize` 完全不计大字符串的 backing store，
负载是字节数时只有 RSS 看得见），但它**只作为佐证，不作为判据**。

**③ 判别式是「GC 之后的 `heapSize` 斜率」。**

采样器**不触发 GC**（会改变被测对象，§2.4 也不许干预）。GC 检查点由跑批方在需要时手动
触发，机制不进这个任务包。判读时：

- 把采样序列按检查点切段，取每段 GC 之后的 `heapSize`；
- **这些点之间的斜率**才是泄漏与否的判别式；
- `heapCapacity` 与 `objectCount` 一起看：capacity 涨而 heapSize 平，是 JSC 留了空间不是泄漏；
  objectCount 单调涨则指向对象没被释放。

**④ `heapSize` 是**步进**的，单点采样会滞后——本地校准跑当场撞到的第六个坑。**

`memory-peak-analysis.md` 列了五个坑，这是第六个。对照实验（同一进程内三次采样）：

| 采样点 | `heapUsed` | `heapSize` | `heapCapacity` | `objectCount` | `rss` |
| --- | --- | --- | --- | --- | --- |
| 分配前 | 0.20 MB | 0.20 MB | 1.45 MB | 2,851 | 27.22 MB |
| 分配 30 万个小对象后 | **0.20 MB** | **0.20 MB** | 18.93 MB | **2,851** | 86.39 MB |
| 再分配 ~8 MB 字符串后 | **0.20 MB** | 52.13 MB | 53.27 MB | 611,909 | 105.55 MB |

两件事：

- **`heapUsed` 三次全等**（0.20 MB）。坑 1 复现无误，它就是不能用。
- **`heapSize` 与 `objectCount` 在第二个采样点纹丝不动**，而 `heapCapacity` 与 `rss` 已经
  涨了一大截。它们要到第三个采样点才一起跳上去。

操作上的结论：**`rss` 与 `heapCapacity` 是先行指标，`heapSize` 与 `objectCount` 是滞后
指标。**所以 §2.3 ③ 那条「判别式是 GC 检查点之间的 `heapSize` 斜率」不只是为了避开释放侧
噪声——**也是因为单点 `heapSize` 本身可能还没反映已经发生的分配**。24 h 曲线要按多点斜率
读，一两个采样点的持平说明不了任何事。

**⑤ 双进程要分开采，不能相加。**

| 通道 | 采什么 | 看不见什么 |
| --- | --- | --- |
| 进程内（`occ resident --mem-sample`） | 父进程 `rss` + `heapSize` / `heapCapacity` / `objectCount` | ACP 子进程；两次采样之间的峰值 |
| 外部（`demo/lib/p73-sample.ts`） | 父与子各自 `VmRSS` / `VmHWM` / `Pss` + cgroup `memory.current` / `peak` / `events` | 任何进程的 JS 堆 |

**两个进程的 RSS 不能直接相加**——父子共享大量页（`Pss` 就是为此采的，共享页按份额摊）。
要一个「这个节点占了多少」的单一数字，用 cgroup 的 `memory.current`，那是内核的口径。

### 2.4 长跑：三层负载 L0 / L1 / L2、六条稳定判据、中断分两类

#### 三层负载

| 层 | 负载 | 它要暴露什么 |
| --- | --- | --- |
| **L0** | 空载常驻，只有 keepalive 与 activity 上报 | 「什么都不干」的漂移。这一层涨了，涨的是常驻机制本身 |
| **L1** | 稳定低速消息（~1 msg/s），不进 ACP | 传输 + 路由 + 审计三条路径的每条消息残留 |
| **L2** | 周期性真 ACP turn（含休眠 / 唤醒穿插） | 完整链路，也是唯一会碰到会话状态与工作集换回的一层 |

分三层而不是只跑最重的那层，是为了**在出问题时还能定位**：只跑 L2 的话，一条上涨的曲线
说不出是常驻机制、消息路径还是会话状态在涨。

#### 六条稳定判据

1. **进程存活**：父进程 24 h 无重启（PID 不变）。
2. **ACP 子进程存活**：重启次数记录在案；重启不必然判红（监督机制本来就该拉起它），
   但**必须有数**——一个每小时重启一次的节点和一个从没重启的节点不是同一个基线。
3. **堆斜率**：GC 检查点之间的 `heapSize` 斜率不持续为正（§2.3 ③）。
4. **无 OOM**：cgroup `memory.events` 的 `oom_kill` 在全程为 0。
5. **审计链完好**：`readTrail(...).intact === true`。
6. **功能仍在**：24 h 末尾重跑一次 L2 的最小闭环并成功——**「没崩」不等于「还能干活」**，
   一个静默停摆的节点在前五条判据上全绿。

#### 中断分两类，记录方式不同

- **计划内中断**（GC 检查点、t=24 h 的唤醒阶梯、手动取样）：记时间点与动作，曲线上标注，
  **不算中断**。
- **计划外中断**（进程退出、机器重启、采样器被杀、网络断）：**中断即数据集分段**。
  分段之后不许把两段接起来当一条 24 h 曲线——续采文件里两段首尾相接，但那是文件连续，
  不是**运行**连续。`p73-report-core.ts` 的断档检查把这种情况标成 gap 区间，就是为了让它
  在报告里显形而不是被平均掉。

### 2.5 栏 B 特有的四个坑（ARM / 无 root / 1 vCPU / 无 swap）

方法节其余各条与架构无关。这一节只记**在降级机上跑才会撞到、而在验收机上不会**的东西，
它们全都能让一份数据静默失真。

**① cgroup 通道默认量错对象——它量的是整个 ssh 会话。**

非 root 用户起的进程落在 `/user.slice/user-<uid>.slice/session-<n>.scope` 里，那个 cgroup
**同时装着 sshd、登录 shell 以及你在同一次登录里跑的任何别的东西**。于是
`memory.current` 读出来是「这次登录一共占了多少」，不是「这个节点占了多少」，而 §2.3 ⑤
恰恰说了要用它当那个「单一数字」。

处置：把被测节点放进 `systemd-run --user` 的**瞬态单元**里，它自带一个只有这个节点父子
两个进程的 cgroup。**采样器不要放进同一个单元**——它读的是目标 pid 的 cgroup，自己进去
只会把自己的 RSS 也算进被测数字。

配套的两条，缺一条会在几小时后才发作：

- **`loginctl enable-linger`**。不开的话，最后一个 ssh 会话断开时 `user@<uid>.service`
  停机，**连带把瞬态单元一起带走**——24 h 长跑会在你登出后的某一刻无声结束。
- **单元脚本用 `exec`**。这样单元的 `MainPID` 就是被测进程本身，而不是外层 shell。
  §9.2 那个「`--resident-pid` 传了外层启动壳」的坑在这里是**结构性消解**的，不是靠人核对。

**② 1 vCPU 上，吞吐阶梯量的是「单核上收发各半」。**

`p73-throughput.ts` 的发送端与接收端在**同一个进程**里（unix socket 自环）。在 4 vCPU 上
它们各占一部分核；在 1 vCPU 上它们**互相抢同一颗核**，再加上补齐循环每毫秒醒一次。
所以栏 B 的 achieved 与 p95 里含着一份调度开销，**它是这台机器的天花板，不是协议的**。
两栏之间比绝对值没有意义，能比的是**形状**：限流在哪一档首现、拐点在不在预测位置、
三节点是不是线性抬升——这些由 `LIMITS` 与算法决定，不由核数决定。

**③ 无 swap：逼近内存就是 OOM，不会先变慢。**

栏 A 有 13 Gi swap，内存压力先表现为换页与变慢，曲线上看得见、还有时间反应。栏 B 没有
swap，`memory.current` 逼近物理内存的下一步直接是 `oom_kill`——**判据 4 从「有没有踩线」
变成「数据集还在不在」**。24 h 长跑因此要留足余量（本次 L0 的水位见 §5.5），并且
`memory.events` 的 `oom_kill` 必须逐次采、不能只在收尾读一次——
`p73-sample.ts` 本来就是每轮都读，这条不需要额外做什么，需要的是**别只看收尾那一条**。

**④ 没有 sudo，所以整条链路都在用户态。**

装 bun 走官方安装器装进家目录，构建产物、配置根、审计链、采样文件全在家目录下。
好处是不碰系统；代价是**任何需要 root 的观测都不在这份数据里**（perf、eBPF、
`/proc/sys` 调参、以及需要守护进程权限的 docker）。§8.6 记了这条的后果。

### 3.1 栏 A · t=0 阶梯（2026-08-17T01:00 ~ 02:38Z，n=100，**100/100 responsive，`pass=true`**）

跑法：P4.1 现场链路（常驻 occ + 模型桩在 Dormice/gVisor 沙箱内），**每轮先等沙箱真冻结**
（静默 20 s 后由活跃度自动冻结，驱动确认 `frozen` 才发下一条），一轮约 58 s，与 §6.5 的
L0 长跑并行（方法允许：吞吐阶梯才要求独占，见 §2.2 静默条款；长跑是空载，两者不共享进程）。
产物 `~/p73/p31-t0/p31-resident.mFOvWA/`（`report.json` + `audit.jsonl` +
`resident-timings.jsonl` + `activator-timings.jsonl`，每轮另有 `round-N.json`）。

阶段名按量具实测的时间戳链（`stages.ts` 的口径）如实给，**不再用模板里的
「`unpause` 系统调用」行**——本驱动不单独掐 `unpause` 那一刀（E2 已单测过：46.6 ~ 55.5 ms），
它测的最细一段是「唤醒发起 → 就绪」，`unpause` 与工作集换回都在这一段里：

**T2 与 T3 一比，`AuditTrail` 每条 `fsync` 的代价直接读得出来**：

| | T2（无审计） | T3（有审计） | 差 |
| --- | --- | --- | --- |
| 1 / 5 / 10 档 p50 | 0 ~ 1 ms | 3 ms | **+2 ~ 3 ms / 条** |
| 1 / 5 / 10 档 p95 | 1 ms | 4 ms | +3 ms |
| 200 档 p95 | **1 ms** | **22 ms** | **×22** |
| 400 档 p50 / p95 | 508 / 3634 ms | 1864 / 4595 ms | 更差 |
| 400 档 attempted | 47800 | 47562 | 少排出 238 条 |

前两行是 §2.2 ② 说的那笔耐久开销，量级落在预期内。**第三行不是。**

**200 档那个 ×22 是被拒路径的代价，不是投递路径的。**两轮在这一档投递数完全相同
（都是 1799、都被预算钉死），差别只在 T3 **给每一条被拒的消息也写了审计**——
这一档有 22198 条被拒，约 185 条/秒，每条都要落盘 `fsync`。于是：

> **「被限流」在生产形态下不是免费的。**T2 里限流几乎零成本（拒了就拒了）；T3 里
> 每一次拒绝都是一次带 `fsync` 的追加写。一个被打满的节点，成本不落在 CPU 上，
> **落在存储上**——而这一层在 T1 / T2 上完全看不见。

这不是缺陷（审计要能还原「被拒的那几条去哪儿了」，见 P7.2 的映射约定），但它是一条
**必须写进容量估算**的事实：按被拒流量算 IOPS，不是按投递流量算。记进 §7 B-3。

#### 4.6.3 T1 裸传输

> **T1 是栏 B 上唯一有拐点判读力的一轮**（§2.2 ③ 的 v0.2 推论）：它没有路由层，
> `rateLimited` 恒为 0，`kneeAt` 的判据才是活的。但**有判读力不等于一定测得到**——
> 拐点预测在 R ≈ 333/s，而 1 vCPU 未必推得到那个速率。要是推不到，栏 B 的结论就是
> 「**没到那条线，所以没看见**」，与 T2/T3 的「被预算挡住」是两个不同的没看见。

结果是**推得到**：1 vCPU 上 T1 把八档一路跑满，400 档 47999 / 48000 条全部投递。

| 目标 msg/s | achieved | audit | dup | rejected | outboxFull | rateLimited | P50 ms | P95 ms | 判读 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 5 | 4.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 10 | 9.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 25 | 24.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 50 | 49.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 100 | 99.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 200 | 199.99 | — | 0 | 0 | 0 | 0 | 0 | 1 | linear |
| 400 | **399.97** | — | 0 | 0 | **0** | 0 | 1 | 4 | **knee** |

**① 裸传输在这台机器上到 400 msg/s 都没有排队。**七档 p50 = 0 ms、p95 = 1 ms、
`outboxFull` 全程 0、投递数逐档等于目标数减一。**1 vCPU 不是传输层的瓶颈**——
这一点很要紧，因为它把 §4.6.1 / §4.6.2 里 400 档的崩塌**从「机器不行」里摘了出去**
（见下面 ③）。

**② 拐点判据在 400 档触发了，但它是一个「弱阳性」，别当成实锤。**
`kneeAt = [{config:'T1', rate:400}]`：p95 从 1 ms 涨到 4 ms，而档位只涨了 2 倍，
超线性成立。预测值 R ≈ 333/s 正好落在 200 与 400 之间——**八档最后两档取 200 / 400
就是为了夹住它**（§2.2 ③），这一夹确实夹到了。

但要老实说清楚三件事：

- **绝对量级只有 3 ms**（1 → 4 ms）。
- **计时分辨率就是 1 ms**，`p50Ms` / `p95Ms` 都是整数毫秒。1 → 4 的比值在这个分辨率下
  很脆：真值可能是 1.4 → 3.6（2.6 倍，仍超线性）也可能是 0.6 → 4.4（7 倍）。
- **只有一个数据点**，没有跑批间方差（§8.4）。

所以结论只能写成：**「在栏 B 上，T1 的 400 档出现了与 `D·R²` 预测相符的超线性拐点信号，
量级 3 ms，需要栏 A 与重复跑批确认」**，不能写成「拐点在 400」。

**③ 400 档的对照是这一轮最有信息量的东西。**同一台机器、同一个档位、同样的 48000 条负载：

| | T1（裸传输） | T2（+路由） | T3（+审计） |
| --- | --- | --- | --- |
| 投递 | **47999** | 1800 | 1805 |
| 被拒 | 0 | 40547 | 25273 |
| `outboxFull` | **0** | 5453 | 20484 |
| p50 / p95 | **1 / 4 ms** | 508 / 3634 ms | 1864 / 4595 ms |

T1 把四万八千条**全投出去**都毫无压力，而 T2 在同样的负载下**只投了 1800 条**却把发送端
的 outbox 打爆、p50 涨到半秒。差别不在投递，在**拒绝**：T2 那一档要拒 40547 条，每一条都
走「路由判否 → `onMessage` 抛错 → 传输层记 `message_rejected` → 回一条带错误码的回执」。

> **「被限流」比「被投递」贵。**这句话反直觉，但这一档的三列数字就是它：投递 47999 条
> （T1）比拒绝 40547 条（T2）**便宜得多**。限流保护的是下游，**不保护节点自己**。

记进 §7 B-6。栏 A 上必须复测——如果 4 vCPU 上依旧如此，它就是一条真的容量结论。

#### 4.6.4 T2 多发送节点（`--senders 3`）

> **读这张表有一个陷阱，先说在前面。**「抬升倍数」不是每一档都该等于 3。

## §8 缺口

> 测不到的东西要单独列，不能靠「表里没有」暗示。一份不列缺口的报告，读者会默认没列的
> 都测过了。

### 8.1 ACP 子进程的 JS 堆**拿不到**

- **为什么**：进程内通道（`--mem-sample`）跑在父进程里，进不去子进程；外部 `/proc` 通道
  看得见 RSS 看不见 JS 堆。子进程本身没有采样出口。
- **后果**：泄漏若发生在子进程的 JS 堆里，本基线**只能看到它的 RSS 在涨**，说不出涨在哪儿。
- **要补需要什么**：给 ACP 子进程一个采样出口（它自己也是 Bun 进程，能用同一套 `bun:jsc`），
  属于改常驻宿主，**不在 M0 范围**。

### 8.2 两个私有观测字段没有覆盖

| 字段 | 位置 | 性质 | 为什么这份基线看不到 |
| --- | --- | --- | --- |
| `#jumps` | `packages/resident/src/deadline-clock.ts` | **无界**：每检测到一次时间跳跃追加一条，全程不裁剪 | 私有字段，无公开计数出口。24 h 里穿插休眠/唤醒的 L2 正是会往里加条目的负载，**而它增长到多少这份报告答不出** |
| `#integrityIssues` | `packages/resident/src/ledger.ts` | 单次 `#load()` 内有界（只在 `close()` 后重载才重置） | 同样私有、无出口。它不是增长风险，但「24 h 里 ledger 有没有出现损坏行」这个问题本报告**同样答不出** |

降级机上还多一层：docker 二进制在，但当前用户不在 `docker` 组、也没有 sudo，
`docker info` 直接被拒。**即使把 gVisor 装上也仍然要 root**，所以这条在这台机器上
不是「再装点东西就行」。

- **P99 不报**（§0 ④）。

### 8.5 栏 B 只有 L0 一层：**L1 与 L2 在没有模型桩的机器上测不了**

§2.4 的三层负载里，栏 B 只跑得了 L0。**这不是懒，是链路结构决定的**：

- **L2 要真 ACP turn，真 turn 要模型。**验收机上的模型桩跑在沙箱里
  （`demo/lib/p41-send.ts` 头注：「正文来自沙箱内的模型桩」）。降级机没有沙箱，
  也没有对外的模型凭据，L2 无从谈起。
- **L1 想「不进 ACP」，但常驻节点没有这样一条入站路径。**每条被接收的消息都先写进
  信箱（`InboundAdapter.deliver`），随后 `ResidentNodeRuntime.deliver` 会对该 agent
  `reader.poll()` 一次——**只要信箱里有未读，就会开一次 ACP turn**。所以「给常驻节点
  灌 1 msg/s 但不触发 ACP」在当前实现里不存在。
- **更要紧的是：拿「必然失败的 turn」当 L1 负载会测出一条假曲线。**turn 在准入回调
  之前就失败时，`ResidentMailboxReader.#submit` 走 reject 分支：消息**留在信箱里未读**，
  ledger 里留下一条只有 `detected` 没有 `admitted` 的记录。下一次 poll 先看
  `ledger.query().pending`，有待恢复项就**直接走恢复分支并返回**，根本不去读新消息
  （`reader.ts` 的 `if (queried.pending.length > 0) return`）。于是：信箱文件里的未读
  **只增不减**，而每来一条消息都要 `readAll` 一遍整个信箱——**每条消息的代价随信箱长度
  线性增长**。24 h 之后一定能画出一条漂亮的上涨曲线，可它描述的是「我们故意把模型拿走了」，
  不是常驻节点的内存行为。**宁可少一层，不要一层假的。**

后果：栏 B 的 §5 / §6 只回答「常驻机制本身在 24 h 里怎么走」（L0 的原话），
**答不了「每条消息留下了什么残留」（L1）与「完整链路会不会涨」（L2）**。这两层等栏 A。

### 8.6 栏 B 没有 root，所以没有内核侧观测

perf、eBPF、`/proc/sys` 调参一律不可用；容器与沙箱同理（§8.3）。这份数据里所有数字
都来自**用户态可读的三个来源**：`bun:jsc` 的堆统计、`/proc/<pid>/{status,smaps_rollup}`、
cgroup v2 的 `memory.*`。够用来判斜率与水位，**不够用来解释「为什么涨」**——真到了要
归因的时候，得回验收机。

### 8.7 `p73-throughput.ts` 不适合当 24 h 的负载源（量具边界，不是缺陷）

跑批时想过用它当 L1 的流量源（`--rates 1 --tier-seconds 86400`），**放弃了**，理由记在这里
免得下一个人再想一遍：`runTier` 把每条消息的 promise 都推进 `inflight` 数组，直到整档
结束才 `Promise.all` 一次性清空。设计用途（120 s 的档）下这是对的——它保证收尾时把在途
消息全部结算；但一档跑 24 h 就意味着**八万多个 promise 全程驻留**，那是量具自己的单调
增长，会长得和被测对象的泄漏一模一样。

**不改它**（N-12 的精神同样适用于「不为一次跑批改量具」）：正式八档跑批用的就是它现在
这个形状，改了之后 §4 的数据与代码就对不上了。要做长时负载源，M1 另开一个专门的驱动。

### 9.1 吞吐阶梯

### 9.2 内存与长跑

```bash
# ① 常驻节点，带进程内采样。stderr 要留档——writer 溢出警告只出现在那里。
export OCC_IDENTITY=qianmo
export QIANMO_TRANSPORT_PSK=...
occ resident \
  --node node-b --team atlas --agent reviewer=/abs/workspace \
  --unix /abs/run/resident.sock \
  --mem-sample /abs/p73/mem-inproc.ndjson \
  --mem-interval-ms 60000 \
  >/abs/p73/resident.out 2>/abs/p73/resident.err &

# ② 外部采样，挂在①的 pid 上（ACP 子进程由采样器自己 pgrep -P 找）。
#    被 SIGTERM 打断后原样重跑同一条命令即可续采：按已写字节偏移接着追加。
bun run /path/to/repo/demo/lib/p73-sample.ts \
  --resident-pid "$(pgrep -f 'occ resident' | head -1)" \
  --out /abs/p73/mem-external.ndjson \
  --interval-ms 60000 --minutes 1440
```

**`--resident-pid` 一定要核对一遍再开跑。**本地校准时踩过：采样器忠实地采了传给它的
那个 pid 和它的直接子进程，而传进去的是**外层启动壳**——于是「resident」那条线记的是壳的
RSS（31 MB），「acp」那条记的才是真正的常驻进程（132 MB）。两条线都不为空、都在动、
看起来毫无问题。**核对办法**：外部通道读到的 resident RSS 应该与①的 `--mem-sample` 头
几条对得上；对不上就是采错了进程。

> **更好的办法是让这个坑不存在**：把常驻进程交给一个 `systemd-run --user` 的瞬态单元，
> 单元脚本最后一行用 `exec`，于是 `systemctl --user show <unit> -p MainPID --value`
> 拿到的就是被测进程本身，中间没有壳。栏 B 就是这么起的（§2.5 ①、§9.6）。核对仍然要做
> ——但它从「靠人记得核对」变成了「结构上没得错」。

### 9.3 判读

```bash
# 把三份产物折进一份报告。判读逻辑零依赖，可在任意装了 bun 的机器上重算。
bun run /path/to/repo/demo/lib/p73-throughput.ts --tier T3 \
  --mem-file /abs/p73/mem-external.ndjson \
  --resident-log /abs/p73/resident.err \
  --out /abs/p73/t3.ndjson --minutes 45
```

判据六条见 `demo/lib/p73-report-core.ts` 文件头。**红了的处置是写进 §7，不是改代码。**

> **注意这条命令会重新跑一整轮阶梯。**`p73-throughput.ts` 是驱动，`--mem-file` /
> `--resident-log` 只是让它在收尾时把两份采样折进同一份报告——它不会因为给了这两个
> 参数就跳过跑批。照上面的写法执行，代价是**又一次 24 min 的八档跑批**，而且会产出
> 第二份 T3 数据（哪一份是正式的，就得靠人记）。
>
> 想**只判读、不跑批**，有两条路：加 `--rates 1 --tier-seconds 31 --minutes 2` 跑一个
> 最小档（仍然满足「档长 > D」，只是那一档的数字不引用），或者直接 `import`
> `buildP73Report` 自己喂数据——它零依赖，正是为这种场合写的（栏 B 用的就是后者，
> 见 §9.6 的 `summarize.ts`）。

### 9.4 在开发机上复现（只用于校准，见 §1.5）

真机用装好的 `occ`。开发机上从源码跑要注意一条：**`bun run src/entrypoints/cli.tsx resident`
起不来 ACP 子进程**——`--acp` 那条快路径由 `feature('ACP')` 把守，而 feature flag 是
**编译期**注入的，直接跑源码时它是关的，子进程会以 `unknown option '--acp'` 连续失败
五次，然后 supervisor 把它 park 掉、整个常驻进程随之退出。

走 `bun run dev`（`scripts/dev.ts` 会把 `DEFAULT_BUILD_FEATURES` 逐个作为 `--feature`
传下去）就正常。代价是进程树多两层（npm-script 壳 → `dev.ts` → 真正的 `cli.tsx`），
所以 §9.2 那条 pid 核对更要做。

### 9.6 栏 B（aarch64 降级机）怎么搭起来的

**一台没有 bun、没有 node、没有 root 的 Ubuntu 24.04 / aarch64 主机，从零到能跑正式
跑批用了不到 5 分钟**（不含跑批本身）。实测各步耗时：

| 步 | 耗时 | 备注 |
| --- | --- | --- |
| `git bundle create`（本地） | < 1 s | 72 MB |
| `scp` 到降级机 | 79 s | 取决于链路，不是机器的锅 |
| `git clone` bundle | 数秒 | clone 出来 `git rev-parse HEAD` 与本地逐字相同、`git status --porcelain` 空 |
| 装 bun 1.3.13 | ~20 s | 官方安装器，**aarch64 有预编译包，不需要从源码编译** |
| `bun install --frozen-lockfile` | **59.9 s** | 1737 个包，**零报错、零缺包**；没有任何依赖需要在 ARM 上现编 |
| `bun run build` | **6.6 s** | 1292 个文件进 `dist/` |

步骤全部用户态，不动系统：

```bash
# ① 送代码：不走网络仓库，用 bundle + scp，落地后 clone 出来的 HEAD 与本地逐字相同。
git bundle create /tmp/atlas-head.bundle HEAD     # 72 MB（全历史；--depth 不被 bundle 接受）
scp /tmp/atlas-head.bundle <host>:~/p73/
ssh <host> 'git clone -q ~/p73/atlas-head.bundle ~/atlas && git -C ~/atlas rev-parse HEAD'

# ② 装 bun，版本对着 .tool-versions 钉死，装进家目录。
curl -fsSL https://bun.sh/install | bash -s "bun-v1.3.13"

# ③ 依赖与构建。常驻节点要构建产物（§9.4：直接跑源码起不来 ACP 子进程）。
cd ~/atlas && bun install --frozen-lockfile && bun run build

# ④ PSK 只落 0600 文件，由被 systemd 拉起的脚本 source，不进任何命令行、不进单元属性。
umask 077; printf 'export QIANMO_TRANSPORT_PSK=%s\n' "$(head -c 48 /dev/urandom | base64 | tr -dc 'A-Za-z0-9' | head -c 40)" > ~/p73/psk.env
```

跑批与长跑都走 `systemd-user` 瞬态单元（理由见 §2.5 ①）：

```bash
loginctl enable-linger "$USER"                # 不开的话登出会把长跑一起带走
systemd-run --user --unit=p73-ladders  "$HOME/p73/run-ladders.sh"    # 四轮吞吐阶梯，顺序跑

mkdir -p "$HOME/p73/l0"                       # append: 只建文件不建目录
systemd-run --user --unit=p73-l0 -p MemoryAccounting=yes \
  --property=StandardOutput=append:"$HOME/p73/l0/resident.out" \
  --property=StandardError=append:"$HOME/p73/l0/resident.err" \
  "$HOME/p73/run-l0-resident.sh"              # 24 h 常驻（脚本内 exec，MainPID 即被测进程）
systemd-run --user --unit=p73-l0-sampler "$HOME/p73/run-l0-sampler.sh"  # 外部采样，pid 取上面的 MainPID
```

> `--property=...append:` 后面**必须是绝对路径**：`~` 在 `append:` 之后不会被 shell
> 展开（波浪号只在词首展开），写成 `~/p73/...` 会得到一个名叫 `~` 的目录。用 `$HOME`。

**吞吐阶梯与 24 h 长跑不许重叠。**1 vCPU 上它们会互相抢核，两份数据一起失真。
本次的顺序是：先跑完四轮阶梯（约 95 min），再起长跑。

判读脚本在降级机的 `~/p73/summarize.ts`（**不进仓库**：它只是把 NDJSON 折成本文
§5 / §6 那几张表的取点与算斜率，判读本身仍然调仓库里的 `buildP73Report`）。
回收一条命令：`~/p73/collect.sh`（加 `--stop` 才停机；默认只读）。
