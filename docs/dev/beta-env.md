## §0 一页纸：八条定案

读完这张表就知道内测环境长什么样；每条的理由在对应小节。

| # | 问题 | **定案** | 在哪 |
|---|---|---|---|
| 1 | 几台节点 | **4 个常驻节点，一机一节点**（沙箱内 1 + 无 sudo VPS 3，含 aarch64 / x86_64 两种架构） | §2.2 |
| 2 | 几个注册中心 | **1 个，单点**（N-6），绑宿主回环；挂了不影响已建连接，恢复动作见 §2.4 | §2.4 |
| 3 | 控制台在哪 | **与注册中心同机同回环**，前面加一层 TLS 反向代理，**它是用户唯一的对外面**（反代后面另有备份服务，给节点用，§2.7） | §2.5 |
| 4 | 账号最小形态 | **不做账号体系**（N-2 不解禁）。全员共享 **1 枚 view token**，**2 人**持 admin token；两枚都**显式提供、绝不用自动生成的**。**v1.3 补注**：章程 v2.19 已按 A′ 部分解禁 N-2，控制台个人账号由 P15.5 实现；上线前本条原样有效，上线后的迁移与回退见 `tenancy-m1.md` §1.5 | §3 |
| 5 | 配置根与审计链 | 每节点一个 `OCC_CONFIG_DIR`，命名 `$QIANMO_BETA_ROOT/nodes/<node>/config`；**审计链按节点分文件、不集中**，宿主上只放**只读镜像** | §4 |
| 6 | 数据保留 | 审计链与 timings **全程不清**（周封存）、备份 store **72 h + 14 天日留存**、日志 **14 天**、准入台账 **禁止外部裁剪**（它自带压实） | §5 |
| 7 | 回滚 | **五级 L0–L4**，各自有 RTO 与照做步骤；**回滚配置根会带走审计链尾巴，必须在运维单页留一行** | §6 |
| 8 | 一期加密 | **PSK，不等 mTLS**；且是**每节点一把**，不是全网一把 | §8 |

**v1.1 现场回写：八条定案一条未改，但其中三条的前提变了。**三台节点的 38625 被云厂商安全组挡死，数据面改走「H 经 SSH 正向隧道到节点回环」。受影响的是第 2 条（**H 这台机器成了数据面单点**，注册中心进程的单点性质不变，§2.4 / §9.9）、第 7 条（L4 多三件事，§6）、第 8 条（跨公网那一段现在是 SSH 隧道套 PSK，§12——**这是现场形态的副产品，不是可以据此推迟 mTLS 的理由**）。另有两件已落地：审计镜像（§4.3）与控制台 token 改走 `--*-token-file`（§3.2 / §8.3）。

**v1.2 回写：那条隧道与那四条镜像现在有仓库出处了。**它们从「H 上手搓的长驻进程」变成
`peers.conf` 的 `node` 坐标行 + `systemd --user` 单元，起停重置三个脚本都认识它们（§6 L0）。
**八条定案仍然一条未改**——v1.2 改的全是「原来靠人记得的事现在由脚本代劳」（§6.5 改端点前挪
落盘表、§9.8 隧道口的假绿判据）与「原来只在环境变量里的东西现在落了盘」（§4.3 的
`console.conf`）。

**一句话概括一期的能力边界**：内测用户**能看**（名册 / 审计 / 消息链 / 上限）、**能被服务**（运维在控制台上唤醒节点），**不是**每人一个自助智能体。并发上限是 **4**（= 节点数，节点级 turn 串行），不是 50。把这句话写在内测公告的第一行，比事后解释便宜得多。

## §1 它是演示环境的升级，不是另起炉灶

`demo/env/` 已经证明的四件事在内测环境里**原样继承，不重新论证**：

1. **一机多进程靠配置根分家**——每个常驻进程一个 `OCC_CONFIG_DIR`，审计链 / 节点身份 / 会话表随之分家（`demo-env.md` §3.1 三条硬规矩）。
2. **删除动作靠三重守卫**——`demo_guard_root` + 标记文件首行 + 逐路径复核（同文 §3.2，六个负向用例已实测拒绝）。内测的 `reset` 沿用同一形状，标记文件换成 `.qianmo-beta-env`。
3. **起停是幂等的**——`up.sh` 对已在跑的进程不重起，就绪判据是「按名解析 + 真拨通」而不是「进程还在」。
4. **两台全新机器的 runbook 成本已实测**——87 s / 105 s（同文 §4.3 / §4.4），冷缓存 + 2 vCPU + 无 sudo 也成立。内测环境的每台机器都走同一条 runbook。

**内测环境相对演示环境只多四件事**，本文的全部内容就是这四件：

| 多的东西 | 为什么演示环境里没有 |
|---|---|
| 跨机（4 台）而不是同机 | 演示只要证明「拓扑成立」，同机两进程就够；内测要证明「别人能连上」 |
| 一个对外可达的面（控制台 + 反代） | 演示的观众坐在跑演示的那台机器前 |
| 数据保留与轮转 | 演示跑 87 s，什么都不会涨 |
| 升级与回滚流程 | 演示坏了就 `reset.sh` |

**没有多出来的东西**：除 §10 落地包 ② 已实现的控制台多节点适配外，不新增功能代码路径。M1
前两个迭代不排新功能，这条约束在本文里被遵守。

## §2 拓扑与节点数

### 2.1 硬件现实（设计的硬边界）

| 类别 | 台数 | 关键约束 |
|---|---|---|
| 可 sudo 真机（记为 **H**） | **1** | 唯一装了 Dormice + gVisor 的机器，因此**唯一能跑沙箱内常驻节点**、唯一能演休眠态；也是唯一能装 systemd unit、能绑低端口、能做包过滤的机器 |
| 无 sudo VPS，aarch64 / 5.9 GB | **4** | 能舒服地跑常驻 + 构建（`bun run build` 峰值 1563 MB，`demo-env.md` §4.4） |
| 无 sudo VPS，x86_64 / 2 GB | **3** | 能跑，余量很薄（实测最低可用 341–409 MB，动过几百 MB swap） |
| 无 sudo VPS，954 MB | 2 | **排除**，构建必 OOM |

两条由此直接派生的硬结论：

- **沙箱节点只能有一个**，因为 gVisor 只有 H 上有。它同时是唯一能验「唤醒冻结态对端」的节点，所以它必须在一期里（否则内测环境比演示环境弱）。
- **反向代理只能装在 H 上**，因为 TLS 终结要绑 443、要装续证的定时单元，两件都要 root。

### 2.2 定案：4 个常驻节点，一机一节点

**上界是 4，理由是「四条审计链仍要有人去看」。**控制台会把当前 `peers.conf` 的四条链独立
列出，但不会把跨节点记录伪造成一条总顺序（§4.3）。4 条是当前内测的可管理上限，8 条不是。

**下界是 4，理由是 2 个节点证不出内测要证的东西。**2 节点是演示拓扑的形状，它无法同时覆盖三件事：跨机器（不是同机两进程）、跨架构（aarch64 与 x86_64）、沙箱冻结态。而 20~50 人共享 2 个节点意味着 2 个并发 turn，排队会直接变成内测的主要体验，测出来的全是队列而不是产品。

**一机一节点，不是一机两节点。**5.9 GB 的 VPS 塞得下两个常驻，但塞进去买不到任何可用性（同机同死），只买到第二条审计链和第二个配置根。唯一的例外是 H：H 自己**不跑常驻**，它跑注册中心 + 控制台 + 反代 + 备份服务，常驻在它的 gVisor 沙箱里。

**节点名定案：`beta-1` ~ `beta-4`，名字里不含机器名与架构。**节点名会进 `qianmo://` 地址、进审计链、进注册表、印在 50 个人看得见的控制台页面上。把机器名写进去等于把部署拓扑发给所有人；而机器一旦要换（VPS 到期、迁移），地址得跟着改，历史审计链里的旧地址会变成没人能解释的谜。机器 ↔ 节点的映射写运维单页。

> **2026-09-26 现场（偏离本节定案）**：3 节点形态**不是负责人逐项认可的**，是负责人 2026-09-26 授权
> 「舰队项全部可以做」之后，由主 agent 在该授权范围内裁定的（同日更正，原措辞「经负责人认可」见 git 历史）。09-19 原甲骨文云（Oracle）
> 机队终止，beta-2 / beta-3 随之消失；新节点命名 beta-5，不复用退役身份。内测按 **3 个**
> 常驻节点运行。可用机器里只有三台的内存与磁盘余量放得下一个常驻节点而不挤占机器上原有的服务，
> 第 4 个节点暂缓，不为凑数把节点塞进余量不够的机器。**3 个节点证不出本节下界那段话里的两件事**：
> 三台都是 x86_64（跨架构没有覆盖），且都没有沙箱冻结态——这两项的结论照旧只能引用演示环境与
> baseline-m0 的证据，不能写成内测舰队的结论。新节点取新的段名，不复用已随机器消失的节点名
> （key-distribution.md §6.5）。机器 ↔ 节点映射照旧只写运维单页。

**Agent 定案：8 个，每节点 2 个，按用途分而不是按人分。**（`planner` / `reviewer` / `ops` / `scenario` 各两份，分布在四个节点上。）不给每人一个 agent 的理由：agent 地址是注册表和审计链里的一等公民，每一个都要有人注册、心跳、到期清理——50 个坑位里大部分永远不会被用，而 N-2 省下来的账号成本会以「运维 50 条注册记录」的形状原样付回去。人 → agent 的映射写运维单页，不进注册表。

**图上要读出来的四件事**：

1. **注册中心与控制台在同一条回环上，注册中心永不出 H。**`packages/registry/src/http.ts` 里没有一行鉴权（`console.md` §8.2），能连上它的人就能注销任意 agent。控制台的 admin token 保护的是控制台，不是注册中心。
2. **节点不连注册中心。**`occ resident` 没有 `--registry` 选项，也没有出站拨号路径——它是纯入站端点。注册与解析由发起方（控制台 / H 上的运维工具）做。这就是注册中心可以躲在 H 回环后面的原因，也是「注册中心挂了不影响已建连接」的原因。
3. **审计镜像是单向的、只读的、从节点流向 H。**H 上那几份不是权威副本，权威副本永远是节点本机那一份（理由见 §4.3；v1.1 起四条链各有一份镜像，且控制台读的就是镜像）。
4. **反代后面有两个 upstream，不是一个。**控制台给人用，备份服务给节点用——备份服务是**唯一一个可以暴露的内部服务**，理由是它自己带鉴权且入站面被断言为无破坏性操作（§2.7）。别把这条推广到注册中心。

**v1.1：图上那三条「PSK(beta-x) 唤醒 ▼」的箭头不再是直连。**它们现在各自穿过一条 H 上的 `ssh -L`（本地口 38631–38634 → 节点回环 38625，§2.6）。图没有重画，因为**逻辑拓扑一个字没变**——变的是那三条线的物理承载。但由此多出来的两件事必须一并读进去：**H 因此进了数据面**（第 2 点里「注册中心可以躲在 H 回环后面」的理由只保护注册中心，不保护 H 这台机器，§2.4 / §9.9），以及**每条线上现在有两道门而不是一道**（SSH key 在前、PSK 握手在后，§2.6 的门表）。

### 2.4 两个单点，不是一个：注册中心**进程**，和 H 这台**机器**

N-6 明文允许注册中心单点，本节原本只讨论它。**v1.1 起必须分成两件事讨论**：现场的数据面
已经从「38625 直连」改成「H 经 SSH 正向隧道到各节点回环」（§2.6），于是**H 这台机器进了
数据面**——而「注册中心不在数据面上」这条让单点变得可接受的理由，只保护得了注册中心
进程，保护不了它脚下的机器。

**① 注册中心进程挂了**——影响面与 v1.0 一字不改，仍然比直觉小得多：

| 挂了之后 | 还行吗 |
|---|---|
| 已建立的连接、正在跑的 turn | ✅ 不受影响。注册中心不在数据面上 |
| 控制台页面本身 | ✅ 照常 200 打开，名册那栏显示 `unreachable`（`console.md` §7.1，e2e 已实测） |
| 审计链、消息链查看 | ✅ 读的是文件，与注册中心无关 |
| 按名解析 → 新的投递 | ❌ 找不到端点 |
| 页面上的注册 / 注销 / 心跳 | ❌ 全部失败 |

**② H 整机挂了 / 掉线**——这一栏是 v1.1 新增的，**它不是「注册中心挂了」的加强版，是
另一件事**：

| 挂了之后 | 还行吗 |
|---|---|
| 三台 VPS 节点在网络上的可达性 | ❌ **消失**。它们的 38625 被云厂商安全组挡死，唯一入口是 H 上那条 `ssh -L`（§2.6）；隧道随 H 一起没了 |
| 已建立的连接、正在跑的 turn | ❌ 一起断。连接本身就跑在隧道里 |
| 运维笔记本直连接管 | ❌ **也不行**。笔记本同样拨不通 38625，它到节点的唯一路径也是 SSH（22 通、38625 不通）——「换台机器接管」要先在那台机器上把四条隧道重建一遍，不是「改个地址」 |
| 用户看到的 | 全网静默：控制台、名册、对话面一起没有 |
| 节点本机的审计链 | ✅ 完好。它是本机文件，权威副本从来就在节点上（§4.3） |

**这是 v1.1 引入的、必须被明确接受的一条**：H 从「持有全部 PSK 与归档 token 的机器」变成了
**数据面单点**。它不是设计选择，是现场约束的后果——`node-provisioning.md` §1.1 把这件事
测清楚了：三台节点上除 22 / 80 / 443 之外，另探的十个端口全不通。所以隧道在当前现场**不是
可选功能，是数据面唯一的落地形态**；同一份文档的 §7.2 同时写清了它为什么**不能**被扶正成
设计形态（跳数与防循环的语义、以及「注册中心挂了连接还活着」这条性质，都是数据面不经过 H
换来的）。**退出条件是安全组放开 38625**，那时兜底退役、这一栏消失。

**处置**：H 整机故障走 §6 的 L4（RTO ≤ 60 min），且 v1.1 起 L4 多三件事（重建 SSH 密钥、
四条隧道单元、四条镜像 timer）。**在 H 恢复之前没有降级路径可走**——这句话要写进运维单页，
免得有人在事故当中现找。

**注册中心进程的恢复动作（照做，RTO ≤ 2 min）**：

```
① 在 H 上确认进程确实死了（pid 文件里的 pid 已不存在），不是端口被占
② 看 logs/registry.err 末 20 行，把原因抄进运维单页（不看就重起 = 下次同样死法）
③ 重起注册中心那一段（带 --state 与全部 --register）
④ 用控制台 /v0/health 与名册栏确认：四个地址全部回来
```

**由此产生一条硬规矩**：**凡是要长期存在的地址，必须同时写进注册中心的 `--register` 启动参数，不能只在控制台上点「注册」。**

理由是可算的：租约 TTL 是 90 s（`DEFAULT_TTL_MS`），而 `InMemoryRegistry` 在 restore 时**按当前时钟重判租约**，已过期的条目直接丢弃（`registry.ts` 的 `#restore`，注释里写明了为什么不能信旧文件）。所以注册中心停机超过 90 s，落盘的 `agents.json` 就等于空文件——注册中心自己带回来的只有 `--register` 里那批。

**2026-09-26 修订：页面上注册的条目现在由控制台带回来**（`console.md` §7.3）。控制台把它们记在自己配置根下的登记簿里，并按周期重新注册：注册中心重启后一个续租周期（默认 20 s）内它们回到名册，控制台重启时也从登记簿读回。此前这里写的是「控制台上那个『注册』按钮活不过一次 90 s 以上的重启」，那是修复前的事实。这些条目仍然**依赖控制台进程**：控制台停机超过一个租约，它们会从名册消失，直到控制台回来。这就是上面那条硬规矩仍然成立的原因——`--register` 是唯一不依赖控制台进程的来源，节点名册（`peers.conf`）只走它。

### 2.5 控制台部署与对外访问面

**控制台绑 `127.0.0.1:38621`，前面一层反向代理做 TLS 终结，反代与控制台之间走回环。**

为什么不直接让控制台绑非回环地址：`console.md` §4.2 已经写清了——非回环时它会强制要求显式 token（这条是对的、要保留），但「给了 token」不等于「可以挂公网」：控制台没有 TLS、没有账号体系，限流也只有登录路由那一处（`console.md` §8.4，v1.1 更正——它不再是「完全没有速率限制」，但面板其余 HTTP 面仍然不限）。20~50 人的访问必须有 TLS，而 TLS 只能来自外面那一层。

为什么不用 SSH 端口转发（`console.md` §4.2 给内测之前的推荐做法）：那需要 20~50 个 SSH 账号，而「不做账号体系」正是 N-2。SSH 隧道仍然是**运维自己**访问控制台的方式（2 个人，本来就有账号）。

**开测前置检查——已于 2026-08-18 实测，结论是方案 A，方案 B 不建。**原文的顾虑是：H 的
SSH 直连路径是坏的（TCP 通、banner 超时，只能经 IAP 隧道访问），而 SSH 坏不等于 443 坏，
也不能假设它好。**实测**：从公网直拨 H 的 443 得 `HTTP/2 200`（TCP 连接 0.3 ms、总耗时
1.57 s），入站路径完好。落地形态因此是方案 A——反代就在 H 上，且比设计假设的更现成：
H 上本来就跑着 host 级 nginx + certbot，只差一个 server 块。

**方案 B（反代挪到一台有公网的 VPS，经隧道回到 H 的回环控制台）就此作废，不要建。**
它是备选不是并选；两个都建会多一跳、多一条要维护的隧道，而那条隧道要解决的问题
（H 的入站路径不可靠）已经被证明不存在。

**一条实测顺带暴露、并已修掉的缺陷**：H 上此前**一个 `default_server` 都没有**，于是任何
未配置的名字（含直接打 IP）都会落到 nginx 加载顺序里的第一个 server 块——那是线上业务站，
出示的是它的证书。控制台的 DNS 记录建好、server 块还没配的那段窗口里就是这个形态：浏览器
报证书名称不匹配，点过去却是真的业务站。现已补一个兜底 server（80 返 444 并记录被拒的
Host，443 用 `ssl_reject_handshake on` 在 TLS 层拒绝且**不出示任何证书**）。**这条对内测的
意义不只是那一个子域**：它把「先建 DNS 后配站点」这个必然存在的时间窗从「串到别的站」
变成「什么都没有」。注意本站证书全部走 DNS-01，不依赖 HTTP-01 的 `/.well-known/`；哪天改用
HTTP-01，必须先在兜底里为 acme-challenge 开一个 location。

### 2.6 端口

内测占用 **38620–38629** 段，与演示环境的 38610–38613 **不重叠**——这样 H 上可以同时留着演示拓扑（复现 AC 用）和内测拓扑，互不打架。

| 端口 | 谁在用 | 绑哪 |
|---|---|---|
| 38620 | 注册中心 HTTP v0 | H 的 `127.0.0.1`，**永不出回环** |
| 38621 | 控制台 | H 的 `127.0.0.1`，由反代暴露 |
| 38625 | 常驻节点入站 WebSocket | **每台节点机各一个**（一机一节点，所以四台用同一个号，不用协调）。**v1.1 起 H 不再直连它**，见下 |
| **38631–38634**（现场取值，**不是常量**） | **隧道本地口，一个节点一个**（`ssh -L <local-port>:127.0.0.1:38625`） | **H 的回环**。这是 H 上「拨某个节点」的实际地址：`peers.conf` 与 `--wake-url` 填的都是 `ws://127.0.0.1:<local-port>` |
| 443 | 反向代理 | H 的对外地址 |

**隧道本地口的唯一出处是 `peers.conf` 里那条 `node` 坐标行的 `local-port=`。**上表那个
38631–38634 是当前现场四条坐标行的取值，不是一个写在脚本里的常量——脚本里没有它的默认值，
`local-port=` 是必填键（`common.sh` 的 `beta_parse_node_line`），四个节点各不相同（同一个口
被两条坐标行占用会带行号 die）。由这一个值派生的有三处，都不用人手对齐：

| 派生物 | 谁生成 |
|---|---|
| `ops/tunnel-<node>.env` 里的 `LOCAL_PORT`（隧道单元的 `-L` 从这里读） | `beta-up.sh` 的 `write_tunnel_env` |
| 地址行的端点必须**正好**是 `ws://127.0.0.1:<local-port>` | `common.sh` 的 `beta_assert_peers_match_tunnels`，不一致就带行号 die |
| 控制台 `--wake-url`（取该节点地址行的端点，所以跟着上一条走） | `beta-up.sh` 的 `run_host` |

第二条那个断言值得单独说：**链路搭在一个口上、应用拨的是另一个口**，两边各自都「正常」，
症状是名册上四个节点全在线而拨号全超时（§9.1）。这类不一致以前只能靠人记得，现在由脚本
在读表时当场拦下。

**v1.1 现场更正：38625 不是从外面拨得通的。**v1.0 这里写的是「38625 在无 sudo 的 VPS 上
必然对全网开放——没有 root 就没有包过滤」。那句话**描述主机侧仍然为真，但它答错了问题**：
三台节点的 38625 被**云厂商安全组**挡死（另探 8080 / 8443 / 3000 / 5000 / 8000 / 9000 /
10000 / 30000 / 38620 / 50000 全不通，只有 22 / 80 / 443 通——实测记录在
`node-provisioning.md` §1.1）。没有 root 挡不住的是主机防火墙，厂商侧的安全组不归主机管。

**所以现场的数据面是**：H 上每个节点一条长驻 `ssh -N -L 3863x:127.0.0.1:38625`，节点侧的
入站端口只需要在**它自己的回环**上被拨到。

**「那个端口上唯一的门是 PSK 握手」这句话因此要改。**现在**门有两道，而且第二道更靠前**：

| 门 | 挡的是 | 上界 |
|---|---|---|
| **SSH key**（H 侧持私钥，节点 `authorized_keys` 里是它的公钥） | 谁能建立这条隧道 | 该 key 上钉着 `restrict,port-forwarding,permitopen="127.0.0.1:38625",command="…"`：**拿不到 shell、`-L` 转发不到别的地址**（`node-provisioning.md` §5.1，P-10/P-11/P-12 实测）。但两件事仍然做得到：**读那个节点的审计链全文**——`mirror` 动作要的就是这个能力；以及**开反向转发**（§9.10）|
| **PSK 握手** | 穿过隧道之后谁能说话 | 与 v1.0 一字不改（§8） |

第二列右边那句要读进去：受限 key **不是**一把「只能转发」的钥匙。它买到的是「不能任意
远程执行」，不是「什么都读不到」。爆炸半径的重算见 §8.3。

### 2.7 备份服务：唯一一个可以暴露的内部服务

三个 VPS 上的节点要往 H 的备份 store 写快照（`occ resident --backup-url`），所以备份服务**不能只绑回环**——这与「注册中心永不出回环」看起来矛盾，其实不是。

**定案：备份服务经同一层反代以 TLS 暴露在一个独立子域（或独立路径前缀）上；节点用 `https://…` 作为 `--backup-url`。**

**为什么它可以暴露而注册中心不可以**，三条都成立才算数：

1. **它有鉴权，注册中心没有。**双 token 分权（写 token 只能 `POST /snapshot`，归档 token 只能读），定长时间比对，最小长度校验，两枚必须不同（`packages/backup/src/service.ts`）。
2. **它的入站面被断言为无破坏性操作。**`assertBackupSurfaceIsSafe` 是**门禁**而不是注释：路由表只允许 GET / POST，且方法名里出现 `delete` / `prune` / `rotate` / `truncate` 等任一 `DESTRUCTIVE_WORDS` 就直接拒绝启动。所以最坏情况下拿到写 token 的人只能**多写快照**，不能删任何东西。
3. **写 token 的能力上界是「塞满磁盘」**，而那由 §5 的保留策略与 `DEFAULT_MAX_ARCHIVE_BYTES`（单份 512 MB 上限）兜着。

**两条配套纪律**：

- **归档 token 永不离开 H。**节点只需要写 token；把归档 token 发到 VPS 上等于让任何一台被拿下的 VPS 读走全部快照。这正是「两枚而不是一枚带 scope」这个设计要买的东西，别在部署时把它退掉。
- **必须走 TLS，不能走明文 HTTP。**写 token 在 `Authorization: Bearer` 头里，明文 HTTP 等于每小时把它广播一次（60 min 快照间隔，§5）。

## §3 账号最小形态

### 3.1 定案：不做账号体系，做「一枚共享 view + 两人持 admin」

> **v1.3 补注**：本节是 v1.0 的定案，原文保留。章程 v2.19 已按 A′ 部分解禁 N-2：M1 做控制台个人账号——邀请开户、每人一枚个人凭据、服务端会话可吊销（`tenancy-m1.md` v1.0 §0.2、§3）。**P15.5 上线前，本节与 §3.2–§3.5 照旧执行。**上线后按该文 §1.5 的迁移步骤走：旧 view token 与 admin token 在迁移期照常可用，admin token 最终保留为 break-glass（该文 D7）；个人凭据不进查询串，§3.3「发完整的 `?token=` 链接」的做法只留给迁移期的旧 token。租户隔离不在本次解禁范围内，挪到 M2。对内测用户的告知见 §3.6。

N-2 在本包里**不解禁**。控制台现有的两枚 token 就是内测一期的全部身份概念（`console.md` §8.1 已经把这条后果写清：谁拿到 admin token，谁就是同一个人；审计链上不会因为动作来自控制台而多出操作者字段）。

| 角色 | 人数 | 拿到什么 | 能做什么 |
|---|---|---|---|
| 内测用户 | 20~50 | **同一枚 view token** | 名册 / 审计 / 消息链 / 上限，只读 |
| 运维 | **2**（负责人 + 一名 backup） | admin token（view 的严格超集） | 加上注册 / 注销 / 心跳 / 唤醒 |

**admin 为什么是 2 人而不是 1 人或 5 人**：admin 能唤醒节点、能注销任意 agent，而审计链上**不记录是谁做的**——持有人数就是「出事之后要挨个问的人数」。1 人的问题是失联即停摆（IAP 隧道下的运维不是随时能上）；≥3 人的问题是「问三个人」已经不比查日志便宜。2 是能保证不失联的最小值。

### 3.2 定案：两枚 token **一律显式提供**，绝不用自动生成的

即使控制台绑在回环上（它确实绑回环）、`resolveTokens` 会自动生成，一期也必须显式提供两枚。

理由是运维性的，不是安全性的：**自动生成的 token 每次重启都变。**控制台会因为改 `--label`（§7 的告知面用的就是它）、改 `--audit`、跟随升级而重启。每重启一次，50 个人手上的链接同时失效，而重新分发一次 token 的成本远高于把它固定下来。固定 token 的代价是「不能靠重启换 token」，但那本来就该是一个有意的动作（§3.4）。

token 来源：H 上 `secrets/console-view-token`、`secrets/console-admin-token`，0600，由 `demo_random_hex 24` 同形生成（48 hex 字符，远超 16 字符下限）。**两枚必须不同**（`resolveTokens` 会校验，这里只是提醒别手抄成一样）。

**v1.1：怎么传进去也定了——`--view-token-file` / `--admin-token-file`，不是 `--view-token` / `--admin-token`。**控制台现在给每枚 token 三个入口（文件 > 环境变量 > 命令行，`console.md` §3.1），而命令行那个入口会把 token 摆进这台机器每一份进程列表里。我们本来就把两枚存成 0600 文件了，直接把路径给它即可；控制台会**自己校验那两个文件的权限**（group / other 任一位不为零就拒绝启动），所以「存成 0600」这件事从一条纪律变成了一道门禁。存放规矩与 PSK 合并成一张表，见 §8.3。

### 3.3 分发

| 步骤 | 定案 | 为什么 |
|---|---|---|
| 谁生成 | 运维（持 admin 那 2 人），在 H 上 | 生成动作和保管责任必须是同一个人 |
| 走什么渠道 | **一对一私信或校内邮箱，一人一条** | 不在内测群里贴。群消息会被转发、被截图、被搜索，而这枚 token 一发出去就再也收不回（§6.4） |
| 发什么 | **完整的 `https://…/?token=…` 链接**，外加一句「这个链接等于你的密码，别转发」 | 让人手抄 token 会产生一批「我进不去」的支持请求，那是运维成本最高的一类 |
| admin token 怎么发 | **不发**。两个人各自在 H 上 `cat` 自己那份 | 一枚永不离开宿主的 token，泄漏面只有宿主本身 |
| 记录 | 运维单页记「发给谁、什么时候」，**不记 token 本身** | 轮换时要知道通知谁；记 token 等于又造一个副本 |

### 3.4 轮换

**节奏定案：每 4 周一次例行轮换 + 事件驱动。**

事件驱动的四个触发条件（任一命中即立刻换，不等例行窗口）：

1. 有人退出内测（因为只有一枚共享 token，**收回单个人的访问 = 换全员的 token**——这是共享方案的全部代价，写在这里，第一次发生时不要惊讶）；
2. token 疑似泄漏（贴进群、贴进工单、出现在某个截图里）；
3. 反代的日志配置被改动过（可能记下过 query string）；
4. 持 admin 的 2 人发生变更。

**轮换流程（照做）**：

```
① 生成新的两枚（H 上，写进 secrets/，0600）
② 换 view token 前先发预告：内测群公告「明日 21:00 换链接」——旧链接会当场失效
③ 到点：重起控制台，带新的 --view-token / --admin-token
④ 逐个私信发新链接（分发清单来自运维单页）
⑤ 旧 token 文件立即删，不留历史副本
```

轮换要重起控制台，所以**它必须落在 §7 的升级窗口里**，不要在工作时间做。

### 3.5 这个方案挡不住什么（如实写）

- **挡不住内测用户之间互相转发 view token。**共享 token 没有「是谁」的概念，转发和正常使用在服务端完全一样。挡它需要按人发 token，那是 §10 的落地包 ④，且**只有在真的需要单独收回某个人的访问时才做**。
- **挡不住 admin 动作的抵赖。**审计链上没有操作者字段（`console.md` §8.1）。一期靠「admin 只有 2 人」把这个问题压到可以口头解决的规模。
- **挡不住拿到 view token 的人看到全部审计。**审计链本身不含 payload（`packages/audit/src/record.ts` 只有 id、code、计数），所以泄漏的是**元数据**而不是会话内容；即便如此，谁在什么时候被拒过一次任务，仍然是信息。一期接受这个，因为内测用户本来就是同一个信任域（N-2 的原话）。

### 3.6 内测用户告知（v1，负责人可改措辞）

> 本节是给内测用户看的一段话，**只写事实，不作承诺**。措辞是 v1，负责人可以改；改措辞不改事实，事实以 `tenancy-m1.md` v1.0 与 `authorization-m1.md` v1.0 为准。标「上线后」的几条，在对应的包上线之前不成立，发告知时要按当时的状态删改。

**给内测用户的告知（v1）**

1. **运维能读你的对话转录。**今天只有持 admin token 的运维能读；控制台记不下是谁读了哪一份——持有人共用同一枚 admin token，审计链上也没有操作者字段（§3.5）。个人账号上线后（P15.5、P15.9），运维每打开一次转录，都会在控制台动作账本里记一条；你能查到自己的转录被谁在什么时候打开过。反复刷新同一份转录只记一条。
2. **同一个 agent 的工作区，对它的全体使用者共享。**你让 agent 写下的文件，其他使用这个 agent 的人能看到、也能让 agent 改动。个人账号上线后，其他内测用户看不到你的会话列表与转录（运维仍能读，见第 1 条），但工作区仍然共享。
3. **账号记录与控制台动作账本在内测期间全程保留**，保留规矩与审计链相同，见 §5。内测结束后怎么处置，目前没有定。
4. **审批页会展示工具的原始输入。**权限审批上线后（P14.5），agent 申请执行需确认的动作时，审批页原样展示它要执行的内容，例如完整的命令或要写入的文件内容。能看到这一页的是有权批准这次请求的人：会话的属主和运维。
5. **审计链不清空。**节点审计链在内测期间全程不清、不截断（§5）；它只记消息的编号、结果码和计数，不记对话内容。

## §4 配置根与审计链分区

### 4.1 每机的目录布局与命名约定

**每台机器一份，形状与 `demo-env.md` §3 同构**（同构是为了让落地包 ① 能直接照抄 `demo/env/common.sh` 的守卫与 helper，不是为了好看）：

```
$QIANMO_BETA_ROOT/                 # 默认 $HOME/qianmo-beta（无 sudo，不能用 /srv）
├── .qianmo-beta-env               # 标记文件 —— reset 的全部安全依据
├── peers.conf                     # 0600，地址行 + 可选的 node 坐标行（H 上才填，见 §2.6）
├── console.conf                   # 0600，只存控制台页头标签（只有 H 上有，见 §4.3）
├── secrets/                       # 0700
│   ├── transport-psk              # 0600，**只有本机这个节点的那一把**（§8）
│   └── peers/<node>.psk           # 0600，**只有 H 上有全部四把**（§8.3）
├── nodes/<node>/config/           # 该机那个节点的 OCC_CONFIG_DIR
├── workspaces/<node>/<agent>/     # 每个 agent 一个真 git 工作区
├── backups/                        # H 的宿主侧备份 store（沙箱挂载之外）
├── mirror/<node>/trail.ndjson     # 审计链的只读镜像（只有 H 上有，见 §4.3）
├── ops/                           # 0700，链路的生成物（只有 H 上有，见 §2.6）
├── state/                         # timings、注册表快照、配置根快照
├── run/                           # pid、ready 文件
└── logs/                          # 每进程一对 .out / .err
```

`nodes/` 下只有一项（一机一节点），层级保留是为了和演示环境同构。

**目录骨架两条腿共用同一个 `beta_seed_root`**，所以节点机上也会有空的 `mirror/` `ops/`
`secrets/peers/`——它们在那里是空的，不是漏铺的。`console.conf` 是例外：它由 H 腿的
`beta_resolve_console_conf` 写，节点机上根本不产生。`ops/` 下的东西全是**生成物**：每节点
一份由 `peers.conf` 坐标行派生的 `tunnel-<node>.env`（0600，含 SSH 用户与机器地址），加上
三个由仓库 `demo/env/beta/ops/` 派生的 systemd 模板与拉取脚本。**真源在仓库，改装好的那几
份没有意义**——下一次 `beta-up.sh --role host` 会照仓库重新派生。

**配置根之下的东西是基座与阡陌各自派生的，不由本文规定**——`OCC_CONFIG_DIR` 一设，`occConfigPath()` 就把审计链、节点身份、常驻会话表、准入台账各自放到位。命名约定只到 `nodes/<node>/config` 为止，**再往下一层都不许手写路径**（CLAUDE.md §1.1②；`check:identity-paths` 已经是零容忍棘轮，2787 文件 0 绕过）。

**身份变量三件套**，每个节点进程都要有，缺一个就是隔离破了：

| 变量 | 值 | 缺了会怎样 |
|---|---|---|
| `OCC_IDENTITY` | `qianmo` | 落到 `~/.occ`，与机器上的 occ 抢配置根 |
| `OCC_CONFIG_DIR` | `$QIANMO_BETA_ROOT/nodes/<node>/config` | 落到 `~/.qianmo`，与该机上其他阡陌进程抢 |
| `QIANMO_TRANSPORT_PSK` | 本机那一把（§8） | 进程起不来（`assertUsablePsk` 前置判死） |

三身份共存的底线由 `identity-coexistence-m1.md` 承担，本文不重述。**内测机器上多的那一条**：`$QIANMO_BETA_ROOT` 必须在 `~/.occ` / `~/.qianmo` / `~/.claude` **之外**，`demo_guard_root` 的同形守卫要原样搬过来——内测机器上真的会有人拿同一台机器跑别的东西。

### 4.1.1 `--allow-workspace-edits`：不给它，agent 连自己的工作区都写不了

这一节讲的不是目录，是一个**必须显式给**的启动开关，放在这里是因为它决定 `workspaces/`
那几个目录到底能不能写。

**默认为什么是写不了。**无人值守的每一轮跑在 `permissionMode: 'dontAsk'` 下，语义是**不
提示、未预批准即拒绝**；而常驻对每一次授权请求都答 `cancelled`
（`packages/resident/src/acp-client.ts`）。两者合起来：没有任何需要授权的动作会被放行，
包括在自己工作区里建一个文件。

**失败的形状很难认**（2026-08-28 在 p11 上撞到过）：投递、回执、已读、终态回复**全绿**，
工作区目录可写，节点 `.err` 里一条文件系统错误都没有，只读工具（`ls`）跑得好好的——只有
模型回话里一句「当前权限模式拒绝文件写入」。查文件权限位查不出任何东西。

**settings.json 的 allow 规则在这条路上不生效，不要往那个方向修。**这是实测结论，不是推
测：ACP 会话的权限上下文由 `getEmptyToolPermissionContext()` 建
（`src/services/acp/agent/createSessionMethod.ts`），`alwaysAllowRules` 是**空的**，settings
里的规则根本不进这条路。第一版修法正是往节点配置根写了一份 `settings.json`，部署上去之后
写文件**依然被拒**——那份文件是惰性的，而且比没有更糟：它看起来像已经授权了。

真正生效的旋钮是**模式**，因为模式经 `_meta` 传进会话。`--allow-workspace-edits` 把它从
`dontAsk` 放宽到 `acceptEdits`，而 `acceptEdits` 只放宽一件事：**工作目录之内**的编辑
（基座 `filesystem.ts` 的 `pathInAllowedWorkingPath` 门控）。三层保护一层没少：

- 配置文件与敏感路径仍由 `checkPathSafetyForAutoEdit` 挡在前面；
- 本节点的硬名单（`packages/resident/src/guard.ts`）排在所有判定**之前**，身份目录、审计
  链、准入台账进不去，且那张表是包内的冻结字面量；
- 其余需要授权的工具照样落到 `cancelled`，也就是照样拒绝。

**它必须写在启动命令里，不能省成默认值**，与任务策略那两个开关同一条纪律（issue #10）：
省掉它，这台节点能不能干活就由「跑的是哪一版产物」决定。`beta-up.sh` 的节点腿写死了它，
`demo/env/resident-task-policy.test.ts` 钉住它不会被悄悄删掉。演示拓扑（`demo/env/up.sh`
等）**不**列它——那两处是本机跑给人看的，放宽与否该是各自的决定。

### 4.1.2 值守作业（`qm watch`）：先让节点信任中枢，再签名

`qm watch` 不签名时，作业能送达，但默认策略的节点会拒收；`--open-policy` 的节点会收下，
agent 却会拒绝执行（console.md §10.1.1）。起法四步，完整说明在 console.md §10.1，这里只列
内测环境要多做的那一步——节点的 `--trust hub=`：

```bash
# ① 中枢机：取中枢的签名身份（只需要 --from，不读 PSK，不起调度器）
qm watch --print-identity --from qianmo://hub/console      # → hub=<publicKey>

# ② 每台目标节点：信任这把公钥。节点腿的尾参以这一趟为准并重写记录（demo/env/beta/README.md
#    「尾参透传」），所以已有的 --trust（比如控制台那一条）要一起带上，否则会被撤掉
./demo/env/beta/beta-down.sh <节点名>
./demo/env/beta/beta-up.sh --role node --node <节点名> -- \
  --trust console=<控制台公钥> --trust hub=<publicKey>

# ③ 中枢机：带 --sign 起调度器
qm watch --jobs ./jobs.json --from qianmo://hub/console --sign
```

只读检查类作业（`df`、工作区内的 Read / Grep）在节点默认的 `dontAsk` 模式下就能执行，
**不需要为它打开 `--allow-workspace-edits`**；工作区之外的读取在两种模式下都会被拒绝
（console.md §10.1.2）。节点在作业运行中推送的工具过程行只进中枢审计链
（`watch_step_received`），不会出现在 `qm watch` 的 stdout 上（console.md §10.1.3）。

### 4.2 定案：审计链按节点分文件，**不集中**

三条理由，任何一条单独成立：

1. **集中就断链。**审计链是每条记录带前一条哈希的链（`packages/audit/src/trail.ts`）。两个节点写进同一个文件 = 两条链交替写入 = `occ audit --verify` 必然报断链。演示环境已经为这条踩过一次（`demo-env.md` §3.1 第 3 条），代价是有人去查「谁改了审计文件」而实际上只是拓扑搭错。
2. **跨机集中要付一个更贵的价。**写入方是 `O_APPEND | O_NOFOLLOW` 的 fd + 每条 `fsync`。跨机集中只有两条路：走网络写（那就给每个节点加了一个能让它停摆的外部依赖——审计写不进去的时候节点该不该继续跑？无论怎么答都是新的失效模式），或者定期拷贝（拷贝件不再是 append-only 的那个文件，**反而弱化了三句承诺里唯一被真正强制的那一句**）。
3. **集中解决不了它想解决的问题。**「一个地方看全部」的正解是 P11.4 的**机外见证 / 定期锚定摘要**，不是把原文搬到一起——搬到一起之后那份仍然是一个「有本机写权限的人可以整篇重写并重算哈希」的文件，只是换了台机器（`console.md` §8.3 的第 3 句）。

### 4.3 控制台怎么看四条链：多节点视图

`--audit <node>=<绝对路径>` 可重复给出。控制台为每个来源独立读取、独立显示完整性与问题
条数：缺文件是该节点的空态，断裂不会拖累其他节点。旧的单路径写法仍兼容，但只能单独使用，
并稳定显示为 `default` 节点。

**H 腿的定案**：`beta-up.sh --role host` 只遍历 `peers.conf` 的当前节点名册，每个节点恰好
生成一条命名审计来源。它不从 `console.conf` 或环境变量接受额外的审计节点或路径；删掉一个
peer 后，下一次启动不可能保留该节点的审计来源。

- **带 `trail=` 坐标的链有只读镜像在 H 上**：`mirror/<node>/trail.ndjson`。**已落地**，
  不再是计划：由 H 上**每 5 min** 一次的 timer 从这些节点**单向拉取**（节点侧只读、H 侧只写），
  写入是**先落
  临时文件再原子替换**——一个正被 append 的链文件，边拉边读会读到半行，而半行在哈希链上
  长得和「链断了」一模一样。镜像文件 0600。
- **v1.2：镜像也收进落地包 ① 了，且它是 `ssh cat` 不是 `rsync`。**形态是 `systemd --user`
  的 `qianmo-mirror@<node>.timer` → 同名 `.service`（oneshot）→ `ops/mirror-pull.sh`，三份
  都由 `beta-up.sh --role host` 从仓库 `demo/env/beta/ops/` 派生；**只对在 `peers.conf` 的
  坐标行里给了 `trail=` 的节点建**（`provision_links`）。**用 `ssh cat` 是那把受限 key 逼出来
  的，不是退化**：§2.6 门表里那一行 `command="…"` 是强制命令，它会忽略客户端发来的命令，
  于是 `rsync` 协商不到远端的 `--sender`，必然挂在握手上。`mirror-pull.sh` 里那个
  `MIRROR_METHOD=rsync` 分支留着只为让「有人把 rsync 写回去」**当场报错**，不是为了扩展性。
  另有一条不显眼但会咬人的守卫：**拉到零字节不覆盖**——节点侧链文件还没建时 `cat` 给出空
  内容而 `ssh` 退出码仍是 0，覆盖上去等于用一次网络抖动抹掉整条镜像，而 `occ audit --verify`
  对空文件不报错、页面上也看不出来。
- **每条命名来源按节点决定读哪份文件。**有 `trail=` 坐标的节点读 H 上
  `mirror/<node>/trail.ndjson`，并以 `--audit-mirror <node>=<分钟>` 显式传入 timer 的最大
  滞后；没有该坐标的节点读 H 上的权威本地文件。路径从不作为镜像判断依据。
- **镜像状态在该节点自己的审计卡上标出。**页面显示「镜像 · 滞后 ≤ N 分钟」或「权威链」；
  一条延迟链和实时链不能只靠相同的记录表让人猜。
- **`console.conf`（0600）只持久化 `LABEL`。**环境变量优先，胜出的标签会回写
  （`common.sh` 的 `beta_resolve_console_conf`）。节点、审计路径和唤醒目标不在这里存副本，
  所以历史配置不能在删 peer 后重新引入旧目标。已经在跑的控制台按幂等规则不重起；改标签要先
  `beta-down.sh console`，再 `beta-up.sh --role host`。
- **镜像不是权威副本。**权威永远是节点本机那一份。镜像的用途有三个：出事时在一台机器上把
  四条链摆在一起看；给控制台一个能读的本机文件；以及给 P11.4 的锚定留一个取样点。哈希链在
  镜像上照样能验（验的是内容），所以「链断了」在镜像上一样看得见。
- **镜像随时可重建，所以永不备份镜像**（§5 已定）。反过来说：**镜像坏了不是事故，拉不到才
  是**——判据是 timer 的成功时间戳，不是文件在不在。

落地包 ②的本地实现已覆盖这里的多来源读取、镜像标注和单来源故障隔离；它不构成任何真机或
长期运行证据。

### 4.4 备份 store 的位置

**P11.3 后半落地的路径与时间语义**：宿主操作员通过 `demo/env/beta/beta-retain.sh` 运行，默认
`--dry-run`，只有 `--apply` 才会变更；升级窗口前另加 `--snapshot-registry` 才会创建一份注册表
快照。全部目标由 `demo/env/beta/common.sh` 的 `BETA_BACKUP_STORE` / `BETA_REGISTRY_STATE` /
`BETA_REGISTRY_SNAPSHOT_DIR` 等固定派生值给出，不接收任意路径参数。这里的注册表源特指
`beta-up.sh` 传给 p81 registry 的 `--state` 文件；`<配置根>/registry/agents.json` 是
`@qianmo/registry` 的通用默认，不是 beta 脚本正在轮转的那份落盘表。

时间一律按 UTC：72 h 边界以内（含边界）全留，之后但在最近 14 个 UTC 自然日内每日保留
`meta.createdAt` 最新的一份，时间并列按快照 id 词典序取大者，其余成为轮转候选。完成日志命名为
`<name>.YYYY-MM-DD.gz`，当前 pid 对应的 `.out` / `.err` 不压缩、不删除；过期 gzip 才删除。审计仅在
周日按 ISO 周复制权威源链，先临时文件 + fsync 后原子发布，源链、镜像链都不删不截断；已有同名但
不同内容的封存一律失败而不覆盖。准入台账仅在单文件大于 10 MiB 时告警，绝不改变字节。

日志淘汰采用可恢复的两阶段语义：raw 即使已经超过 14 天，本轮也必须先生成并验证 gzip，确认源在
压缩前后身份、大小、mtime 与摘要一致后才删 raw；本轮新生成的 gzip 不立即淘汰，后续运行才按
14 天判断。已有同名 gzip 只有在解压字节与稳定 raw 完全一致、保留时间也一致时才算幂等完成；否则
双方都保留并非零退出。`--apply` 的全量扫描与执行用宿主侧锁串行化，并发等价运行由后一份在前一份
完成后重新扫描结算；这不改变默认 dry-run 的零写入语义。

工具在执行任何数据操作前完成全部 planner 的只读预检并汇总逐对象错误；registry snapshot、pid、
node 和 ledger 等逐项扫描不会在第一个坏项停下，一个 planner 或对象失败也不妨碍报告其他错误，但
任一错误都会阻止整轮数据操作。active pid 只禁止 raw 日志轮转，不会跳过 raw 与已有 gzip peer 的
等价性验证。内测根的 mode 必须严格为 0700；marker、文件和每级后代目录必须与根同 owner，后代
目录允许正常 umask 产生的 0775。捕获后的父目录按精确 mode/dev/ino/owner 身份在操作前复验，
`chmod` 或替换都会失败关闭；每份身份的全部字段来自同一次 bigint stat，dev/ino 保持 bigint，其他
字段只在安全转换后使用，既避免大设备号/inode 精度丢失，也不把两次 syscall 的不同 inode 拼成快照。
备份归档与元数据成对删除。删除任一方前，元数据 staging 按 payload fd fsync、临时目录 fsync
（提交 payload 目录项）、`run` 目录 fsync（提交临时目录项）的顺序持久化；每一步都在已捕获的
同 owner、非符号链接、精确 mode/dev/ino/uid 目录身份下前后复验。公开 pathname 不直接 unlink：
工具在同一父目录建立并 fsync 私有 `.retain-delete-*` quarantine，再用 macOS
`renamex_np(RENAME_EXCL)` 或 Linux `renameat2(RENAME_NOREPLACE)` 把公开 pathname 原子、无覆盖地
隔离；原生能力不可用时失败关闭，不回退到覆盖式 rename。隔离对象与计划身份一致、quarantine 与
原父目录均 fsync、原 pathname 确认缺失后，才在 private quarantine pathname 上执行物理 unlink。
两个对象完成后必须 fsync planner 捕获的 `backups` 目录，并在该父目录身份仍成立时复验两个公开
pathname 都缺失，才把 paired deletion 标成 committed。archive 已被并发移走或 pathname 重新出现
都不算提交，也不会触发 staging 清理。

syscall 边界隔离到不同 inode 时绝不 unlink quarantine 对象；回滚只能 no-clobber，公开目标被占用
就保留对象并报告 quarantine 位置。因此公开 pathname 上的 replacement 不会被删除或覆盖。对有权
改写 quarantine namespace 的本地对手（典型是同一 UID；父目录若另行授权 writer 也包括在内），最后
一次身份复验与 private unlink 之间仍有 pathname API 无法消除的微小竞态；这里的承诺精确限定为公开
pathname replacement 安全，残余仅在 quarantine 物理清理。

paired deletion 未提交时，先稳定复验计划 metadata 的原身份与字节；仍安全才回收 staging，否则只
用 no-clobber hard link 恢复原路径，验证 staging/目标两链接的身份与字节，fsync `backups` 后再次
复验。恢复 durable commit 与 cleanup 分阶段记录：cleanup 依次执行 payload unlink、临时目录 fsync、
临时目录 rmdir、`run` 目录 fsync。目标占用、父目录/文件替换、未知 blocker 或任一步故障都不会导致
并发对象被覆盖或删除；错误按当前磁盘事实区分「恢复未提交并保留 payload」与「恢复已提交但 cleanup
不完整」，并报告 payload/临时目录状态。payload 尚在时位置为 `<root>/run/.retain-*/payload`，需
操作员核查归档与目标后人工收敛。

本次有隔离临时树回归，但**§10 包③的真机一次运行记录和两周后体积复核尚未采集**，不得以本段
替代那两项现场证据。

**一条要改默认值的定案：内测期把备份快照间隔从默认 15 min 调到 60 min**（`occ resident --backup-interval-ms 3600000`；默认见 `DEFAULT_SNAPSHOT_INTERVAL_MS`）。

算给自己看：8 个 agent、单份 workspace 归档按 5 MB 估。15 min 间隔 = 96 份/天/agent → **3.8 GB/天**，72 h 保留就是 11 GB，H 上既放不下也没人看。60 min = 24 份/天/agent → 0.96 GB/天，72 h ≈ 2.9 GB… 仍偏大，因此**日留存那 14 份单独算**：72 h 全量 ≈ 2.9 GB + 14 天日留存 ≈ 0.56 GB ≈ **3.5 GB**。这是可接受的上限；开测两周后按真实归档体积复核一次，超了就先砍 72 h 到 48 h，**不要先砍日留存**（日留存是「三天前那个版本」的唯一来源）。

代价如实写：一次删库最多丢 **60 min** 的工作。AC-6(b) 的判据是「可恢复」不是「零丢失」，所以判据不受影响；但这件事要写进内测公告，别让人以为快照是连续的。

## §6 回滚

**回滚的定义**：把内测环境退回一个**已知好**的状态，且知道这次退回丢了什么。五级，从便宜到贵，**先试便宜的**。

### L0 · 进程级（RTO ≤ 2 min）

**用在**：某个节点不响应 / 控制台 502 / 注册中心死了。

```
① 该机 beta-down.sh <name>        # 只停这一个，不动别的节点
                                  # v1.2：在 H 上给一个铺过链路的节点名时，它的隧道与
                                  #       镜像 timer 一起停并取消自启（说明见下）
② tail -20 logs/<name>.err        # 抄进运维单页，不看就重起 = 下次同样死法
③ 该机 beta-up.sh                 # 幂等，已在跑的不会被重起
④ beta-smoke.sh                   # 判据：按名解析 + 真拨通 + 审计链 intact
```

**第①步在 H 上多做的那件事是 v1.2 新增的行为，不是新增的步骤**（四步编号不变——`demo/env/beta/`
下的脚本注释按编号引用着它）：H 上自己不跑常驻，`run/` 里根本没有节点名对应的 pid 文件，所以
在 H 上「停掉 `<node>`」唯一有意义的解释就是切断通往它的那条链路。判据是 `ops/tunnel-<node>.env`
在不在——`beta-down.sh` 只对真的铺过链路的名字动手。

**2026-09-26 修订（舰队部署补记）：① 不再只认 pid 文件，③ 的就绪要「刚起的那个 pid」在应答。**
p1 上旧树留下的 pid 文件对不上真进程，① 报「本来就没在跑」而旧进程照跑、占着端口；③ 起的新进程
EADDRINUSE 退出，就绪探测却被旧进程的应答骗成绿。现在 ① 在 pid 文件之后按命令行（`resident` +
`--node <name>` + 本内测根的工作区 / 配置根）再认一遍并按同一流程停；认不出而端口被占时只报不杀、
以非零退出——**绝不按端口挑人杀**，H 上 38625 是它自己身上那个节点。③ 在端口已被占时不起新进程，
就绪判据是「pid 活着 + 启动行是本节点 + 本机查得到的监听者就是这个 pid」。怎么读输出见
`demo/env/beta/README.md`「pid 文件对不上真进程时」。

**③ 之后 `grep priorLife logs/<name>.out` 看上一条命是怎么结束的**，和 ② 那几行一起抄进运维单页。
这一行紧跟在启动 banner 后面，由节点自己打出：`killed` = 上一条命没走停机路径（OOM、`kill -9`、
断电，或 ① 等不到 SIGTERM 改用了 SIGKILL，这种情况 ① 自己会报），行里带着那条命的
`pid` / `startedAt` / `updatedAt`，拿 pid 去 `dmesg` / `journalctl -k` 里对，才分得清是哪一种；
`clean` = 自己停下的；`unknown` = 配置根里没有可读的记录（首次启动也是这个）。它只是取证，节点不会
因为它改变任何行为；旧构建没有这一行。

不动任何数据。**80% 的故障应该止步于这一级**；止不住再往下。

**v1.1 补一条已验事实：在 H 上重起「H 腿」那一套（注册中心 + 控制台）不会动到隧道。**
四条 `ssh -L` 是独立的长驻进程，重起一轮注册中心与控制台之后不需要重建隧道，也不需要等它们
回来。

**v1.2 更正上面这条的后半句：`beta-down.sh` / `beta-up.sh` 现在认识那四条隧道了。**v1.1 写
的「两个脚本不认识它们」「隧道断了 `beta-up.sh` 修不好」是当时的现场形态——那时四条 `ssh -L`
是手搓的、仓库里没有出处。现在它们由 `peers.conf` 的 `node` 坐标行派生成 `systemd --user`
单元，于是：

| 动作 | 现在对链路做什么 | 出处 |
|---|---|---|
| `beta-up.sh --role host` | 建 / 收敛 / 收残，**已在跑的一律不重起**；单元文件被改写而实例在跑时，在末尾列出实例并给出维护窗口里的 `systemctl --user restart` | `provision_links` / `sweep_orphan_links` / `ensure_unit` |
| `beta-down.sh`（不给名字） | 按停机顺序最后停链路：隧道与镜像 timer 都停并**取消自启** | `beta_stop_link` |
| `beta-down.sh <node>` | 只切该节点那一条（前提是它铺过链路） | 同上 |
| `beta-reset.sh --purge-links` | 再删链路的**生成物**（`ops/` 与五个单元文件）；`mirror/` 一条不动 | `beta-reset.sh` |

**所以「隧道断了 `beta-up.sh` 修不好」也不再成立**：`beta-up.sh --role host` 会把停掉的单元
重新拉起来，并且**在返回之前对每个隧道口真读一次应答**（`wait_tunnel_live`），读不到就带分诊
命令 die。但**症状的读法一个字不改**：「进程都在、名册也在线、就是拨不通」时先看链路再看节点
（§9.8），只是现在看的是 `systemctl --user status qianmo-tunnel@<node>` 而不是 `ps` 里那几个
`ssh`。

**要重起在跑的隧道，只有维护窗口里手动那一条路。**`beta-up.sh` **绝不 restart** 任何在跑的
单元——重起隧道 = 该节点在几秒内不可达，注册中心的租约 90 s 兜得住，但正在跑的投递会断。

### L1 · 状态级（RTO ≤ 5 min）

**用在**：名册与实际对不上（有幽灵条目 / 少了条目），且 L0 重起注册中心没解决。

```
① 停注册中心
② 从 state/snapshots/ 取最近一份 registry-<ISO>.json 覆盖 agents.json
③ 起注册中心（带全部 --register）
④ 名册栏确认四个地址全在
```

**不清审计链、不清 workspace、不动节点。**注意租约会被按当前时钟重判（§2.4），所以快照里超过 90 s 的条目本来就会被丢掉——这一级真正救回的是「`--register` 之外那些手工注册的条目」，而按 §2.4 的硬规矩，那种条目本来就不该存在。**如果这一级经常被用到，说明那条硬规矩没被遵守，去修规矩不是修状态。**页面上注册的条目不靠这一级：控制台的登记簿会在一个续租周期内把它们重新注册回来（`console.md` §7.3）。

### L2 · 配置根级（RTO ≤ 15 min）

**用在**：某个节点行为异常，怀疑配置根里的状态坏了（会话表 / 准入台账 / 节点身份）。

```
① 停该节点
② 把当前配置根**改名**成 config.bad-<ISO>   ← 不删！审计链在里面
③ 解开 state/snapshots/config-<node>-<ISO>.tar.gz
④ 起该节点，跑 beta-smoke.sh
⑤ 在运维单页写一行：「<node> 于 <T> 回滚到 <快照时间>，<T1>..<T2> 段审计在 config.bad-<ISO>」
```

**第 ⑤ 步是这一节最容易漏、后果最大的一步。**配置根里装着审计链——恢复旧快照等于把链退回旧尾部，之后的 append 会接在旧 hash 上，中间那段记录**在当前文件里消失了、但在 `config.bad-<ISO>` 里还在**。不留这一行，三天后查链的人会看到一段无法解释的空白，然后开始怀疑审计机制本身。**回滚配置根不是撤销历史，只是把历史挪到旁边。**

快照哪来：**每次升级窗口前对每个节点的配置根做一次 tar 快照**，落 `state/snapshots/config-<node>-<ISO>.tar.gz`，保留最近 4 份。

### L3 · 代码级（RTO ≤ 5 min）

**用在**：升级之后坏了（§7），且不是配置问题。

```
① 该机 beta-down.sh
② dist → dist.prev 换回来（升级时保留的上一版构建产物）
③ beta-up.sh + beta-smoke.sh
```

**定案：每次升级在各机保留上一版 `dist/` 为 `dist.prev/`，回滚只换构建产物、不重跑 `bun install`。**理由：重跑 install 会把「依赖版本」变成第二个变量，而回滚的全部价值就是**只改一个变量**。（`bun.lock` 是 pin 死的，但冷缓存下的重装仍可能拉到不同的平台可选依赖——`demo-env.md` §4.4 实测过 macOS 1717 包 / Linux 1737 包的差异。）

### L4 · 整机重建（RTO ≤ 60 min）

**用在**：某台 VPS 没了 / 被重装 / 磁盘满到起不来。

```
① 新机器按 demo-env.md §4.1 装 bun（pin 1.3.13）+ node，再跑 bootstrap.sh
② beta-seed.sh 铺目录与工作区
③ 从 state/snapshots/config-<node>-*.tar.gz 恢复配置根   ← 关键
④ 从 H 的运维副本写回该节点的 PSK
⑤ beta-up.sh + beta-smoke.sh，在控制台确认该地址回到名册
```

**v1.1：重建一台节点机时多三件事**，漏掉任何一件的表现都是「起来了但拨不通」——

```
⑥ 把 H 的公钥写进新机器的 authorized_keys，并带上那一行选项：
   command="…",restrict,port-forwarding,permitopen="127.0.0.1:38625"（§2.6 / §8.3）
⑦ 重建该节点那条隧道单元（ssh -L 3863x:127.0.0.1:38625），并**真穿一次**确认
⑧ 重建该节点的审计镜像 timer（5 min，§4.3）
```

**⑦ 的「真穿一次」不能省。**隧道的本地口由 `ssh` 自己 LISTEN，所以「端口收不收连接」在隧道
形态下**永远是绿的**（§9.8）；`-L` 建得起来也不是判据（`permitopen` 是在 channel 打开的
那一刻才拒，不是建立转发的那一刻——`node-provisioning.md` P-12 实测）。判据只有一个：真拨
一次握手。

**H 整机重建**是同一件事乘以四：**重建 SSH 密钥对 + 四条隧道单元 + 四条镜像 timer**，外加
原本就有的注册中心 / 控制台 / 反代 / 备份服务。新密钥意味着四台节点的 `authorized_keys`
都要改一行——**这四行是四台机器上的四次编辑，不是一个配置项**，RTO 要按这个算。

**第 ③ 步不能跳。**节点身份（`qianmo/identity/<node>.json`）在配置根里，`loadOrCreateNodeKeys` 是「首次创建、之后永不替换」。跳过恢复 = 生成新密钥对 = **公钥变了**，于是：注册表里的 `publicKey` 要重发布、所有把它写进 `--trust <node>=<publicKey>` 的对端都要更新。那不是回滚，是**换了一个节点**，必须在告知面上按「新节点上线」来说，不能说成「恢复了」。

配置根快照也没了的情况：接受换身份，但**必须**在运维单页与内测公告里各写一行，且当天不做其他变更（不要在身份变更的同一天升级代码，否则出问题分不清是哪件事）。

### 6.4 回滚不了的三样

| 东西 | 为什么 | 只能怎么办 |
|---|---|---|
| **已发出的 token** | 发出去就是别人机器上的一个字符串 | 只能轮换（§3.4），不能收回 |
| **审计链已写入的记录** | append-only fd，没有 seek / truncate / delete | 只能挪走（L2），不能撤销 |
| **turn 对 workspace 的写** | 那是数据面的事，不是环境面的事 | 走备份恢复（`demo/ac6b-restore.sh` 那条路，实测 11 条 check 全绿 / 19 ms），不在本节 |

### 6.5 原理（v1.1 立为硬规矩，v1.2 起由脚本代劳）：**改端点之前，注册中心的落盘表与活表都要处理**

**先说结论：这条从「一条要人记得的运维纪律」变成了「脚本自己查、自己处置」**，
`beta-up.sh --role host` 在起注册中心之前跑 `assert_registry_matches_peers`。本节保留为
**原理说明**——脚本能替人做动作，替不了人理解为什么，而这个病根静默到没有任何一行日志会
提到它。

原来那条纪律的表述是：

> **改 `peers.conf` / `--register` 之前，先把注册中心的落盘表（`agents.json`）挪走或删掉，
> 再重起注册中心。**

理由在代码里，而且是**静默**的：`demo/lib/p81-registry.ts` 的 `announce()` 对每个地址
**先续租**——`registry.heartbeat(address)` 返回非 `null` 就 `continue`，**整条 `--register`
被跳过**。而注册中心带 `--state` 重启时会 restore 落盘表，租约只要还没过期（TTL 90 s，
§2.4），旧条目就是活的。于是：**你改了端点、重起了、什么错都没报，注册中心继续对外发旧
端点。**症状是 `beta-smoke.sh` 全红而 `peers.conf` 明明是对的——一个「配置看起来完全正确、
行为却是旧的」的现场，是这套拓扑里最贵的一类排查。

**v1.2 补上原文缺的那一半：不一致有两处，挪文件只治得了其中一处。**

| 哪张表 | 在哪 | 不一致怎么处置 | 脚本怎么做 |
|---|---|---|---|
| **落盘表** | `state/registry-agents.json` | **改名挪开，不删**（审计与排查都要留证） | 逐条比对 `peers.conf`，不一致就 `mv` 成 `registry-agents.json.stale-<ISO>` 并打出前后两个路径 |
| **活表** | 在跑的那个注册中心**进程的内存里** | **必须重起注册中心**——挪文件对它一点用都没有 | 逐个地址问 `/v0/agents/<地址>`，答的端点与 `peers.conf` 不一致就停掉注册中心，随后用新端点重新起一份 |

第二行是这条规矩最容易漏掉的那一半：**表已经在内存里了**，`--state` 那个文件只是它上次的
快照。所以「我把 `agents.json` 挪走了，怎么还是旧端点」有一个完全平淡的答案——你挪的是快照，
在服务的是内存。**这也是 `beta-up.sh` 唯一一个会重起在跑组件的场合**，且只在真的检出不一致
时发生（`assert_registry_matches_peers` 的 `live_bad` 分支）；它会明说自己在重起什么，因为
一个「幂等脚本」突然重起了一个组件，不说清楚就是下一次排查的起点。

顺带说清它和 §2.4 那条硬规矩（「凡是要长期存在的地址必须写进 `--register`」）的关系：
那条说的是**注册中心停机超过 90 s 之后只有 `--register` 里的会回来**；这条说的是**停机不
超过 90 s 时 `--register` 反而不生效**。两条都成立，因为它们说的是同一个 `announce()` 在租
约的两侧各自的行为。

## §7 升级面

### 7.1 顺序定案：注册中心 → 节点（一次一个）→ 控制台

**注册中心先升。**它是唯一**无状态可重建**的组件：表是 soft state（90 s TTL + 20 s 心跳），落盘文件读不动就空表重来（`FileRegistryStore.read()` 的注释写明这是刻意的恢复姿势）。所以「新版本能不能起来」这个问题应该先在**最便宜的地方**问一次——如果它起不来，四个节点一个都还没动。

**节点一次一个，中间跑一次 `beta-smoke.sh`。**节点重启会中断在跑的 turn，一次一个把影响面压到四分之一。四个节点的窗口预算 **30 min**（含每次的就绪探测——2 vCPU 机器上首次拨号实测 6.5–7.1 s，探测重试会吸收掉）。

**控制台最后升。**它是用户唯一看得见的面：它挂着的时候，用户以为整个网络挂了。让它在其余部分都已经绿了之后再动。

**反过来的顺序（先节点后注册中心）在协议未变时也能工作**，它只是把最贵的问题放在最前面问。所以不是「不能」，是「不划算」。

### 7.2 什么时候不能滚动升级

**协议不兼容变更走停机窗口，不走滚动。**判据是机器可查的：

```
git diff <上一个已部署版本>..HEAD -- packages/protocol/src
```

非空即走停机窗口（全部停 → 全部换 → 全部起 → 冒烟）。理由：滚动升级期间网络里同时存在两个协议版本，而阡陌**没有版本协商的降级路径**（协商扩展在 `protocol.md` §13，管的是能力不是线格式）。滚动一个不兼容的线格式改动，得到的是一半节点互相听不懂，而症状会表现为「偶发投递失败」——那是最难查的一类。

### 7.3 窗口

**每周二 21:00–22:00（校内低谷），最多每周一次。**上游同步（章程 §5.7 定稿的每 2–4 周 / 每 5–8 release）**落在其中某一个窗口里，不另开窗口**——上游同步在内测环境眼里只是「一次代码升级」，它的特殊性全在合入阶段，部署阶段没有任何不同。

窗口之外只做 §6 的 L0（进程级重起）。**L1–L4 都是有数据后果的动作，不在工作时间做。**

### 7.4 告知面：用 `--label`，不新建东西

`--label` 是控制台页头的一行字（≤120 字符），**它是唯一一个 50 个人都会看到、且不需要账号体系的广播位**。用它，不要为了公告新建任何东西。

| 时点 | label 写什么 |
|---|---|
| 平时 | `阡陌内测 · 审计视图：beta-1` |
| 窗口前 24 h | `阡陌内测 · 维护窗口 08-25 21:00 · 审计视图：beta-1` |
| 窗口进行中 | `维护中 · 预计 22:00 恢复` |
| 窗口结束 | 改回平时 |

外加内测群一条公告（窗口前 24 h 一条 + 结束一条）。

**改 label 要重起控制台**——这正好和 §3.2 的定案互相印证：token 必须显式固定，否则每改一次公告就换掉全员的链接。这两条是同一个约束的两面。

**v1.2：label 现在持久化在 `<内测根>/console.conf` 里，不再只活在环境变量中**（§4.3）。这
改的不是「改 label 要重起」这一条（它仍然成立），而是**反过来那一条**：此前一次与公告完全无关
的重起——跟随升级、机器重启——就会把 label 静默清空，页头于是从「审计视图：某节点（镜像 ·
滞后 ≤ N min）」变回默认，而**没有任何人会因此收到通知**。现在改法有两种，效果一样：临时设
一次环境变量（会被回写，所以下次也记得），或者直接编辑 `console.conf` 的 `LABEL=` 行；两种都
要 `beta-down.sh console` 之后再 `beta-up.sh --role host` 才生效（起进程是幂等的，在跑的那份
不会被重起）。

## §8 传输加密：一期用 PSK，且是每节点一把

### 8.1 定案：PSK，不等 mTLS

**理由是排期事实，不是技术偏好**：P11.2 的任务包原文就是「生产级加密与密钥分发的**设计**（只设计，不实现）」，mTLS 的**实现**在 M1 候选池里且未排期。内测一期与 P11.2 并行推进，等不到实现。所以一期必然是 PSK——章程 N-3 在 M1 被解除之前，这本来就是既定形态。

**切换到 mTLS 的时点判据（写死，免得将来靠感觉判断）**，三条同时成立才在**下一个升级窗口**替换：

1. mTLS 实现落地，并在**两台真实机器**之间跑通一次（不是单测、不是同机双进程）；
2. 证书签发 / 轮换的运维流程写完，且回滚路径（换回 PSK）可照做；
3. `SIGNED_TASK_POLICY` 切默认的时点与回滚写清（P11.2 的 DoD 本来就要求这一条）。

替换动作本身与 §8.4 的 PSK 轮换**同形**：一次换一个节点、停 → 换 → 起 → 冒烟。

### 8.2 定案：每节点一把，不是全网一把

**理由**：无 sudo 的 VPS 上入站端口 38625 必然对全网开放（§2.6），PSK 就是那个端口上唯一的门。一把通用 PSK 意味着**任何一个节点被拿下、或任何一次误发到群里，等于四个节点全开**。每节点一把把爆炸半径从「全网」压到「一个节点」。

**控制台的适配**：节点进程自身仍只从 `QIANMO_TRANSPORT_PSK` 读取本机那一把；控制台的
命名 `--wake-url <node>=<url>` 则只读取
`QIANMO_TRANSPORT_PSK_NODE_<node 的 UTF-8 大写十六进制>`。例如 `beta-1` 对应
`QIANMO_TRANSPORT_PSK_NODE_626574612D31`。这个编码对每个合法协议节点段一一对应；节点名
语法以 `packages/protocol/src/address.ts` 为准。命名目标不能回退到全局变量：一把缺失只让该节点在页面上
显示不可用，不影响其他可用目标。

**为什么不为了方便就用一把**：方便的那一把，正是「一个人退出内测就要换全网」那类问题的加密版本。§3 里我们已经因为 token 只有一枚而接受了一次这种代价，没有理由在唯一的传输门禁上再接受第二次。

### 8.3 放哪：一张表管全部凭据（v1.1 合并）

v1.0 这里只管 PSK。现场又多了两类持密面（控制台两枚 token 的文件入口、H → 节点的 SSH
密钥），三者的存放规矩本来就是同一条，所以合并成一张表——**分散在三处的存放规矩，就是三处
可以各自漂移的存放规矩**：

> `demo/env/beta/README.md`「审计见证」。
> 控制台带 `--anchors` 时只从名册取节点公钥。**这一步已由脚本自动登记**：H 腿给注册中心带上每个节点的公钥
> （走隧道的节点取 `peers.conf` 坐标行的 `public-key=`，跑在 H 上的节点读本机身份文件），随每一次登记——包括
> 租约过期后的重新登记——一并发布，不会再丢。**缺省行为与改动前一致**：坐标行没写 `public-key=`、或直连的远端
> 节点（H 读不到它的身份文件），登记照旧不带公钥，H 腿逐节点告警；后者仍按 README「审计见证」第 ⑥ 步手工发布。
> 来源与细节见 `demo/env/beta/README.md`「名册上的节点公钥」。公钥不是凭据，不进上表。

H 需要全部四把 PSK，因为唤醒与投递都从 H 发起。**节点机上不存别人的 PSK**——一台 VPS 被拿下时，攻击者拿到的只有它自己那一把。**节点上也不存任何指向 H 的凭据**：SSH 信任严格单向（H → 节点），这条不只是纵深防御，它是 P11.4 机外见证那条前提（见证方与被见证方处在不同失陷域）在本形态下仍然成立的唯一理由（`node-provisioning.md` §4.3）。

**`authorized_keys` 那一行是一道会静默失效的门。**它住在一个我们不拥有的文件里——云厂商的元数据服务、别人的配置管理、同事的一次手工编辑都可能改写它，而**被改写之后那把 key 照样能认证，只是不再受限**：隧道照常工作、页面全绿、什么都不报。**一个失效之后长得和成功一模一样的防线，必须有人定期去看它还在不在。**列进运维单页的巡检项。

**永远不走命令行。**命令行上的密钥就是这台机器每一份进程列表里的密钥；这与 `occ resident --backup-url` 要求 `QIANMO_BACKUP_WRITE_TOKEN` 走环境变量是同一条纪律（`console.md` §4.4）。v1.1 起控制台的两枚 token 也已经照这条办（§3.2）。

生成用 `demo_random_hex 32`（64 hex 字符，远超 `PSK_MIN_LENGTH`）。**演示环境的 PSK 与内测环境的 PSK 是两套，永不共用**——演示 PSK 在 `.demo-env/secrets/` 下，是一次性的演示密钥。

### 8.3.1 爆炸半径重算（v1.1）：一笔要还的债

§8.2 的定案是「每节点一把 PSK，把爆炸半径从『全网』压到『一个节点』」。**那句话说的是节点侧
的爆炸半径，它仍然成立；H 侧从来不成立，而 v1.1 让它更不成立了。**如实摆出来：

| 拿下谁 | v1.0 的后果 | v1.1 的后果 |
|---|---|---|
| 一台 VPS 节点 | 一把 PSK（它自己那把）+ 该节点的审计链与工作区 | **不变**（单向信任：节点上没有任何指向 H 的凭据） |
| **H** | 四把 PSK + 归档 token + 控制台两枚 token → 能对四个节点**说话** | 以上全部，**再加一把能在四台节点上跑那五类动作的 SSH 私钥**，以及**四条隧道断掉时整个网络静默**（§2.4） |

**v1.4 补注（2026-10-03，章程 v2.22）**：P18 落地之后，H 这一行还要再加两样：全部模型密钥（主密钥与密文在同一台机器上，信封加密在这里帮不上忙），以及每台节点一把能执行第六类动作的 SSH key——它能改写节点的模型服务，把节点的对话流量导到别的端点，但仍然不能执行任意命令（闭合由节点的 sshd 强制）。这是负责人接受的代价，见 [`providers-console-m1.md`](./providers-console-m1.md) §7.7。

**四把 PSK 副本集中在 H 一台机器上，这件事与 §8.2「每节点一把、爆炸半径限一台」的原意是相
悖的**——每节点一把买到的边界，在 H 上被一份全量副本抵消掉了大半。v1.0 里这是一个可以辩护
的取舍（H 是唯一的发起方，它总得能对每个节点说话）；v1.1 之后不再只是取舍，因为同一台机器
上又多了一把能在每台节点上执行代码的私钥。

**这是一笔明确记账的债，不是「已解决」**。还债的方向有两个，都不在一期：① 每节点一把 SSH
密钥（现场现在是**一把服务四台**，`node-provisioning.md` §4.3 第 2 条同样把它记成待还的债）；
② 把 PSK 的持有从「H 上一份全量明文副本」改成按需解封（`key-distribution.md` 的方向）。
一期的处置只有一条，而且要写进运维单页：**H 的失陷是这套环境的全域失陷，按这个前提做它的
访问控制与巡检**。

### 8.4 怎么换

**节奏：每 4 周 + 事件驱动**（任一节点重装、人员变动、疑似泄漏）。

换 PSK 会把还连着的对端**全部踢下线**（这正是 `demo/env/reset.sh` 默认不换密钥的原因），所以**只能在升级窗口做**。

**每节点一把的运维红利就在这里：一次只换一个节点，其余三个不受影响。**流程：

```
① H 上生成新的一把
② 停该节点
③ 写进该机 secrets/transport-psk（0600），删旧值
④ 起该节点
⑤ 更新 H 上 secrets/peers/<node>.psk
⑥ beta-smoke.sh：从 H 对该节点真拨一次
⑦ 控制台是幂等启动的；若它已在跑，重起控制台，使该节点新导出的命名 PSK 生效
```

第 ⑦ 步对当前 `peers.conf` 中的每个控制台唤醒目标都成立；缺少某一把 PSK 时控制台局部降级，
不会拿另一节点的密钥代拨。

## §9 现状限制清单

按「会咬人的程度」排。**每一条都必须在内测开跑前让那 2 个运维知道**——它们不是缺陷，是已知边界，但不知道就会被当成缺陷去查。

**v1.1 新增的两条（§9.8、§9.9）按咬人程度本该排在很靠前的位置，但它们追加在末尾**：小节号被
`demo/env/beta/*` 的注释与 README 逐条引用着，重排会让那些指针静默指错。**读的时候把它们当成
§9.1 之后的第二、第三条读。**

### 9.1 名册说的「在线」不等于节点活着（一期最容易骗人的一条）

演示环境的注册中心进程**代替节点做心跳**：它按启动参数里的 `--register` 列表，每 20 s 给每个地址续一次租（`demo/lib/p81-registry.ts` 的 `announce`）。所以只要**注册中心**活着，名册上就一直是「在线」——**哪怕那个节点的机器已经关机了**。

这在演示里无害（演示时四个进程一起起、一起停），在内测里是真会咬人的：用户在控制台上看到 beta-3 在线，点唤醒，得到一个超时。

**一期的处置（不改代码）**：`beta-smoke.sh` 每 5 min 由 H 上的定时任务跑一次，对四个节点各**真拨一次**；任一失败就把控制台 `--label` 改成 `beta-3 疑似不可达 · 排查中`。这是拿现有的探测器（`demo/lib/p81-probe.ts` 做的正是「解析 + 真拨」）补一个巡检，不新建机制。

**正解**是让节点自己心跳（节点自注册 + 自续租），那要给 `occ resident` 加 `--registry`，属于新功能，**M1 前两个迭代不排**。登记进 §10 的候选，不进一期。

**这一条不是单独成立的，它有一个同向的搭档，必须一起读**：隧道形态下「那个端口收不收 TCP
连接」**也**恒为真（§9.8）。两条叠起来是三个绿灯一个真相——名册说在线（注册中心代它心跳）、
TCP 说端口开着（`ssh` 自己在本地 LISTEN）、而节点可能已经关机两小时。**所以巡检的判据只能是
真读一次对端应答或一次真握手**，绝不能是端口探测；`beta_tcp_open` 被喂一个隧道口时直接 die，
就是为了不让这条假绿再被写进任何一个新脚本。

### 9.2 注册中心零鉴权

`packages/registry/src/http.ts` 里没有一行 token 检查。**绝不能把它暴露到 H 的回环之外**，这条已经是 `console.md` §8.2 的硬规矩，本文只是把它落到部署上（§2.5 的反代 allowlist、§2.6 的绑定表）。

> **2026-09-27（P15.8）**：注册中心可以要求一枚写 token，挡住 H 上其他本地账号的写入；读仍然公开，上面那条硬规矩不变。内测环境按 `secrets/registry-write-token` 在不在决定开不开，启用顺序见 `demo/env/beta/README.md`「注册中心写 token」。

### 9.3 多节点视图不做跨链时序合并

见 §4.3。控制台把每条链当作独立证据显示，故障也独立呈现；它不伪造一个跨节点的总顺序。
跨节点还原仍要保留节点名和各自的链内序号。

### 9.4 审计的「外部改动无法阻止」

三句承诺里只有前两句成立：写入方确实改不了、外部改动确实可检测、外部改动**没有被阻止**（`console.md` §8.3）。**一个有本机写权限的人可以整篇重写审计链并重算全部哈希，控制台会显示「完好」。**内测环境里有写权限的人 = 那 2 个运维 + 各 VPS 的 root。缺口归 **P11.4**，一期不解决，但**必须让评审知道内测环境是在这个前提下运行的**。

### 9.5 没有 TLS 在控制台自己身上

控制台自己不做 TLS，全靠反代那一层（§2.5）。这意味着**反代与控制台之间的回环流量是明文的**——同机上的其他进程理论上能抓到。H 上跑的东西全是我们自己的，一期接受。

### 9.6 控制台除登录路由外不限流（v1.1 限定）

面板的 HTTP 面**只有 `POST /login` 有限流**：5 次免罚，之后每失败一次封锁时长翻倍（第 6 次 1 s、第 7 次 2 s…），**从第 15 次起封顶 300 s**，闲置 1 小时遗忘，成功一次即清零（`console.md` §8.4）。名册、审计、片段、对话、SSE 一概不限。

**反代那一层仍然要加一个粗粒度限流**（比如每 IP 每分钟 120 请求），够挡住误配的轮询和无脑扫描，不够挡有针对性的攻击。页面自身的局部刷新频率要与这个数对齐，别自己把自己限了。

**反代上那条规则不能被当成登录限流的替代品**，反过来也不行：控制台自己那条守的是「一个答 200/401 的文本框是一台猜测预言机」，而反代那条守的是流量。

**多一条部署侧的坑**：登录限流按 socket 对端地址计数，**不认 `X-Forwarded-For`**（直连时那个头由客户端自己写）。所以在我们这个「单层反代 + 回环 upstream」的形态下，**所有人共享一个桶**——好处是任意 IP 的攻击者都被限住，坏处是**一个连错密码的运维会把其他人一起挡住，最坏 5 分钟**。这不是缺陷、是已知取舍，但要让那 2 个运维知道，否则第一次发生时会被当成「控制台挂了」。

### 9.7 并发上限是节点数

节点级 turn 串行（roadmap v2.15 决策 Q3：同节点多 agent 的真并发要回到基座核心，在 M1 候选池未排期）。**4 个节点 = 4 个并发 turn**，与内测人数无关。队列深度与等待时间一期**不做保证**，观测口径是 `state/<node>-timings.jsonl`（这也是 §5 里它必须全程保留的原因）。

### 9.8 隧道口的 TCP 是**假绿**（v1.1 新增，比 §9.1 更会骗人）

`ssh -L 3863x:127.0.0.1:38625` 的本地口**由 `ssh` 自己 LISTEN**，与远端死活无关。远端节点
进程没了、机器关机了、隧道另一头根本没通，本地那个端口**照样 accept**——连接进来之后立刻被
关掉，但那已经是 accept 之后的事了。

**后果**：**任何形如「这个端口收不收连接」的检查，在隧道形态下永远是绿的。**这一条把 §9.1
那个骗人的东西又叠了一层：名册说在线（注册中心代它心跳）、TCP 说端口开着（ssh 自己在听）、
而节点可能已经关机两小时了。

**唯一算数的判据是真握手**——PSK 握手成功、或者一次真投递拿到回执。`beta-smoke.sh` 的
probe 做的正是「解析 + 真拨」，它是对的；**不要**为了「快一点」把它换成 `nc -z` 之类的端口
探测，那个换法在直连形态下勉强能用，在隧道形态下等于把探测器换成一个恒返回 true 的函数。

**v1.2：这一条从「一条纪律」变成了「代码里的两道门」，另外多出一个比握手便宜的合法判据。**

| 判据 | 答的问题 | 现状 |
|---|---|---|
| **真读一次对端应答**（`beta_endpoint_live`） | 隧道另一头那个**进程**还在不在 | ✅ 隧道口就绪的唯一判据。发一条普通 GET 并读一行应答，节点的 WebSocket 服务回 `HTTP/1.1 426 Upgrade Required`——**那一行只有节点进程产生得出来**，中间只转发不应答的链路伪造不出来。三种红都是对的：连不上、连上后立刻 EOF（= 假绿那个形状）、超时没有任何字节 |
| **PSK 握手 / 一次真投递** | 认证与数据面通不通 | ✅ 仍然是最终判据（`beta-smoke.sh` 的 probe）。`beta_endpoint_live` **答不了这个**——它只回答就绪，不回答鉴权 |
| **TCP 连得上**（`beta_tcp_open`） | 什么都不答 | ❌ 喂它一个隧道口**直接 die**。把一条恒真的判据留在那儿，比没有判据更糟 |

`beta-up.sh` 建完隧道之后用第一条等就绪（`wait_tunnel_live`），`beta-smoke.sh` 的 ⓪ 节对每条
隧道查「单元 `active`」+「真读一次应答」两条，**缺一不可**——单元 `active` 只证明 `ssh` 进程
活着。三条负向自验的复跑命令在 `demo/env/beta/README.md`，本文不复制。

同一条的另一面在 §6 L4 第 ⑦ 步：建隧道之后必须**真穿一次**，因为 `permitopen` 也是在 channel
打开的那一刻才拒绝，不是在建立转发的那一刻（`node-provisioning.md` P-12 实测）。

### 9.9 H 是数据面单点（v1.1 新增）

见 §2.4 的第 ② 张表：三台节点的 38625 被云厂商安全组挡死，它们在网络上的可达性完全依赖 H 上
那四条 `ssh -L`。**H 挂 = 三个节点在网络上消失，且运维笔记本也无法直连接管**（笔记本同样拨
不通 38625）。

这与 §2.4 原本那句「注册中心挂了不影响已建连接」**不矛盾但常被读混**：那句话说的是注册中心
**进程**，而它成立的理由正是「数据面不经过 H」——那个理由现在只对注册中心成立，对 H 这台机器
不成立了。**退出条件是安全组放开 38625**；在那之前，兜底形态必须被显式标注为降级态，不能和
直连长得一样（`node-provisioning.md` §7.2 的三条要求）。

### 9.10 那把 key 的 `permitopen` 只管一个方向（v1.2 新增）

`restrict` 关掉一切，随后的 `port-forwarding` **同时**开回本地转发（`-L`）与反向转发（`-R`），
而 `permitopen` 只约束前者——约束后者的是 `permitlisten`，那一行里没有。所以这把 key 除了
建那条隧道，还能**让节点开一个监听端口**。

2026-08-18 在 rowan 上实测：带 `-o ExitOnForwardFailure=yes` 的 `-R 127.0.0.1:<高位口>` **被接受**
（用完立即关闭）。这不是推断。

**危害有限但不是零。**威胁模型是「H 被拿下」：到那一步攻击者本来就能读审计链、能拨节点的
入站口（那一层由 PSK 挡）。`-R` 多给的是「让节点上的本地进程有一条通回 H 的路」。所以它是
纵深防御的缺口，不是当前的主要暴露面——**但它让 §8.3 那句「转发不到别的地址」在字面上是错的**，
已改。

**关掉的办法**是在那一行里补一条匹配不到任何有用目标的 `permitlisten`。这要改四台节点的
`authorized_keys`，属于访问控制变更，**留给一个有人在场的维护窗口**，别顺手做——
改错那一行的表现是隧道照常工作、什么都不报（§8.3 末尾那段）。

## §12 意外收获：跨公网那一段现在是加密的（v1.1 新增）

隧道是被安全组逼出来的，但它顺手改掉了一件本来记在风险栏里的事。**先说清楚它改了什么、
没改什么**：

| | v1.0（38625 直连） | v1.1（经隧道） |
|---|---|---|
| 跨公网那一段 | 明文 `ws://`，PSK 只用于**握手认证** | **SSH 加密隧道**，里面再套 PSK 握手 |
| 消息体在公网上 | 明文可读 | 隧道内，不可读 |
| 中间人改写消息 | 靠协议层自己的完整性保证 | 隧道先挡一道 |

所以 §8.1「一期用 PSK 不等 mTLS」那条风险的**描述**可以相应放松一档：mTLS 相对 PSK 要买的
东西里，「传输保密性」这一半在经隧道的链路上已经由 SSH 提供了；PSK 在这条链路上退化成一个
**应用层的对端认证**，而不是唯一的安全边界。

**但这条放松只对经隧道的链路成立，不得写成全局结论。**三个必须一并记住的限定：

1. **它是现场形态的副产品，不是设计保证。**安全组一放开、兜底退役（§9.9 的退出条件），
   直连回来，这一档放松**当场消失**。一条会随部署形态消失的性质，不能被写进「我们的加密
   方案」。
2. **它不改变 §8.1 的切换判据。**mTLS 的三条时点判据（实现落地并在两台真机跑通、签发与
   轮换流程写完且可回滚、`SIGNED_TASK_POLICY` 的切换与回滚写清）**一条不动**——SSH 隧道
   买到的是保密性，不是身份体系，也不是密钥轮换流程。
3. **它对 §9.9 是净负债。**同一条隧道，一头买来保密性，另一头把 H 变成数据面单点。**两件事
   要一起记，不能只记好的那一件。**

一句话：**这是一笔可以如实记的收获，不是一个可以据此推迟 mTLS 的理由。**
